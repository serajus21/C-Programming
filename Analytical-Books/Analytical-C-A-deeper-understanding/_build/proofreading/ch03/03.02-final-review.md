## 1. Errors

**E1. Line 192: "too inclusive" is not in Defect Report #003, and "1992 complaint" misdates the complaint.**

- **Problem 1.** The sentence reads: "In its answer to a 1992 complaint that preprocessing numbers were "too inclusive" (Defect Report #003)…". Neither the question nor the response contains the word "inclusive".
- **Problem 2.** The question came from X3J11/90-011 (Terence David Carroll, 1990). It was published as DR #003 with the response on 10 Dec 1992.
- **Evidence.** DR #003, Question 1 (open-std.org/jtc1/sc22/wg14/docs/rr/dr_003.html): "I am surprised at the Committee's decision to allow such a loose description." The response: "It, contrary to your opening remarks on this topic, is not a ``loose description,''…".
- **Fix.** "In its answer to a 1990 complaint that the rule for preprocessing numbers was "a loose description" (published in 1992 as Defect Report #003), it explained…". Remove "too inclusive" from the Sources bullet too, if it appears there. It does not; line 802 is clean.

**E2. Line 292: the quotation from Rationale §3.1.4 contains the word "to", which the source does not have.**

- **Problem.** The text reads: 'its Rationale says the old method required the continuation "to start in the first position of the next line"'.
- **Evidence.** C89 Rationale §3.1.4: "…but this practice requires that the continuation of the string start in the first position of the next line."
- **Fix.** "its Rationale says the old method "requires that the continuation of the string start in the first position of the next line"". Alternatively, take the quotation marks off and paraphrase.

**E3. Lines 245 and 265: "EBCDIC, in which … the newline is 37" states as a property of EBCDIC what is only glibc's conversion table.**

**Problem.** EBCDIC has two candidate codes:
- NL, X'15' = 21;
- LF, X'25' = 37.

Conversion tables disagree on which one C's `\n` maps to:
- glibc's IBM1047 table maps U+000A to X'25', which is why GCC gave 37.
- IBM's own z/OS conventions use NL, X'15', as the line end.
- IBM i's ILE C uses 0x15 or 0x25, depending on a compile option.

The output 37 is correct for GCC on Fedora. The sentence "in which A is 193 and the newline is 37" is not a fact about EBCDIC, and line 265's "so it becomes 37" inherits the problem. 193 for `A` (X'C1') is correct.

**Evidence.**
- Red Hat bug 170072, "IBM1047 maps EBCDIC 0x15 and 0x25 incorrectly". There, glibc's maintainer writes that EBCDIC "sometimes is 0x15 LF and 0x25 NEL, while sometimes vice versa".
- IBM z/OS XML documentation: "the line ending character is typically a NL (x'15') character".
- IBM i ILE C/C++ Runtime Library Functions, "Newline Character": 0x15 or 0x25 depending on SYSIFCOPT.

**Fix.**
- Line 245: "…a different code, EBCDIC, in which `A` is 193."
- Line 265: "…the escape `\n` stands for the newline *character*, so it becomes whatever code the conversion table gives the newline: 37 in the table GCC uses here. (EBCDIC has two line-ending codes, 21 and 37, and IBM's own compilers on z/OS use 21; the choice belongs to the implementation, which is the point of phase 5.)"

This version is more accurate, and it also teaches the section's lesson better.

**E4. Line 385: "§03.01's change to `puts` happens later, inside phase 7, when GCC chooses instructions" is wrong about where the change happens.**

- **Problem.** The `printf`→`puts` replacement is done in GCC's middle end, on its internal tree form, long before any instruction is chosen.
- **Evidence.** In /tmp/r0302c, `gcc-14 -std=c23 -fdump-tree-all -c hello.c` writes a series of dump files. `puts` first appears in `hello.c.010t.lower`. It is absent from `005t.original` and `006t.gimple`. Instruction selection (RTL expansion and later) comes many passes after that.
- **Fix.** "The call is still `printf`: §03.01's change to `puts` happens later, inside phase 7, in one of GCC's early passes over this internal form (GCC 14's dumps show it in the pass called `lower`), still well before any instruction is chosen."

**E5. Line 568, with line 334: "Inside phases 1 to 7 the same reasoning fixes the order" is false for phases 2/3 and 5/6.**

**Problem.** The "same reasoning" is "each step does what can be known at its time". That reasoning does explain:
- phase 4 before phase 7;
- phase 7 before phase 8.

It does not force phase 2 before phase 3, or phase 5 before phase 6. Either opposite order would be just as well defined:
- Splicing after tokenizing would simply forbid continuing a name, and it would remove the trap of Listing 03.02-3.
- Joining literals before converting escapes would give `"\x41" "BC"` the meaning of `"\x41BC"`.

These orders are *precedence decisions*. That is exactly what the `:::why` box (line 39) and the precise box (line 56) teach. The committee chose them for stated purposes:
- 2 before 3, so that "*any* token" can be continued (Rationale §2.1.1.2);
- 5 before 6, so that concatenation never changes the meaning of the pieces, as in the standard's own `"\x12" "3"` example.

The pre-existing sentence at line 334 has the same flaw: "it is what gives such programs a definite meaning". Any fixed order gives a definite meaning; this order gives the useful one.

A demanding reader will see that the section contradicts itself here.

**Fix.**
- Line 568, replace the last sentence with: "Inside phases 1 to 7 two kinds of reason fix the order. Some are dependencies of the same kind: phase 4 must precede phase 7, because the parser must see the text *after* `#include` has pasted in the declarations and the macros have been replaced. Others are decisions about which rule wins, made for stated purposes: phase 2 precedes phase 3 so that any token, even a name, can be continued (at the price of Listing 03.02-3), and phase 5 precedes phase 6 so that joining literals never changes what each piece means (`"\x41" "BC"`)."
- Line 334, last sentence: "The order of the phases is not bureaucracy; it is what lets a literal mean the same thing whether or not another literal stands next to it."

## 2. Remaining gaps

**G1. Lines 192 and 211: the committee's answer in DR #003 lists five benefits, and the section says "three reasons".**

The response gives these benefits:
- "all tokenization for all implementations would now be the same";
- "no ``garbage'' character sequences would be able to be converted to valid C code";
- "skipped blocks of code could silently be scanned withou[t] generating needless and unnecessary tokenization errors";
- "the preprocessing tokenization of numeric tokens would be greatly simplified";
- "room for future expansion of C's numeric tokens was reserved".

The skipped-blocks reason is the instructive one the section omits. Text inside `#if 0` is still cut into preprocessing tokens in phase 3. A forgiving rule for numbers means that dead code full of odd numerals produces no errors (§22.05 will use `#if 0`).

Fix: change "give three reasons" to "give several reasons", and add one sentence after the second reason: "Another: text inside a block switched off with `#if 0` (§22.05) is still cut into preprocessing tokens, and a forgiving rule lets such dead text be skipped without errors."

**G2. Line 572: "The order compile, assemble, link is therefore not a convention; it follows from where the information … becomes available" claims more than the argument shows.**

The argument proves one thing: each unit must be translated before translated units are combined. It does not prove that machine-code *encoding* must come before linking:
- Plan 9's loader "combines the roles of second half of the assembler, global optimizer, and loader" (Pike, "How to Use the Plan 9 C Compiler").
- Go's toolchain inherited that arrangement: "instruction selection occurs partly after code generation" (go.dev/doc/asm).
- The section's own `-flto` parenthesis also bends the rule.

Fix: "What is forced is the order *translate each unit, then combine*; it follows from where the information needed by each step becomes available. Where exactly the last encoding into machine code happens is an engineering choice: GCC does it in `as`, before the link; Plan 9's linker, and Go's after it, finish some of the assembler's work during the link."

Also add this to the Inference bullet if kept.

**G3 (optional). Lines 211 and 231: the Rationale's own comparison for `0x123E+1` would tie phase 3 back to §03.01.**

Rationale §3.1.8 judges the anomaly "no worse than the principle under which the characters `a+++++b` are tokenized as `a ++ ++ + b` (an invalid expression)". That is §03.01's maximal munch, and the ledger already sends `x+++y` to §11.03. One clause at line 231 would join the two lessons.

**G4. The promise ledger has no entries for the forward references the rework added.**

Ledger lines 148–152 (promises.md) predate the rework. Missing entries:
- §03.05: `R_X86_64_PLT32` and the `-0x4` addend.
- §03.07: the dynamic loader filling the `puts` hole.

## 3. Imprecisions

**I1. Lines 441, 562 (and term, line 673): the relocation is described as "put in the address of `greet`".**

Two sentences earlier, line 562 correctly says the four bytes "should hold the distance from the end of the instruction to `greet`". `R_X86_64_PLT32` asks for a PC-relative distance, and that is what the `-0x4` adjusts for. Fix: "at offset 5, put in the distance to `greet`, worked out from its address". At line 441: "the linker was to write the distance to `greet`". The term definition can stay general.

**I2. Line 566: the hole for `puts` is filled by the dynamic loader "when the program starts".**

With lazy binding, the usual default unless the program is linked with `-z now`, the slot is filled at the first call. Fix: "…which the dynamic loader fills when the program starts or at the first call (§03.07)".

**I3. Line 167: "GCC is even stricter than the standard's wording here".**

GCC joins *more* lines than the standard says. That makes it more permissive, not stricter, and it widens the trap. Under the standard, `// …\ ` followed by a newline does not splice. Fix: "GCC departs from the standard's wording here, in the direction that widens the trap: it also treats…".

**I4. Line 440: "runs phases 1 to 7 (and the assembler)".**

This sets the assembler beside phase 7, while lines 410, 458, 507 and 584 put it inside. Fix: "runs phases 1 to 7, the assembler included, and stops". The myth box's "(phases 1 to 7)" for `cc1` at line 636 could likewise read "(phases 1 to 7, as far as assembly)".

**I5. Lines 410 and 507: the same point is made twice, almost word for word.**

- Line 410: "The standard has no separate phase for that second step, because it does not say what form phase 7's result takes".
- Line 507: "The standard has no separate phase for that, because it does not say what phase 7 translates *into*".

Self-check 11's answer repeats it a third time, which is fine there. Fix: keep line 410. At line 507, shorten to "Second, there is a program, `as`, that has no phase of its own: as the end of the phase-7 subsection explained, it finishes phase 7's work." Then continue with "Not every compiler…".

**I6. Line 105: two parentheses in a row (depth-review I10, not addressed).**

The line reads "…or with `-trigraphs`.) (This is an example of §02.05's rule…". Fix: make the second a sentence: "This is an example of §02.05's rule that the edition of the standard changes what a program means; here it changes the first phase of all."

**I7. Line 39: "So each phase is the settlement of an argument about *which rule wins*".**

This overgeneralizes. The Rationale's examples concern the early phases (comments, trigraphs, splices, directives); phases 7 and 8 settle no such argument. Fix: "So the order of the phases settles arguments about *which rule wins*…". This also prepares E5's fix.

**I8. Line 245: "in C's early decades, programs typed on ASCII terminals were compiled for IBM mainframes".**

This is an unsourced historical claim. Mainframe C compilers usually ran on the mainframe, with source converted to EBCDIC. The Rationale (§2.2.1) says only that "translation and execution environments may have different character sets". Fix: "…and C programs written on ASCII machines were carried to IBM mainframes, which used a different code, EBCDIC". Alternatively, list the claim in the Inference bullet. The general point (translate on one machine, run on another) is sound and well illustrated by the ATmega328P.

**I9. Lines 248–263: the EBCDIC block is a composite of two runs.**

- `ebc.c` comes from log 040.
- `nl.c` and `hx.c` come from log 041. Log 040's `nl.c`/`hx.c` contained a doubled backslash and returned 224, the EBCDIC backslash, so they were rightly rerun.
- `cat ebc.c nl.c hx.c` was never run as one command.

Every line is character-exact, so this is acceptable. If the house rule is "one block, one session", rerun the block as shown, or add "(from two runs)" to the Sources bullet.

**I10. Line 500: "the rules `*cpp_mcu: -D__AVR_ATmega328P__` and `*asm_arch: -mmcu=avr5`" are printed in code font as if they were literal text.**

In the file, each rule is a name line followed by a tab-indented value line (log 041). The rule `*cpp` itself is `%(cpp_mcu) %(cpp_rodata_in_ram) %(cpp_avrlibc)` (log 040). Fix: "…in that text file the rule `cpp_mcu` holds `-D__AVR_ATmega328P__`, and `asm_arch` holds `-mmcu=avr5`…".

**I11. Line 336 (pre-existing), with lines 457, 671 and §03.01 line 139: "compiler proper" names two different things.**

- The heading "Phase 7: the compiler proper" uses it for phase 7.
- Lines 457 and 671 call `cc1` "the compiler proper", and `cc1` also preprocesses.
- §03.01 says the preprocessor "runs before the compiler proper".

Fix: either retitle the heading "Phase 7: translation proper", or add at line 457 "(GCC's name for it; in the standard's terms it does far more than phase 7, since the preprocessor is built in)".

**I12. Line 173: "Ritchie calls such tricks operations "previously available only by accidents of implementation"".**

The quotation is accurate but the attribution is loose. Ritchie says the standard's preprocessor "provides operations, like token concatenation, previously available only by accidents of implementation". Fix: "Ritchie says that token concatenation had been "previously available only by accidents of implementation"."

**I13. Line 570: "SQLite is distributed as one C file containing its whole source".**

The amalgamation is the *library* in one C file, `sqlite3.c`, with its header `sqlite3.h`. The command-line shell is a separate file. Fix: "(SQLite's library is distributed as a single C file, which its authors call the "amalgamation")".
