Re-ran in /tmp/r0301 every command in the section with gcc-14 (14.2.0; note that plain `gcc` in this workspace is GCC 13, which rejects `-std=c23`, so every x86-64 check used `gcc-14`), clang 18.1.3, binutils (nm, objdump, objcopy, size, readelf), strace, bash, avr-gcc 7.3.0 + avr-libc 2.0.0, avr-objcopy, avr-size and simavr. History and documentation checks used the primary sources online: Kernighan's B tutorial, Kernighan's 1974 C tutorial, Ritchie's "The Development of the C Language", Langley's goto-fail post, man7.org exit(3), the N3096 table of contents and the ESP-IDF stdio page. Line numbers refer to 03.01.md as it stood at 10:47:44 (58,985 bytes, 712 lines). That version already contains the corrected ELF explanation at line 633 and "§11.03" at line 134.

## 1. Errors

**E1. Line 511, fact vs output, high.**
**Problem:** "Of that, 30 bytes are your `main`, and 14 your string". The `hello` executable does not hold a 14-byte string. GCC replaced `printf` with `puts` and dropped the `\n`, which is what line 479 itself says, so the binary holds `hello, world` plus a null character: 13 bytes.
**Evidence:** `objdump -s -j .rodata hello` gives `2000 01000200 68656c6c 6f2c2077 6f726c64` / `2010 00`, a 17-byte .rodata: 4 bytes of `_IO_stdin_used` and then 13 bytes of string. `hello.s` line 5 contains `.string "hello, world"`. The `lea ... # 2004` at line 471 points at that 13-byte string.
**Fix:** "Of that, 30 bytes are your `main`, and 13 your string (`hello, world` and its null character; the newline left with the change to `puts`)".

**E2. Line 237, fact (Linux/glibc), high.**
**Problem:** "if the output were going to a full disk or a closed pipe, `printf`'s negative result would be the only sign that the message was lost." This is false for both examples in this very program. Because stdout is buffered, `printf` returns 13 in both cases, and Experiment 03.01-5's own answer (line 694) shows this for a full disk. With a closed pipe, the write that eventually happens during `exit` raises SIGPIPE, which kills the process. `printf` never returns a negative value.
**Evidence:** `./retn > /dev/full` gives exit status 13, and strace shows `write(1, ...) = -1 ENOSPC` inside exit. `pipe.c` (sleep 1, then printf, then report n on stderr) run as `./pipe | true` prints `printf returned 13`, and `${PIPESTATUS[0]}` is 141 = 128 + 13 (SIGPIPE).
**Fix:** "...in a program that must not fail it is a decision, not a habit. And `printf`'s result alone is not enough: because the characters first go into a buffer, `printf` usually reports success even when the eventual write to a full disk fails (Experiment 03.01-5), and a write to a closed pipe kills the program with a signal instead. §34.03 returns to this."

**E3. Line 694, answer to Experiment 03.01-5, medium.**
**Problem:** "Detecting the failure needs `fflush(stdout)` and a check of its result, or a check of `ferror(stdout)`, before `main` returns." Checking `ferror(stdout)` without flushing first detects nothing, because no write has been attempted yet.
**Evidence:** printf, then `ferror`, then `fflush`, then `ferror`, run with output to /dev/full, prints `n=13 ferror-before=0 fflush=-1 ferror-after=1`.
**Fix:** "Detecting the failure needs `fflush(stdout)` and a check of its result (only after the flush does `ferror(stdout)` report the error), or a check of the result of `fclose(stdout)`, before `main` returns (§32.04)."

**E4. Line 690, answer to Experiment 03.01-3, medium.**
**Problem:** (a) The answer says "`-H` printed 30 lines", but the command prints 38: 30 header lines plus the 8-line list "Multiple include guards may be useful for:". (b) The explanation is backwards. With GCC, a header that has an include guard is not reopened on a second `#include`, so it does not appear twice in `-H` output. The names that repeat are exactly the headers that have no guard. `bits/wordsize.h` has no include guard at all, and its contents are processed again every time.
**Evidence:** `gcc-14 -std=c23 -H -fsyntax-only hello.c 2>&1 | wc -l` gives 38. wordsize.h (5 times), timesize.h (2) and long-double.h (2) repeat. `cat /usr/include/x86_64-linux-gnu/bits/wordsize.h` shows no `#ifndef` guard. `bits/types.h`, which has the guard `_BITS_TYPES_H`, is `#include`d by stdio.h:39, `__fpos_t.h:4` and `struct_FILE.h:33`, yet it is listed once. The GCC CPP manual, "Once-Only Headers", says GCC "does not bother to rescan the file at all" when the guard macro is defined.
**Fix:** "On the author's verification machine, `-H` printed 38 lines: 30 header names, then a list headed 'Multiple include guards may be useful for:'. A name appears again only when a header is included again *and is reopened*. A header protected by an include guard (§21.02) is not even reopened: GCC remembers the guard and skips the file, so `bits/types.h`, included three times, is listed once. The names that repeat, such as `bits/wordsize.h`, have no guard. They contain only definitions that may harmlessly be repeated, and are read in full each time."

**E5. Lines 609 and 633, arithmetic, medium.**
**Problem:** The text calls `send_one_character_through_the_universal_asynchronous_transmitter` "the 64-character" name in both places. It has 65 characters.
**Evidence:** `python3 -c "print(len('send_one_character_through_the_universal_asynchronous_transmitter'))"` prints 65.
**Fix:** "65-character" at lines 609 and 633.

**E6. Line 86 (also 60, 72, 578), standard / internal contradiction, medium.**
**Problem:** "the first thing it does with them, after removing the comments, is to cut the stream into tokens". Line 60 says the compiler "removes them before it reads anything else", line 72 says comments are "removed before the program is read", and line 578 says "comments disappear before the tokens are formed". These contradict line 390, which says correctly that tokens and comments are recognized "in a single left-to-right pass". They also contradict the standard. In translation phase 3, the source is decomposed into preprocessing tokens and white space, including comments, and each comment is then replaced by one space. Comments cannot be removed before tokenizing, because only tokenizing reveals that `/*` inside `"..."` is not a comment (Listing 03.01-7). Phases 1 and 2 also come before phase 3.
**Evidence:** N3096 §5.1.1.2, phase 3, and §6.4.9p1 ("Except within a character constant, a string literal, or a comment, the characters /* introduce a comment"). Line 390 of the draft.
**Fix:** Line 86: "...and the first thing it does with them is to cut the stream into **tokens**, recognizing comments in the same pass and replacing each by a space". Line 60: "...and the compiler replaces each by a space at the same moment it cuts the text into tokens, before any meaning is considered". Line 72: "a comment: replaced by a space when the text is cut into tokens". Line 578: "comments are replaced by spaces when the text is cut into tokens".

**E7. Lines 308–314, standard / overclaim, medium.**
**Problem:** "white space has exactly three jobs, and no others" and "Everywhere else, the compiler does not care." This is false as stated, and the reader will meet the exceptions within weeks. (a) A space inside a character constant (`' '`) is part of the constant, just as inside a string literal. (b) A space between a macro's name and `(` in `#define` changes a function-like macro into an object-like one. (c) The `#` operator turns white space between tokens into one space in the resulting string. (d) The line break ends a `//` comment. Also, Self-check 11's question "What three jobs..." builds on the overclaim.
**Evidence:** Feeding `#define f(x) [x]`, `#define g (x) [x]`, `f(1) g(1)` through `gcc-14 -E -P -` gives `[1] (x) [x](1)`. N3096 §6.10.4 (macro replacement; "#" operator), §6.4.4.4, §6.4.9.
**Fix:** "After that, in ordinary program text, white space has three jobs: [list as now, with item 2 reading 'Inside a string literal or character constant it is part of the value']. (The preprocessor gives it a few more, small ones, such as ending a `//` comment and distinguishing `#define f(x)` from `#define f (x)`; Chapter 22 shows them.)" Change line 314 to "Everywhere else in ordinary program text, the compiler does not care."

**E8. Line 58 (also 63 and 660), fact / internal contradiction, medium.**
**Problem:** "The language knows nothing about it except what line 3 tells it". Line 63 says "since the compiler does not know `printf`", and Self-check 2's answer repeats it. Both contradict lines 173, 179 and 479, where GCC's "built-in" knowledge of `printf` is shown and used. They also misstate the standard. The library is part of the C standard (N3096 clause 7), which specifies exactly what `printf` does in a hosted implementation. That specification is what allows GCC to know it and to substitute `puts`. The accurate statement is narrower: the core language has no output statement, and the compiler is not *required* to know `printf`'s declaration unless a header supplies it.
**Evidence:** Draft lines 173, 179, 479. N3096 §7.23.6.3 and §7.1.3 (reserved identifiers). §02.06 (line 118 there) also says that GCC "knows what `printf` does".
**Fix:** Line 58: "...compiled long before you wrote `hello.c`. The standard describes what it must do, but the rules of the language do not oblige the compiler to know it: a program must declare it before calling it, and line 3 does that, giving its name, the types of its parameters and the type of its result. (GCC in fact knows more, as you will see below; a program may not rely on that.)" Line 63: "The cost of this freedom is line 3: since the language does not oblige the compiler to know `printf`, the program must declare it." Make the same change in the Self-check 2 answer.

**E9. Line 186, fact / internal contradiction, low.**
**Problem:** "`main` is ... an identifier like any other as far as the compiler is concerned." It is not. The compiler issues `-Wmain` only for `main` (line 298), and it must make reaching the closing `}` of `main`, and of no other function, return 0 (§5.1.2.2.3, mentioned at line 303).
**Evidence:** voidmain.c warning (line 298). N3096 §5.1.2.2.3.
**Fix:** "`main` is the function's name. Grammatically it is an ordinary identifier; its special role comes from the rules for a hosted environment, where the standard says that the function called at program startup is named `main` (§5.1.2.2.1) and gives it a few privileges, such as returning 0 if it reaches its closing brace; §02.06 showed what calls it."

**E10. Line 131 (and 704), internal consistency, medium.**
**Problem:** "...the reader's newer C library gives a different number, as the verification notes at the end record." The notes at the end (line 704) record nothing of the kind. Unlike §02.06 (its line 544), this section has no "For the reader to confirm on GCC 15 or 16" list, although every x86-64 output block depends on the system.
**Evidence:** Lines 702–712.
**Fix:** Add to the Toolchains bullet: "**For the reader to confirm on Fedora 44 / GCC 16:** the token count (1,868 lines), the `-E` line count (557) and the line number of `printf`'s declaration (364), the length of `stdio.h` (985 lines) and the `-H` output, the `nm`/`objdump` addresses, the sizes 15,960 / 1,375 / 600 / 8, the strace output and the diagnostics' wording; and with Fedora's avr-gcc and avr-libc, the AVR sizes and the HEX comparison."

**E11. Lines 277 and 708, source citation, low.**
**Problem:** The text says "the `exit(3)` manual page states that the parent receives `status & 0377`". The current manual page, which is the one the reader's Fedora 44 man-pages 6.x will show, says "the least significant byte of status (i.e., status & 0xFF)". The reader will look for 0377 and not find it. An octal constant is also unexplained at this point in the book.
**Evidence:** man7.org exit(3), Linux man-pages 6.19.
**Fix:** "(the `exit(3)` manual page states that the parent receives 'the least significant byte of status', that is, the value modulo 256)". At line 708: "the parent receives the least significant byte of status (written `status & 0xFF`; older editions `status & 0377`)".

**E12. Lines 479 and 680, fact, medium.**
**Problem:** "A `printf` whose format contains no `%` conversion and ends in a newline does exactly what `puts` does". It does not do *exactly* the same thing, because the results differ: `printf` returns the number of characters, `puts` only "a nonnegative value". GCC therefore substitutes `puts` only when the result is discarded. The section's own count.c shows this: there `printf` is kept.
**Evidence:** `nm count` gives `U printf@GLIBC_2.2.5` and no `puts`. objdump of count's main shows three `call printf@plt`. N3096 §7.23.7.9 (`puts` returns a nonnegative value).
**Fix:** Line 479: "...A `printf` whose format contains no `%` conversion and ends in a newline, and whose result is thrown away, has the same effect as `puts` of the string without its newline..." and add "(In count.c, where the result is kept, GCC leaves `printf` alone: `puts` would not return 13.)" At line 680 add the same condition, "and whose result is not used".

## 2. Imprecisions and risks of misunderstanding

**I1. Lines 9, 54, 443, 514 vs 152, internal consistency, medium.**
**Problem:** The section calls the program "seven lines" four times, but line 152 says "Your 8 lines became 557". Line 9's "Almost every course in C begins with the same seven lines" is also untrue: two of the seven non-blank lines are this book's own comments. A course's program is five non-blank lines.
**Evidence:** `wc -l hello.c` gives 8. The listing has 7 non-blank lines, 2 of them comments.
**Fix:** Line 9: "Almost every course in C begins with the same five lines". Elsewhere write "eight lines" (or "seven non-blank lines") consistently, or say "a few lines" at 443 and 514.

**I2. Line 49, history, medium.**
**Problem:** (a) The B tutorial's program also calls `putchar('!*n')`, so it printed `hello, world!` and a newline. A reader who checks the source (it is cited at line 706) will find a fourth `putchar` and an exclamation mark that the text omits. (b) Wikipedia's "Hello, World!" article shows the 1974 version *with* `\n`. The primary source (Kernighan, "Programming in C: A Tutorial", §2) has none, so the book is right, but say so to forestall the reader's doubt. (c) "nearly every introduction to a programming language since then has begun with an equivalent" is an unsourced generalization. (d) "(§02.01 built a model of that machine)" could not be checked, because §02.01 is not in the files provided. Confirm it, because §02.01's TOC bullets mention only word-addressed machines in general.
**Evidence:** btut.html (Nokia Bell Labs copy): `putchar(a); putchar(b); putchar(c); putchar('!*n');` and "A 'character' is one to four ascii characters... stored in a single machine word". The lysator copy of bwk-tutor: `printf("hello, world");`.
**Fix:** "...and the program printed them one after another with `putchar`, followed by `'!*n'`, B's way of writing an exclamation mark and a newline." Add: "(Some modern retellings print the 1974 version with `\n`; the tutorial itself has none.)" Change "nearly every" to "a great many".

**I3. Line 179, standard history, medium.**
**Problem:** "In ... the first standard of 1989, calling an undeclared function was allowed ... That is why the 1978 'hello, world' needed no `#include`." This is true for ordinary functions, but in C89 calling a function with a variable argument list such as `printf` without a prototype in scope is undefined behavior. The 1978 program was therefore not strictly correct C89, and this is why the second edition of K&R (1988) added `#include <stdio.h>`. A strict reader will find this rule and think the book got it wrong.
**Evidence:** C89 §3.3.2.2 / C99 §6.5.2.2p6: a call without a prototype to a function whose definition has a prototype ending in `, ...` is undefined.
**Fix:** Add after "needed no `#include`": "(Strictly, from 1989 on, `printf` was an exception: calling a function with a variable number of arguments without a declaration was undefined behavior, which is why the 1988 second edition of the book added `#include <stdio.h>`.)"

**I4. Line 190, standard, medium.**
**Problem:** "In C89 to C17, empty parentheses in a declaration meant 'parameters unspecified'". For a *definition*, which is the case here (`int main() { ... }`), C89–C17 said that an empty list "specifies that the function has no parameters". What was missing was a *prototype*, so calls were not checked. Since a definition is also a declaration, the sentence is wrong for exactly the case under discussion.
**Evidence:** C17 §6.7.6.3p14: "An empty list in a function declarator that is part of a definition of that function specifies that the function has no parameters. The empty list in a function declarator that is not part of a definition of that function specifies that no information about the number or types of the parameters is supplied."
**Fix:** "In C89 to C17, empty parentheses in a declaration that was not a definition meant 'parameters unspecified'; in a definition such as `int main() { ... }` they meant 'no parameters', but still gave the compiler no prototype, so the arguments of a call were not checked against it."

**I5. Lines 134, 527, 705, standard terminology, low.**
**Problem:** The longest-sequence rule in §6.4 is stated for *preprocessing tokens*, not tokens. The five kinds listed at 86–92 are tokens, which preprocessing tokens become in phase 7. The book cites §6.4 for both without distinguishing them, and a reader checking §6.4p4 will find the other word. One visible consequence: `0x1E+1` is a single preprocessing number, and so an error.
**Fix:** Line 134: "...the next *preprocessing token* is the longest sequence of characters that could form one (§6.4; §03.02 explains how preprocessing tokens become the tokens above; the rule is often called **maximal munch**)."

**I6. Line 119, unsourced claim, low.**
**Problem:** "...which Clang keeps for its error messages and for the preprocessor". The error-message use is unsourced, and the flags' known uses are all in preprocessing: recognizing `#` at the start of a line, spacing in `-E` output, and the `#` operator. "survives only as the notes" is fine.
**Fix:** "which Clang keeps for the preprocessor (for example, to recognize a `#` that begins a directive, and to space its `-E` output), not for the meaning of the program."

**I7. Line 259, line reference, low.**
**Problem:** "Line 6: with no word typed, `argc` is 1, and the program reports failure with ... `EXIT_FAILURE`". The `return EXIT_FAILURE;` is on line 7.
**Fix:** "Lines 6–7: ...".

**I8. Lines 314–318, internal accuracy, low.**
**Problem:** The text says "every optional space and line break removed", but the space in `#include <stdio.h>` is optional.
**Evidence:** `#include<stdio.h>` with the same second line compiles, and diff against `hello.s` shows only the `.file` line.
**Fix:** Write `#include<stdio.h>` in Listing 03.01-5 (and in squashed.c), or say "every optional space after the directive".

**I9. Line 370 (and 706), history, low.**
**Problem:** "`//` ... is the form of BCPL ... C left it out". B had already dropped it, and C inherited B's `/* */`. The sources bullet calls the origin "widely documented" where two primary sources say it directly.
**Evidence:** Ritchie, "The Development of the C Language": "B uses /**/ to enclose comments, where BCPL uses //, to ignore text up to the end of the line" and "(C++ has resurrected the BCPL comment convention.)" Kernighan's B tutorial: comments are "anything enclosed in /*...*/, just as in PL/I."

**I10. Line 63, history, low.**
**Problem:** "...a print statement, as BASIC, Pascal and Fortran did". Pascal's `write`/`writeln` are standard procedures, with built-in special treatment, not statements.
**Fix:** "...as BASIC and Fortran have print statements and Pascal built-in `write` procedures".

**I11. Line 493 and Figure 03.01-1, risk of misunderstanding, medium.**
**Problem:** (a) "...when it is a file or a pipe, only when the buffer fills or the program exits": omits an explicit `fflush`. (b) The figure draws the `write` system call *inside* the `puts` call (call, copy, write, kernel, return), which is true only when stdout is a terminal. Only the last box carries "(when stdout is one)". With output to a file, which is the case in Experiment 03.01-5, the write happens inside `exit`, in the "After main" column.
**Fix:** (a) "...only when the buffer fills, when the program calls `fflush`, or when it exits". (b) Change the second library box to "if stdout is a terminal: the buffer is written at once with one system call, write(1, ..., 13); otherwise later, inside exit".

**I12. Line 511, true but misleading, medium.**
**Problem:** "The rest of the file is structure: startup code, the information the dynamic loader needs..., and headers". Most of the 15,960 bytes are padding: zero bytes that place the code, read-only data and writable data at 4 KB page boundaries in the file. The reader will open the file in a hex viewer and find mostly zeros.
**Evidence:** `readelf -S` shows sections at file offsets 0x0610 (end ≈ 0x628) → 0x1000, 0x1175 → 0x2000, and 0x20f4 → 0x2db8. Runs of 64 or more zero bytes total 9,684 of the 15,960 bytes. Allocated sections total about 2 KB, and .symtab/.strtab/.shstrtab about 1.3 KB.
**Fix:** "The rest of the file is structure and padding: about 10 KB of zero bytes that place the code and data on 4 KB page boundaries so that the kernel can map them directly (§27.02), plus the startup code, the information the dynamic loader needs to find `puts`, a table of names, and headers describing how to load the program (§03.05 and §03.06 take it apart)."
