# Independent review of §03.06 "Linking: Completing the Program"

Reviewer's basis: `03.06.md` (912 lines), `out.pdf` (36 pages), logs 075–084, `hello.map`, `avr_hello.map`, `prev-03.05.md`. Where I ran commands myself, they ran in my Ubuntu 24.04 workspace (`gcc` = 13.3.0, `gcc-14` = 14.2.0, binutils 2.42, glibc 2.39). Fedora facts come only from the logs. Line numbers refer to `03.06.md`.

## Summary

This is a strong section. It covers the whole link of `hello` with real data, and almost every number checks out against the logs: the 40-argument link command, the map arithmetic for `main` (0x401090 + 0xa6 = 0x401136), the PLT32 calculation (−0x114 → `ec fe ff ff`), `.got.plt` = 0x401036, the `-y` traces, Table 03.06-3, the static/dynamic measurements (267×, 677,012/1,068, 1,987/29 lines), the AVR layout sum (0xce = 206), and the AVR `ldi`/`cpi` values. I checked the H. J. Lu quote, its date (October 7, 2015, x86-64-abi list), and the `man ld`/`man gcc`/`man ldd` quotes. They are word for word. The Ubuntu claims also reproduce on my machine: the `-pie`, `-z now -z relro` and `--as-needed` options, the `%{!fsanitize=*:--as-needed}` spec, the failure of `gcc -lm cube.c`, and `crt1.o` against `Scrt1.o` differing only by `_dl_relocate_static_pie`.

The problems fall into four groups:

1. **One wrong offset.** The `R_X86_64_32` hole is at offset 5, not 6. §03.05 itself says 5.
2. **`crtbegin.o`/`crtend.o` described from the generic `crtstuff.c` source, not from the built files.** On this toolchain `frame_dummy` does not register exception tables, and `__do_global_dtors_aux` walks no destructor list. Both only (de)register TM clones.
3. **Wrong labels in the figure and several imprecise statements about who does what.** The figure puts `_start` at 0x401090 and credits linker-made `.eh_frame` bytes to `crt1.o`. The text says "loader" where the kernel maps the program, misdescribes `GNU_STACK`, misdescribes the hand-built command, and misdescribes `hello_byhand`.
4. **Experiments, consistency and layout.** Two experiments have wrong premises or wrong methods (03.06-3 and 03.06-6). One cross-reference implies §03.05 used only invented addresses, but it did not. The PDF has real breakage: Listing 03.06-1 inside the "Under the hood" box is mangled, and every double-backtick code span renders wrongly.

The most valuable additions for depth would be: what `GROUP`, `libc_nonshared.a` and `DT_SONAME` really do; why `--as-needed` turns into an *undefined reference* and not just a missing `NEEDED`; the RW segment's address 0x402df8 and RELRO (the only address in the section still unexplained); and the GLIBC_2.34 version tag tied to the zeroed `rcx`/`r8` in `_start`.

Counts: **17 errors, 14 improvements, 15 nits.**

## Errors

### E1. Wrong offset of the `R_X86_64_32` hole
- **Text (line 496):** "1. **`R_X86_64_32 .rodata + 0`, at offset 6 of `main`.**"
- **Wrong:** `main` starts at 0x401136. `55` (1 byte) and `48 89 e5` (3 bytes) come first, so the `bf` opcode is at offset 4 and its 4-byte immediate starts at offset **5**. §03.05 says so too (prev-03.05.md line 457: `000000000005 ... R_X86_64_32 ... .rodata + 0`; line 486: "at offset 5 of `.text`, the four bytes after `bf`"). The PLT32 hole at 0xa is consistent with 5, not 6: 5 + 4 = 9 = the `e8`.
- **Correction:** "at offset 5 of `main` (the four bytes after `bf`, at 0x40113b)".

### E2. `crtbegin.o`/`crtend.o` described from the generic source, not from this build
- **Text (line 171, Table 03.06-2):** "GCC's start-up and exit support: exception tables, transactional-memory clones, old-style destructors". **Line 238:** "registering the exception and unwinding tables on systems that require it (`frame_dummy`), cloned functions for transactional memory (the `tm` in `register_tm_clones`), and running an older form of the list of destructors (`__do_global_dtors_aux`). `crtend.o` ends the tables that `crtbegin.o` begins; its four zero bytes in `.eh_frame` mark the end of the unwinding tables." Self-check 1 (line 862) repeats the claim.
- **Wrong:**
  - On this toolchain `frame_dummy` is 6 bytes. Log 075's `nm` puts it at 0xa0 in a `.text` of 0xa6 bytes, so it is 0xa0–0xa6. On my Ubuntu GCC 14 `crtbegin.o`, which has the same offsets (0x30/0x70/0xa0) and the same 166-byte `.text`, it is exactly `endbr64; jmp 30 <register_tm_clones>`.
  - `__do_global_dtors_aux` (0x70–0x90) is: `cmpb $0,completed; jne; push rbp; call deregister_tm_clones; movb $1,completed; pop; ret`. It walks no `.dtors` list and registers no frame info.
  - Those features (`__register_frame_info`, the `.dtors` walk) are compiled out on x86-64 GNU/Linux, which uses `PT_GNU_EH_FRAME` and `.init_array`/`.fini_array`.
  - Also, `crtbegin.o` has **no `.eh_frame` section at all** (log 075 `size -A crtbegin.o`: no `.eh_frame`). So `crtend.o` does not end an `.eh_frame` table "that `crtbegin.o` begins". Its 4 zero bytes terminate the `.eh_frame` contributed by all inputs (crt1.o, the linker, hello.o). Only the TM-clone table (`__TMC_LIST__` … `__TMC_END__`) is truly begun by `crtbegin.o` and ended by `crtend.o`.
- **Evidence:** log 075 (`nm`/`size -A` of `crtbegin.o`, `crtend.o`); my `objdump -dr /usr/lib/gcc/x86_64-linux-gnu/14/crtbegin.o`.
- **Correction:** State the general purpose (on some targets `crtbegin.o` registers unwind tables and runs `.ctors`/`.dtors`), then state what this build actually does. On x86-64 Linux, `frame_dummy` only jumps to `register_tm_clones`, and `__do_global_dtors_aux` only calls `deregister_tm_clones` once, guarded by the byte `completed`. Both do nothing unless `libitm` is loaded, because `_ITM_registerTMCloneTable` is a weak undefined symbol (`w` in `nm crtbegin.o`). Fix the Table 03.06-2 "Purpose" cell and Self-check 1 the same way. Suggest the reader run `objdump -d --disassemble=frame_dummy hello`.

### E3. Figure 03.06-1 has two wrong labels
- **(a)** The `.text` row's note reads "_start; at 0x401090; main at 0x401136". `_start` is at **0x401040** (`nm hello`: `0000000000401040 T _start`; `readelf -l`: entry point 0x401040). 0x401090 is the start of `crtbegin.o`'s `.text` (`deregister_tm_clones`). The stray ";" after `_start` also suggests a template glitch. **Correction:** "_start at 0x401040; main at 0x401136".
- **(b)** The `.eh_frame_hdr .eh_frame` row shows "crt1.o (0x80)". `hello.map` has two pieces attributed to crt1.o: `0x4004f8 0x58 crt1.o` with "0x70 (size before relaxing)", and `0x400550 0x28 crt1.o` with "0x40 (size before relaxing)". `crt1.o`'s whole `.eh_frame` is 112 = 0x70 bytes (log 075 `size -A`), so it is all in the first piece. The second piece is the unwind information the linker generates for `.plt`, filed under the first input file in the same way as the `.plt` line, which the text itself explains (line 407). **Correction:** "crt1.o (0x58) | linker (0x28, for .plt) | hello.o (0x20) | crtend.o (4)". One sentence in the text could note that the linker also writes unwind data for the PLT.

### E4. The `.rodata` arithmetic does not close
- **Text (line 415):** "`.rodata` begins at 0x4004a0, `crt1.o` contributes 4 bytes (`_IO_stdin_used`), `crtbegin.o` contributes 8 (`__dso_handle`), and `hello.o`'s 13 bytes begin at 0x4004b0."

### E5. "Loader" used where the kernel maps the program
- **Text:**
  - Line 97, Table 03.06-1: "`-dynamic-linker /lib64/ld-linux-x86-64.so.2` | the program that will load this program and its libraries"
  - Line 175: "The kernel does not call `main`; it starts a program at a single address, the **entry point**"
  - Line 465: "The three `LOAD` lines are what the loader acts on"
  - Line 771, Terms: "Entry point … the address at which the kernel starts a program"
- **Wrong:** For a dynamically linked program started by `execve`, the **kernel** maps `hello`'s `PT_LOAD` segments, and also maps the interpreter named by `PT_INTERP`. It then starts the *interpreter* at the interpreter's own entry point. `ld-linux` loads the shared libraries, applies the dynamic relocations, runs the libraries' initializers, and then jumps to `hello`'s `e_entry`. `ld-linux` loads the program itself only when it is run as a command (`ld.so ./hello`). The section's own "Under the hood" box (line 270) says correctly that "the loader, `ld-linux`, prepares the C library before it jumps to `_start`", which contradicts line 175 and the Terms entry.
- **Correction:**
  - Table row: "the program interpreter: the kernel maps `hello` and this program; it loads the shared libraries, fills the GOT, then jumps to `_start`".
  - Line 175: "…the entry point… For a statically linked program the kernel jumps there directly; for `hello`, the kernel first runs the interpreter, which jumps there when the libraries are ready (§03.07)."
  - Line 465: "what the kernel (and, for libraries, the loader) acts on".
  - Terms: adjust in the same way.

### E6. `GNU_STACK` does not "point into" anything

## Improvements

**I1. Explain `GROUP`, and the real reason `libc_nonshared.a` exists (lines 321, 872).**
- The section quotes the script's `GROUP ( … )` but never says what `GROUP` means. It is the script form of `--start-group … --end-group`: the named files are searched repeatedly. That is why log 076's `--trace` lists `libc_nonshared.a` and `ld-linux-x86-64.so.2` **twice** — the group was rescanned. That output is already in the logs and would make the AVR `--start-group` paragraph a second meeting, not a first.
- Say why those four members must be static. `atexit`/`at_quick_exit`/`pthread_atfork` must register the *calling module's* `__dso_handle` (defined in `crtbegin.o`, the 8 bytes in `.rodata`!), so each executable or library needs its own copy. `__stack_chk_fail_local` is a hidden-visibility stub that PIC code can call without a PLT.
- That is a first-principles reason, and it connects to `__dso_handle`, which the section already shows. The script's comment ("only in the static library") states the fact, not the reason.

**I2. Replace part of the "versioned name" inference with the fact behind it: `DT_SONAME` (line 321).**
- `NEEDED [libc.so.6]` is not derived from the file name the linker opened. The linker copies the library's `DT_SONAME` (`readelf -d /lib64/libc.so.6 | grep SONAME` → `libc.so.6`).
- That is the mechanism by which the build-time name `libc.so` and the run-time name `libc.so.6` are decoupled, and it is verifiable. (Run it on the reader's machine and log it.) The inference bullet can then shrink to the *why* (interface versioning).

**I3. Explain why `--as-needed` produces *undefined reference*, not merely a missing `NEEDED` (lines 584–588).**
- The quoted man text speaks only about emitting `DT_NEEDED`. A first-principles reader would expect `cube3` to *link* and then fail at run time.
- What actually happens: when GNU ld finds an as-needed library unneeded at that point, it removes the symbols it had just added from its global table. The later reference from `cube.o` then has nothing to bind to.
- The `-y` evidence in E13 (definition printed, link still fails) shows this directly.

**I4. Account for the last unexplained address: the RW segment at 0x402df8, and RELRO (lines 417, 445–465).**
- The section promises to account for "every address the linker chose" but never says why writable data starts at 0x402df8 rather than 0x402000.
- The reason is visible in the output already shown: `GNU_RELRO` covers 0x402df8 + 0x208 = **0x403000**, a page boundary. The linker placed the read-only-after-relocation data (`.init_array`, `.fini_array`, `.dynamic`, `.got`) so that it *ends* on a page. The loader can then `mprotect` that page to read-only, while `.got.plt`'s `puts` slot at exactly 0x403000 stays writable for lazy binding.
- Mention also that file offset ≡ address (mod 0x1000) (0x1df8 ↔ 0x402df8), which is why the file has a gap: `separate-code` costs file size (bytes 0x600–0xfff are padding). That explains much of the 12,624 bytes for 1,068 bytes of "text".

**I5. Tie the GLIBC_2.34 version to the `_start` code the section shows (lines 198–202, 525).**
- The box says versioning lets a function "change … while programs linked against the old version keep receiving the old behavior", but both versions here have the *same address* (log 076). Without more, the reader is left puzzled.
- The new version tag marks a change in `_start`'s calling contract. Since glibc 2.34, `_start` passes NULL for the old `init`/`fini` arguments: that is the `xor %ecx,%ecx` and `xor %r8d,%r8d` in the listing. A binary built this way must not run on an older glibc that would call `init`.
- That is a concrete, checkable instance of what versioning protects. (Verify and cite the glibc 2.34 NEWS/commit before stating it as fact.)

**I6. Contrast the two `GOTPCRELX` relocations in `crt1.o` (lines 214, 499).**
- `crt1.o` has `R_X86_64_REX_GOTPCRELX main-0x4`, which was relaxed, and `R_X86_64_GOTPCRELX __libc_start_main-0x4` (log 075), which was **not**: it stayed `call *0x1f73(%rip)` through the GOT.
- Putting the two side by side states the rule from the evidence: relaxation is possible only when the symbol is defined in the output file.

**I7. Explain PLT0 and the reserved GOT entries (lines 509–522).**
- The logs contain `puts@plt-0x10` at 0x401020 (`push 0x1fca(%rip) # 402ff0 <_GLOBAL_OFFSET_TABLE_+0x8>; jmp *0x1fcc(%rip) # 402ff8`).
- They also contain the `.got.plt` dump, whose first slot holds 0x402e08 = `_DYNAMIC`.
- The text treats `jmp 0x401020` as a black box ("code that asks the loader"). Three sentences would remove it: GOT[0] holds the address of `.dynamic`; GOT[1] and GOT[2] are filled by the loader with its link-map pointer and the address of its resolver; and the `push $0x0` is the index the resolver uses into `.rela.plt`.

**I8. Turn Self-check 10's prediction into a measurement.**
- Ubuntu's PIE `hello` (gcc-14, my workspace) has `1078: 48 8d 3d ca 00 00 00  lea 0xca(%rip),%rdi  # 1149 <main>`, relaxed from the same `R_X86_64_REX_GOTPCRELX main-0x4` in `Scrt1.o`.
