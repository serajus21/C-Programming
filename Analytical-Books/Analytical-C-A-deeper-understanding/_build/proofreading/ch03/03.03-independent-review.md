# Independent review of §03.03 "Preprocessing: Text Before Language"

Reviewed: `03.03.md` (976 lines), `03.03-rendered.pdf` (36 pages), `fig_header_library.png`, the program sources, and logs 044–055. Benchmarks: `03.01.md` and `03.02.md`.

How it was checked:
- Every output block, number, line number and command was compared with the Fedora logs.
- Quotations were checked with WebFetch against these sources:
  - Ritchie, chist.html (every quoted string confirmed character for character, including the doubled "the the");
  - the GCC cpp manual, "Preprocessor Output" and "Search Path";
  - GCC "Common Function Attributes" (gnu_inline);
  - the GCC 4.8 porting notes;
  - C23 N3096 §§6.10.2, 6.10.4 p9/p10, 6.10.4.4 p2, 6.10.5, 6.10.7 p1, 6.10.9.1, 7.1.2 (including footnote 230), 7.1.4, 7.23.1 p4, 7.23.2 p9.
- Reasoning was tested in my own shell (Ubuntu 24.04, gcc 13.3 and gcc-14 14.2, avr-gcc 7.3, glibc 2.39). The Fedora logs remain the authority. Where a correction rests on my shell rather than on a Fedora log, I say so and give the command to confirm it on Fedora.

## Verdict

**Revise before approval. The structure is sound, but several statements of fact are wrong.**

The section is strong:
- the structure follows the TOC bullets;
- the experiments are well chosen;
- almost every output block matches the logs;
- every quotation I could reach is word for word;
- the clause numbers are right;
- the depth is comparable to 03.01 and 03.02.

However, I found 19 errors. They include:
- one claim that contradicts §03.02 (the preprocessor "completely" finishes before the compiler proper in GCC);
- one number that contradicts §03.01 (`-H` "printed 31 lines");
- three output blocks that do not match the logs exactly (one wrong `head` count, one `sed` range, one silently truncated diagnostic);
- one block with no log behind it;
- several overstated or wrong claims: flag 4, "408 built-in macros", "five opening braces", "2,198 functions", the implicit-int register story, "-P removed only markers and blank lines", "986 of them C text", "twice a second", "above the comment", the `nopragma.c` line number, and the Experiment 03.03-4 answer.

None of these requires restructuring. Most need one sentence changed.

All quotations verified exactly. Notes:
- The Ritchie history box quotes are exact. The word "usefulness" sits outside the quotation marks; the original says "utility" (nit N1).
- §7.1.2's "Each library function is declared in a header, whose contents are made available by the #include preprocessing directive" is exact in N3096. In C23 the C11 words "with a type that includes a prototype" are gone, and footnote marker 230 sits after "header,".

Arithmetic verified:
- 111 + 238 + 224 = 573, and 601 − 573 = 28.
- `_delay_ms(500)`: 3 + (1,599,999 × 5 − 1) + 2 + 1 = 8,000,000 cycles. I assembled `rjmp .` with avr-as: it encodes as `00 c0`, which `avr-objdump` shows as `rjmp .+0`, a 2-cycle jump to the next instruction. So the cycle count is right.

## ERRORS (must fix)

### E1. The preprocessor does not finish "completely" before GCC's compiler proper starts (line 37). This contradicts §03.02.

Text:
> "Second, the preprocessor does its work completely before the compiler proper begins. In GCC both are done inside one program, `cc1` (§03.02), but the boundary between them is still exactly where the standard puts it, at the end of phase 4, and `gcc -E` lets you stand on it."

Why it is wrong:
- Inside GCC's integrated `cc1`, the C parser pulls tokens from the preprocessor (cpplib) one at a time. GCC's lexer interface (`c-family/c-lex.cc`) calls `cpp_get_token`. So preprocessing and parsing are interleaved, not sequential.
- §03.02 line 56 says the opposite of this sentence: implementations behave "as if" the phases were separate, "even though in practice many of them are usually folded together. The phases are a specification of meaning, not a description of GCC's internals."
- §03.02 line 490 also shows that `-E` is a separate mode (`cc1 -E`).

Replace with:
> "Second, the preprocessor's work is *logically* complete before the compiler proper begins: the standard requires the result to be as if phase 4 had finished first (§03.02). Inside GCC's `cc1` the two are interleaved (the parser asks the preprocessor for one token at a time), but nothing the parser does can change what the preprocessor produces, so the boundary is exactly where the standard puts it, at the end of phase 4, and `gcc -E` (which runs `cc1 -E`, §03.02) lets you stand on it."

### E11. The implicit-`int` story gets the registers wrong (line 509).

Text:
> "(Had the compiler guessed, as compilers before 1999 did, it would have guessed a function returning `int`, and passed and received the `double` in the wrong registers: §18.04 shows the damage.)"

- The argument is *not* passed in the wrong register. A call without a prototype applies the default argument promotions; a `double` stays a `double` and goes in `xmm0`, with `al` = 1.
- Only the result is taken from the wrong register: `eax` instead of `xmm0`.
- In my shell, gcc 13 with `-std=gnu89 -fno-builtin noheader.c -lm` produces:

- Without `-fno-builtin`, GCC uses its built-in knowledge of `sqrt` even when guessing, and prints `1.414214`. That ties in nicely with the "third source of knowledge" subsection.

Replace with:
> "(Had the compiler guessed, as compilers before 1999 did, it would have assumed a function returning `int`: the `double` argument would still travel correctly in `xmm0`, but the result would be read from `eax` instead of `xmm0`, an unrelated value: §18.04 shows the damage.)"

## IMPROVEMENTS (should fix)

### I1. Pragma definition (line 704 and Terms, line 799)

Text:
> "A **pragma** is a directive addressed not to the preprocessor but to the compiler proper"

and in Terms:
> "a directive addressed to the compiler proper, passed through by the preprocessor"

Why it should change:
- This is overstated, and the section's own GCC quotation contradicts it: "#pragma (only if the preprocessor does not handle the pragma itself)".
- GCC's preprocessor carries out several pragmas itself: `#pragma once`, which §21.02 will use; `#pragma GCC poison`; `#pragma GCC system_header`; `#pragma push_macro`/`pop_macro`.

Suggested text:
> "A **pragma** is a directive whose meaning the implementation defines (§6.10.7). A few are meant for the preprocessor itself (`#pragma once`, §21.02); this one is for the compiler proper, so the preprocessor passes it on."

Also mention that the manual's list includes `#ident` (always kept) and `#define` (kept with `-dD`), which links to Experiment 03.03-4.

### I2. "A declaration carries exactly that information, and nothing more" (hood box, line 212)

Why it should change:
- This is overstated, and the logs supply a better lesson.
- The section's own output (line 149) shows `perror` declared with `__attribute__ ((__cold__))`.
- Log 044 shows that under `-std=c23`, `scanf` is declared as `extern int scanf (…) __asm__ ("" "__isoc23_scanf")`. The header decides which library symbol the call will be linked to.
- This is the sharpest possible illustration of the header/library link: the `-std=` option changes the header's text, which changes the name the linker looks for.

Suggested text:
> "A declaration carries that information (and sometimes a little more: attributes, and occasionally the name under which the library's definition is to be found, as with `scanf` at line 440)."

### I3. Hood box: name the calling convention

Why it should change:
- "On x86-64, the convention…" is true for the System V AMD64 ABI used by Linux. Windows x64 passes the first integer argument in `rcx` and does not use `al`.
- `al` is defined as an upper bound on the number of vector registers used. GCC sets it exactly.

Suggested text:
> "On x86-64 Linux, the System V calling convention (§19.02)…"

### I4. `.LC0` is asserted to hold √2 without evidence (line 541)

Text:
> "The result is stored as a constant (the read-only label `.LC0`)"

Why it should change:
- This is an inference from a label name.
- In my shell, `gcc -O2 -S root.c` shows `.LC0: .long 1719614413 / .long 1073127582` in `.rodata.cst8`. That is 0x3FF6A09E667F3BCD, the IEEE 754 bit pattern of √2 (§07.03).
- The format string is a separate label, `.LC1`, in `.rodata.str1.1`.

Fix: show those two `-S` lines from a Fedora run. Then the claim is demonstrated, not inferred, and the reader sees the folded constant.

### I5. `nm` values are addresses, not file offsets (Table 03.03-2 line 366, line 384, line 476, and the figure)

Text:
> "at offset 0xb0c50", "at the offset shown", "at offset 0x8da70", and the figure's "puts at offset 0xd9a60"

Why it should change: `nm` prints the symbol's value, which in a shared object is an address relative to where the library is loaded. It is not a position in the file, even when the two happen to coincide.

Fix: say "at address 0xb0c50 (relative to the library's load address, §03.07)".

### I6. Explain `__builtin_avr_delay_cycles` (Hands-on A)

Why it should change:
- Hands-on A shows `extern void __builtin_avr_delay_cycles(uint32_t);` (line 884) and then the counted loop, but never says where the loop comes from.
- The header supplies only the arithmetic. The compiler expands the built-in `__builtin_avr_delay_cycles(8000000)` into the exact `ldi/subi/sbci/brne/rjmp ./nop` sequence.
- This is a third kind of built-in: one that is not a library function at all. That also means the Terms definition (line 800, "a library function whose meaning the compiler knows") is too narrow.
- For a first-principles reader, this is the most important missing step in the Hands-on.

### I8. A better example for the "In orbit" box (line 784)

Text:
> "as avr-libc's `util/delay.h` does with a `#warning` when optimization is off"

Why it should change:

### I9. Repeatable "type definitions" and include guards (line 583)

Text:
> "what may be repeated (declarations, type definitions, macros) goes into headers"

Why it should change:
- In one translation unit, repeating a structure definition was an error before C23. C23 allows only an identical redefinition.
- Repeating a `typedef` is allowed only since C11, and only with the same type.
- A macro may be redefined only identically (§6.10.4 p2).
- As written, the sentence implies a header could be included any number of times without include guards. That sits badly with the myth box's mention of include guards (line 96) and with §21.02.

Suggested text:
> "what every file needs its own copy of (declarations, type definitions, macros)…"

Add one sentence: "repeating some of these *within* one file is restricted, which is why headers carry include guards (§21.02)".

### I10. "gnu_inline guarantees that they never produce a definition" (line 585), and line 250

Why it should change:
- In C terms they *are* definitions: inline definitions. What `gnu_inline` with `extern` guarantees is that no standalone (external) definition, and so no symbol, is ever emitted.
- Line 250, "a program that is not inlined uses it", should be "a call that is not inlined uses it".

Suggested text:
> "never produce an external definition (a symbol that the linker could see twice)"
