## 1. Errors

**E1. Line 579, factual (GCC behavior), medium.**
**Problem:** The answer to Experiment 03.02-4 says that `gcc -###` "prints the commands, with each argument in quotation marks". That is how Clang behaves. GCC does not quote every argument.
**Evidence:** The GCC manual, Overall Options, on `-###` says: "arguments are quoted unless they contain only alphanumeric characters or `./-_`". Log 035 shows the GCC 16 `-###` line ` /usr/libexec/gcc/x86_64-redhat-linux/16/collect2 -plugin /usr/libexec/.../liblto_plugin.so "-plugin-opt=..."`, where only some arguments are quoted. Log 034 shows that `gcc -### ... | grep -E '^ "'` matched nothing (exit 1), because the program name is not quoted. gcc-14 here gives ` .../cc1 -quiet -imultiarch x86_64-linux-gnu hello.c ... "-mtune=generic" ... -Wall -Wextra -Wpedantic "-std=c23"`.
**Fix:** "`-###` prints the commands but does not run them (GCC puts quotation marks only around arguments that contain characters other than letters, digits and `./-_`), so the lines that `cc1` itself prints while running (its version and the header search list) are absent."

**E2. Line 591, verification claim, medium.**
**Problem:** The text says the cross-check with GCC 14.2.0 on Ubuntu 24.04 gave "the same results apart from paths and the linker's name". My re-run of the same commands on that system shows several substantive differences:
- The by-hand `cc1` command fails (see E3).
- `hello` is a "pie executable" linked with `Scrt1.o`, `crtbeginS.o` and `crtendS.o`, not `crt1.o`, `crtbegin.o` and `crtend.o`.
- The sizes differ: hello.i 14,825; hello.s 667; hello.o 1,504; hello 15,960; greet.o 1,360.
- The undefined reference is at `.text+0x9`, not `+0x5`.
- `gcc -v` prints 36 lines, not 33.
- `grep -E 'string|ascii' escape.s` also prints `.string "GNU"`.
- `-Wint-conversion` is only a warning with GCC 13 (I3).
§03.01's Sources bullet listed such differences honestly; this one hides them.
**Evidence:** /tmp/r0302 runs: `CC1=$(gcc-14 -print-prog-name=cc1); $CC1 -quiet -std=c23 hello.c -o byhand.s` gives "fatal error: bits/libc-header-start.h: No such file or directory". The `-save-temps` listing and `file hello` gave the sizes and "pie executable" above. `gcc-14 -v hello.c` shows Scrt1.o and crtbeginS.o.
**Fix:** "The x86-64 programs were cross-checked in the author's workspace with GCC 14.2.0 on Ubuntu 24.04. The results agreed in substance, except that Ubuntu's GCC builds position-independent executables by default (so the startup files are `Scrt1.o`, `crtbeginS.o` and `crtendS.o`, the file sizes differ and `file` reports a "pie executable"), and that running `cc1` by hand needs Debian's extra option `-imultiarch x86_64-linux-gnu` (see the note after the by-hand commands)."

**E3. Lines 418–431, overgeneralization (portability), medium.**
**Problem:** The text presents `$CC1 -quiet -std=c23 hello.c -o byhand.s` as something any reader can do: "nothing stops you from doing the driver's job yourself" and "`cc1` and `as` are ordinary programs that you can run by hand". On Debian and Ubuntu (multiarch systems), the driver passes `cc1` an extra option, `-imultiarch x86_64-linux-gnu`. Without it, `cc1` cannot find `/usr/include/x86_64-linux-gnu/bits/...`, and `#include <stdio.h>` fails. This is also a good lesson about what the driver adds.
**Evidence:** The gcc-14 `-v` cc1 line is `.../14/cc1 -quiet -v -imultiarch x86_64-linux-gnu hello.c ...`. The by-hand run without that option fails as quoted in E2. With `-imultiarch x86_64-linux-gnu` added, it builds and prints `hello, world`.
**Fix:** Add after line 425: "(This works on Fedora as shown. On Debian and Ubuntu the driver also gives `cc1` the option `-imultiarch x86_64-linux-gnu`, which tells it where the system keeps its machine-specific headers. Without it, `cc1` stops with `bits/libc-header-start.h: No such file or directory`. Copy the option from your own `gcc -v` output. This is one more thing the driver does for you.)" Then change line 431 to "`cc1` and `as` are ordinary programs that you can run by hand, provided you give them the options the driver would have given".

**E4. Line 132, factual (what -E shows), low–medium.**
**Problem:** "so that `return 0;` stays on line 9 of the output as in the source" is false. In the `-E` output, `return 0;` comes after all of `stdio.h` (hundreds of lines). It counts as line 9 of `splice.c` only because a line marker `# 5 "splice.c"` comes before `int main`, and every line after it is counted from that marker.
**Evidence:** `gcc-14 -std=c23 -E splice.c | tail -8` shows `# 5 "splice.c"` directly before `int main(void) {`.
**Fix:** "GCC then prints two empty lines. The `-E` output contains a line marker, `# 5 "splice.c"`, just before `int main`, and the compiler counts the lines after it from there. The two empty lines keep `return 0;` at the position it is counted as line 9 of `splice.c`, so error messages after it keep their correct line numbers."

**E5. Lines 53–66, reasoning, low–medium.**
**Problem:** The paragraph says that phase 1 "turns whatever the system uses into one newline character", and then offers a CRLF file on Linux as the check ("You can check that GCC does this"). Linux does not use CR LF, so the experiment does not show phase 1 mapping the system's own convention. It shows that GCC also accepts a foreign convention. That is GCC's implementation-defined choice: phase 1's mapping is "in an implementation-defined manner" (N3096 §5.1.1.2). Another Linux compiler could treat the CR as an ordinary character. The conclusion at line 66 ("as if they were ordinary Linux newlines") is right, but the experiment does not prove the general claim it is offered for.
**Evidence:** N3096 phase 1: "Physical source file multibyte characters are mapped, in an implementation-defined manner, to the source character set (introducing new-line characters for end-of-line indicators) if necessary."
**Fix:** Replace the last sentence of line 53 with: "How the end of a line is recognized is left to each implementation. GCC goes further than the standard requires: it accepts a newline, a carriage return followed by a newline, or a lone carriage return as an end of line on every system, so a file written on Windows compiles unchanged on Linux. You can check it:". At line 66, add "(an implementation's choice, which GCC documents in its preprocessor manual)".

**E6. Line 160 (and Self-check 5, line 553), incomplete statement of a rule, low–medium.**
**Problem:** The section quotes the pp-number rule from N3096 §6.4.8 as "begins with a digit (or a point and a digit), and continues with any letters, digits, underscores and points, and also with a + or - sign ...". It leaves out C23's digit separator: a pp-number also continues with `'` followed by a digit or a nondigit. This is the edition the book uses, and the reader will meet `1'000'000` in §05.06. The rule as written would make the reader expect `1'000` to be cut into several preprocessing tokens.
**Evidence:** N3096 §6.4.8 pp-number alternatives: digit; `.` digit; pp-number identifier-continue; pp-number `'` digit; pp-number `'` nondigit; pp-number e sign, E sign, p sign, P sign; pp-number `.`.
**Fix (line 160):** "... and continues with any letters, digits, underscores and points; with a single quote followed by a digit or letter (C23's digit separator, as in `1'000'000`, §05.06); and also with a `+` or `-` sign when it follows `e`, `E`, `p` or `P` ...". Add "a digit separator `'`" to the answer to Self-check 5 as well.

## 2. Imprecisions and risks of misunderstanding

**I1. Lines 68, 81–97, version and mode specific, medium.**
**Problem:** The reader may conclude that a C17 compiler, or GCC before C23, converts trigraphs. GCC converts them only in strict ISO modes (`-std=c89` … `-std=c17`) or with `-trigraphs`. In its default GNU modes (`gnu17` in GCC 14, `gnu23` in GCC 15+), it ignores them, so plain `gcc tri.c` prints `Is it true??!` under any version. Also, line 97's "GCC merely warns that, under an older standard, they would not have" misreports the warning, which only says "ignored, use ‘-trigraphs’ to enable".
**Evidence:** `gcc-14 -std=gnu17 -Wall tri.c` and `gcc-14 -Wall tri.c` both print the "ignored" warning and `Is it true??!`. Only `-std=c17` converts. Clang behaves the same way in its GNU modes.
**Fix (line 97):** "Under C23 the three characters stay as they are; GCC warns that it ignored a trigraph and names the option, `-trigraphs`, that would restore the old behavior. (GCC ignores trigraphs in its default GNU modes too, even under older editions; it converts them only when a strict `-std=c89`…`-std=c17` is given, as here.)"

**I2. Line 261, standard conformance, medium.**
**Problem:** "`\x41BC` is a single escape sequence with the value 0x41BC, too large for a character (hence the warning)" presents the warning as an advisory and the 2-byte result as the meaning. An out-of-range hexadecimal escape is a constraint violation (N3096 §6.4.4.4 Constraints, applied to string literals by §6.4.5). The standard requires a diagnostic and gives such a program no meaning. The 2 bytes and the stored value (GCC keeps the low byte, 0xBC) are GCC's choices.
**Evidence:** `gcc-14 -std=c23 -pedantic-errors one.c` gives "error: hex escape sequence out of range" and exit 1.
**Fix:** "... with the value 0x41BC, too large for a `char`. That breaks a rule the standard calls a *constraint*, so a diagnostic is required. GCC gives a warning (an error with `-pedantic-errors`), keeps one character, and the literal holds that character and the null character: 2 bytes, not 4."

**I3. Lines 267–288, version specific, medium.**
**Problem:** `sem.c` is shown as an error. It is an error only since GCC 14, which made `-Wint-conversion` an error by default. GCC 13 and earlier give a warning and produce a program. The standard requires only a diagnostic (a constraint violation in simple assignment/initialization).
**Evidence:** `gcc -std=c2x -Wall sem.c -o sem13` (GCC 13) gives "warning: initialization of ‘int’ from ‘char *’ makes integer from pointer without a cast" and exit 0.
**Fix:** Add after line 288: "(Before GCC 14 this was only a warning, and a program was produced; the standard requires a diagnostic but not that translation stop. Treat such a warning as an error.)"

**I4. Line 321, mechanism, low.**
**Problem:** "is relayed by `collect2`" suggests that the `undefined reference` text passes through collect2. `ld` writes its own messages to the terminal. collect2 only adds the last line, reporting ld's exit status.
**Fix:** "The first two lines come not from the compiler but from the linker, `ld.bfd` (Fedora's `ld`), and the last from `collect2`, which ran it and reports that it failed: ..."

**I5. Line 339, source attribution, low.**
**Problem:** GCC Internals describes collect2 as working by linking once, scanning for constructor symbols, and linking a second time. It does not say "on some systems". The claim that on Linux collect2 "in effect just runs ld" is not in the cited manual, and it is not listed as inference at line 597. collect2 also takes part in LTO. The `-plugin .../liblto_plugin.so` and `lto-wrapper` arguments on line 332's source line show this.
**Fix:** "(GCC's internals manual describes `collect2` as the utility that arranges for initialization functions to be called at start time, if necessary by linking the program twice. On GNU/Linux, whose linker and startup files already provide that service, it in effect runs `ld` once, as the `-v` output shows.)" Add this point to the Inference bullet.

**I6. Line 339 vs §02.06, cross-section consistency, low–medium.**
**Problem:** The promise ledger records that §02.06 named the startup files `Scrt1.o`, `crti.o`, `crtbeginS.o`, `crtendS.o`, `crtn.o` (position-independent variants). Here, with "§02.06 met their role", the reader sees `crt1.o`, `crtbegin.o`, `crtend.o` with no explanation. Both are correct for their machines: Fedora's default GCC builds non-PIE (the log's `file hello` says "executable", not "pie executable"), while Ubuntu's builds PIE.
**Fix:** Add: "(On systems whose GCC builds position-independent executables by default, such as Ubuntu, you will see `Scrt1.o`, `crtbeginS.o` and `crtendS.o` instead, the names §02.06 showed; §03.06 explains the difference.)"

**I7. Lines 364–370, completeness of the "why this order" argument (promise §00.02), medium.**
**Problems:**
1. Line 366 says the data dependency "fixes the order completely", which makes the next two "deeper" reasons logically redundant. The dependency only says what follows from GCC's chosen file formats. The real reason the formats are arranged so is reason 2.
2. The argument does not mention link-time optimization. With `-flto`, cc1 writes GCC's intermediate representation instead of final code, and `lto1` finishes the translation during the link, through the very `-plugin liblto_plugin.so` / `lto-wrapper` arguments visible in the collect2 line. That does not break the standard's as-if order, but it contradicts the unqualified "Phases 1 to 7 ... need nothing from any other" and "not a convention". A reader who meets `-flto` will think the section was wrong.
3. "this turns hours into seconds" (line 370) is unsourced and not in the Inference bullet.
**Fix:**
1. Line 366: "This is the plain data dependency of a pipeline: once each program's output format is chosen, the order follows. The next two reasons explain why the formats are arranged so that linking comes last."
2. Add after line 370: "(One modern option bends, but does not break, this arrangement: with `-flto`, link-time optimization, `cc1` writes an intermediate form of the program instead of finished code, and the last part of translation runs during the link, when all the files can be seen together. The `-plugin` and `lto-wrapper` arguments in the `collect2` command above are the hooks for it; §39.02 returns to it.)"
3. Replace "turns hours into seconds" with "can turn a long rebuild into a short one", or list it as the author's estimate.

**I8. Line 434 (myth box), heuristic stated too strongly, low–medium.**
**Problem 1:** "a message beginning with the assembler's name or `Assembler messages` ... in normal use means a bug in the compiler or in hand-written assembly". In practice the commonest causes are inline `asm` statements in C (§39.03), and a binutils older than the compiler (an `-march` that `as` does not know).
**Problem 2:** "it has never seen the C library" is too strong: `cc1` read the library's headers, its declarations. It never saw its code.
**Fix:** "... `as`, which in normal use means an error in hand-written or inline assembly (§39.03), an assembler too old for the compiler, or, rarely, a compiler bug". Also: "it has seen the C library's declarations in the headers, but never its code, the startup files or your other source files."

**I9. Line 359, overgeneralization, low.**
**Problem:** "every processor GCC supports" is not true: some GCC targets use a non-GNU assembler. Examples: Darwin uses the system assembler, AIX uses its native `as`, amdgcn uses LLVM's `llvm-mc`, and nvptx uses its own tools.
**Fix:** "... and almost every processor GCC supports".

**I10. Line 535, version specific, medium.**
**Problem:** The naming rule for `-save-temps` intermediates (`avr_hello.elf-avr_hello.i`) is presented as how GCC behaves. It was introduced in GCC 11. avr-gcc 7.3, the version in Ubuntu's own package and the one §03.01 used in the author's workspace, writes `avr_hello.i`, `avr_hello.s` and `avr_hello.o`. A reader with an apt-installed avr-gcc will not see what the text describes.
**Evidence:** In /tmp/r0302/avr, avr-gcc 7.3.0 with the same command produced `avr_hello.i`, `avr_hello.o` and `avr_hello.s` (and an elf of 6,608 bytes and a hex of 635 bytes). The GCC manual (Overall Options) gives the current rule: `gcc foo.c bar.c -o dir/foobar` gives `dir/foobar-foo.*`, and a single input whose base name matches the output gives `dir/foo.*`.
**Fix:** "The intermediate files are named after the output, `avr_hello.elf-avr_hello.i`. Since GCC 11, when the output's name is not simply the source's name without its suffix, GCC puts both names together, so that two programs built in one folder cannot overwrite each other's files. (For `-o hello` and `hello.c` it used the plain names; older versions, such as the avr-gcc 7.3 that some Linux distributions still ship, always use the plain names.)"

**I11. Line 535, Intel HEX description, low.**
**Problems:**
1. The text quotes `0C9434000C94490...` without telling the reader that the line begins with `:10000000` (start code, byte count 0x10, address 0000, record type 00), which must be skipped.
2. "written as text with an address and a checksum on each line" omits the byte count and record type, and the last line (`:00000001FF`) carries no data.
3. Grammar: "is `jmp` instructions".
4. "exactly the bytes avr-objdump showed there" holds only if §02.06's program had its `__ctors_end` at 0x68 (no PROGMEM data or constructors). I could not see §02.06 to confirm.
**Evidence:** The facts themselves are correct. In the log's first record `:100000000C9434000C9449000C9449000C94490061`, `0C 94 34 00` is `jmp 0x68` (word address 0x34), and `0C 94 49 00` is `jmp 0x92` (`__bad_interrupt`). avr-objdump -d of my build shows `0: 0c 94 34 00 jmp 0x68 <__ctors_end>` and `4: 0c 94 49 00 jmp 0x92 <__bad_interrupt>`. The checksum works out: 0x10+0x0C+0x94+0x34+0x0C+0x94+0x49+0x0C+0x94+0x49+0x0C+0x94+0x49 = 0x39F, and 0x100-0x9F = 0x61.
**Fix:** "... compare its first line with the vector table of §02.06. After the colon come the number of data bytes (`10`, sixteen), the address (`0000`) and the record type (`00`, data); then `0C943400` is the first `jmp` instruction, `0c 94 34 00`, the bytes `avr-objdump` showed there, followed by three more `jmp`s and a checksum, `61`."

**I12. Line 537, Arduino IDE claims (not run), low–medium.**
**Problems:**
1. The Arduino IDE has no menu command for uploading an arbitrary `.hex` file. "upload `avr_hello.hex` with the Arduino IDE's uploader" can only mean running the `avrdude` it bundles.
2. The verbose compile output shows the driver-level commands (`avr-g++ -c ...`, `avr-gcc -c ...` for the core's C files, `avr-gcc-ar` building `core.a`, the `avr-gcc ... -flto` link, `avr-objcopy` twice for `.eep` and `.hex`, `avr-size`). **Fix:** "If you have an Uno, upload `avr_hello.hex` with `avrdude` (§36.01 gives the command; the Arduino IDE installs a copy). There is also an extra first step that turns the `.ino` sketch into a C++ file (sketches are C++, §02.05, so for the sketch the driver runs `cc1plus` instead of `cc1`)." Hands-on A's answer (line 585) already says this was not observed.

**I13. Line 27 and line 545, history, low.**
**Problem 1:** "A PDP-11 program could address only 64 KB" is true only of a single address space. The PDP-11/45 and /70, which V7 ran on, had separate instruction and data spaces (`cc -i`/`ld -i`), giving 64 KB of each. **I14. Line 48, normative status, low.**
**Problem:** "It requires only that the result be *as if* the phases occurred separately and in this order" attributes the requirement to §5.1.1.2. The sentence is footnote 6 ("This requires implementations to behave as if these separate phases occur, even though many are typically folded together in practice"). Footnotes are not normative. The binding basis is the precedence statement in §5.1.1.2 together with the general as-if rule of §5.1.2.3 (§02.03).
**Fix:** "... and a footnote to §5.1.1.2 spells this out, remarking that in practice many of them are usually folded together."

**I15. Line 158, completeness, low.**
**Problem:** The list of preprocessing-token categories omits "each universal-character-name that cannot be one of the above" (N3096 §6.4).
**Fix:** "... punctuators, and, as a last resort, any single character (or universal character name, §08.03) that fits none of these."

**I16. Line 180, wording, low.**
**Problem:** "which the rule treats as the start of an exponent" is not what the rule does. The rule does not know about exponents or hexadecimal; it simply allows a sign after any `e` or `E`.
**Fix:** "phase 3 sees `E` followed by `+`. The rule allows a sign after any `e` or `E`, because there it might begin an exponent, so it makes `0x1E+1` a single preprocessing number."

**I17. Line 186, factual detail, low.**
**Problem:** "every trace of `#` has gone, except ... the line markers" is not quite true of GCC's `-E` output. `#pragma` directives are passed through as `#pragma` lines, so that `cc1` can act on them.
**Evidence:** `printf '#pragma GCC diagnostic push\nint x;\n' | gcc-14 -E -` keeps `#pragma GCC diagnostic push`.
**Fix:** "... except the line markers that GCC adds ..., and any `#pragma` lines, which GCC keeps for the compiler proper (§22.06)."

**I18. Lines 147–154, presentation of output, low.**
**Problem:** Listing 03.02-3's output is shown with no terminal block, and it stops before the `0` that the next sentence says `echo $?` prints. The log (034) was produced by `gcc -std=c23 -Wall -Wextra -pedantic trap.c -o trap; ./trap; echo $?`, and its output ends with `0`. Every other listing shows its command.
**Fix:** Insert the terminal block `$ gcc -std=c23 -Wall -Wextra -pedantic trap.c -o trap; ./trap; echo $?` before the output block, and add the final line `0` to the output block.

**I19. Line 192, implementation-defined value, low.**
**Problem:** "`\n` becomes the single code 10, `\x41` becomes 65, the code of `A`" states the codes as if C fixed them. 10 for newline and 65 for `A` are ASCII/UTF-8 values, which GCC uses on this machine. The standard fixes only that `\x41` has the value 0x41.
**Fix:** "... `\n` becomes the single code 10 (in the ASCII-based codes GCC uses here; §08.01), `\x41` becomes 65, which in those codes is `A`."

**I20. Line 265, grammar statement, low.**
**Problem:** "a declaration with `=` must be followed by an expression" is wrong: `=` is followed by an *initializer*, which may also be a braced list (`int a[2] = {1, 2};`, and in C23 `= {}`).
**Fix:** "... the rules that say, for example, that the `=` in a declaration must be followed by an initializer, an expression or a list in braces."

**I23. Line 577, Experiment 03.02-3 answer, low.**
