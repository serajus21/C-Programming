# Independent review of §03.05 "Assembling: Object Files"

Reviewer's evidence: Fedora logs 066–070 (the authority). Checks in my own shell were done on Ubuntu 24.04 with gcc-14, binutils 2.42, avr-gcc 7.3 and avr-binutils 2.26. Where a correction rests on my shell, I give a Fedora command to confirm it. Sources fetched: the psABI (uclibc copy, Draft 0.99.7), the TIS ELF 1.2 PDF (Princeton copy), MaskRay's "Evolution of ELF object file format", the McCamant lecture notes, and GAS's `write.c` and `dw2gencfi.c` (NetBSD mirror of the binutils sources).

## Verdict

**Approve after corrections.** The numerical core is excellent. Every output block matches the logs exactly, except two that the text says it shortened or that come from the psABI. I recomputed all the arithmetic and found it correct: the 1,512-byte accounting, every figure offset, the ELF-header decode, the symbol entry, the `.rela.text` bytes, 0xfffffeec, 0x4004b0, 7, 0xfffffe12, 0xf9c, −60, and the `.bss`/`.data` sizes. The psABI quotations are verbatim, and so is the readelf man-page quotation.

However, the section has these problems:
- one plainly false claim in the opening puzzles;
- a missing listing that is referenced twice;
- three wrong AVR claims: who defines `__do_copy_data`, why `.LC0` is kept, and what `avr-size` counts in `text`;
- a self-check whose answer rests on a false premise (12) and another whose question cannot be answered as posed (1);
- a weak, partly wrong answer to Self-check 10;
- an incomplete Experiment 1 answer (strip also removed the relocations);
- a history sentence that misstates its source;
- a false mechanism for the `.cfi` listing;
- four promises from `source-notes.md` that are not kept.

Depth is adequate for the TOC bullets. Several items in the logs that would strengthen it are unused (listed under Improvements).

## ERRORS (must fix)

**E1. Puzzle 3 is false.** Text: "`main` begins at address 0 in `hello.o`, and so does every function in every object file."
In `sections.o`, `main` is at 0x2b and `helper` at 0 (log 066, `nm sections.o`: `000000000000002b T main`). The section's own Table 03.05-2 shows this.
Fix: "…and so does every *section* in every object file", or "…and so does the first function of every object file."

**E2. "Listing 03.05-3" does not exist.** It is referenced in puzzle 4 ("(Listing 03.05-3)") and at line 331 ("Listing 03.05-3's experiment makes the point…"). The only listing is 03.05-1 (`sections.c`), and there is no 03.05-2. `bss.c` and `data.c` are never shown, yet the reader is asked to reason about them (Self-check 4).
Fix: add `bss.c` and `data.c` as Listing 03.05-2 (both files in one listing, or 03.05-2 and 03.05-3 in order of appearance) where they are introduced. Change puzzle 4's reference to "(Listing 03.05-2, below)" and correct line 331.

**E3. Table 03.05-3 introduction.** Text: "All but `xxd` come from GNU binutils, the same package as `as` and `ld`."
`file` is not part of binutils. It is the `file` program (libmagic). `xxd` comes with Vim.
Fix: "All but `file` and `xxd` come from GNU binutils…". Fedora check: `rpm -qf /usr/bin/file /usr/bin/xxd /usr/bin/nm`.
Also in the table, `file` decides "from its first bytes" only in part: it also parses the headers and the section table (that is how it knows "not stripped"). Say "from its headers".

**E4. `__do_copy_data` is not avr-libc's.** Text (line 588): "`__do_copy_data`, from avr-libc's startup code, copies…". Sources (line 705): "avr-libc's startup code (`__do_copy_data`, `__data_start`, `__data_end`, `__data_load_start`)".
- `__do_copy_data` (and `__do_clear_bss`) are defined in **libgcc**, in section `.init4`. In my shell, `avr-nm` on avr5 `libgcc.a` shows `T __do_copy_data` in a member that has `U __data_end`, `U __data_load_start` and `U __data_start`, and `avr-objdump -h` shows that member's code in `.init4`.
- `__data_start`, `__data_end` and `__data_load_start` are defined by the **default linker script** (`PROVIDE (__data_start = .)`, `__data_load_start = LOADADDR(.data)` in `avr-ld --verbose -m avr5`). That is also why log 067 shows `000000ce A __data_load_start`: the capital `A` marks an absolute symbol assigned outside any section. This fact closes the `a`/`A` theme nicely.
- §03.04 already taught that libgcc supplies `__udivmodhi4`, so attributing this routine to libgcc keeps the book consistent.

Fedora check:
```
avr-nm -A $(avr-gcc -mmcu=atmega328p -print-libgcc-file-name) | grep -E 'T __do_copy_data'
avr-objdump -h $(avr-gcc -mmcu=atmega328p -print-libgcc-file-name) | grep -B1 -A1 init4 | head
avr-ld --verbose -m avr5 | grep -n -E '__data_(start|end|load_start)|rodata|ALIGN \(2\)|ALIGN\(2\)'
```
Also fix the mechanism. Log 066 shows symbol 18 `__do_copy_data` as UND, but **none of the 7 relocations uses it**. The compiler writes `.global __do_copy_data` at the end of the `.s` file (`avr-gcc … -S -o - | tail -2`). The reference is not a call. It exists only so that the linker extracts the routine from the archive `libgcc.a`. The routine's code lands in `.init4`, and the startup sections run by falling from one into the next before `main` (§36.05). Without this explanation the reader has no first-principles answer to "how does a mere name make code run?"

**E5. Self-check 12 has a false premise, and its answer is wrong.** Question: "why does the string count in both `text` and `data` in `avr-size`?" Answer: "The bytes therefore occupy flash (counted in `text`, as part of the image after `.text`)…"
Log 066: `avr-size` gives `text 206`, and `.text` is 0xce = 206 bytes. So `text` is the `.text` section alone. The string's flash copy (at LMA 0xce) is **not** in `text`; it is counted once, in `data` (16). Berkeley `size` puts allocated read-only/code sections in `text` and allocated writable sections with contents in `data`. Flash use is text + data = 222 (the `dec` column). RAM use is data + bss = 16.
My shell shows the same pattern (`text 204`, `.text` 0xcc).
Fix the question to: "why does the string cost both flash and RAM, and how do you read that from `avr-size`?" Fix the answer to: "flash = text + data = 222; RAM = data + bss = 16". Make line 588 say the same: "206 bytes of `text` and 16 of `data`: flash holds 206 + 16 = 222 bytes, and RAM 16."

**E6. AVR: `.LC0` is not kept for relaxation, and the relocation description is incomplete.** Text (line 565): "The local labels `.L2`, `.L3`, `.L4` and `.LC0` are present… They are kept because the AVR's linker can *relax* the code…"
That reason holds for `.L2`–`.L4`, which are in a code section. It does not hold for `.LC0`. Log 066 shows two pairs of LDI relocations:
- `18/1a: R_AVR_LO8_LDI/HI8_LDI .rodata.str1.1 + 0` (converted to the section symbol);
- `2a/2c: R_AVR_HI8_LDI/LO8_LDI .LC0 + e` (left on `.LC0`).

GAS's `write.c` (`adjust_reloc_syms`) says: "Never adjust a reloc against local symbol in a merge section with non-zero addend." `.rodata.str1.1` is a mergeable string section (`AMS`). The zero-addend reference was converted and the +0xe reference was not, which is exactly the rule. The first-principles reason (the GAS comment gives none, so label this as inference): the linker may delete duplicate strings and move the survivors. "Section + 14" would mean "the string that starts at offset 14", which does not exist. "`.LC0` + 14" means "14 bytes into the string `.LC0`", which survives merging.
The text also never mentions the `.LC0 + e` pair. It is 0xe = 14 bytes past the start, the end of the 14 characters, which the loop compares `Z` against (inference from the addend; confirm by disassembly).
The claim "`R_AVR_7_PCREL .L3` (the 7-bit branch of `brne`)" is not in the logs: log 067's disassembly stops at `<.L3>`. Confirm on Fedora:
```
avr-objdump -dr avr_hello.o | sed -n '/<.L3>:/,$p'
```
Minor point on naming: `R_AVR_13_PCREL` is named for the byte range (a 12-bit word field), whereas `R_AVR_7_PCREL` is named for the 7-bit word field. Binutils' naming is inconsistent, and this precise reader will want to know that.

**E7. Experiment 03.05-1 answer: strip removed four sections, not two.** Text: "`strip` removed the symbol and string tables (the copy has 10 sections instead of 14…)… (and the linker also complains that it cannot process `.eh_frame`, whose relocation needed a symbol)."
14 − 10 = 4. `strip` also removed `.rela.text` and `.rela.eh_frame`. On my binutils 2.42 the stripped copy keeps exactly: NULL, `.text`, `.data`, `.bss`, `.rodata`, `.comment`, `.note.GNU-stack`, `.note.gnu.property`, `.eh_frame`, `.shstrtab`. (Log 068's `grep -c '\]'` printed 11 because it also counts the `[Nr]` heading, so 10 is right.)
The lesson the answer misses: a stripped object file has lost its *notes*. Its holes are still zeros but nothing says how to fill them, so it is unusable for linking even apart from `main`. The `.eh_frame` error follows because the relocation for the FDE's start address was removed (not "needed a symbol").
Fedora check: `readelf -S -W s.o`.

**E8. Self-check 1 cannot be answered as posed.** It asks "Which byte in the header distinguishes the three files' kinds", but `/bin/ls` and `libc.so.6` both have type 3 (`DYN`), as the answer itself and log 068 show. Also, the type field is two bytes (`e_type`), not one byte.
readelf's label "Position-Independent Executable file" comes from the `DF_1_PIE` flag in the dynamic section, not from the header. My shell: `readelf -d /bin/ls` prints `Flags: NOW PIE`. Fedora: `readelf -d /bin/ls | grep FLAGS_1`.
Fix the question to "which field…, and can it tell all three apart?" and the answer to "No: `ls` and `libc.so.6` both have 3. readelf tells them apart from the dynamic section's PIE flag (§21.06)." While there: `libc.so.6`'s OS/ABI byte is 3 ("UNIX - GNU"), not 0 (see E9).

**E9. ELF header decode, item 2.** Text: "the **OS/ABI** (0: System V, the generic value Linux uses). The rest of the first 16 bytes is padding."
- Byte 8 is the **ABI version** (`EI_ABIVERSION`), which `readelf -h` prints as "ABI Version: 0". Only bytes 9–15 are padding.
- "the generic value Linux uses" is too broad. Files that use GNU extensions (IFUNC, unique symbols) carry 3, `ELFOSABI_GNU`. On my machine `readelf -h libc.so.6` prints `OS/ABI: UNIX - GNU`. Fedora: `readelf -h /lib64/libc.so.6 | grep OS/ABI`.
- Sourcing: TIS 1.2, cited for "header fields", has neither `EI_OSABI` nor `EI_ABIVERSION`. In TIS 1.2, `EI_PAD` begins at byte 7: "This value marks the beginning of the unused bytes in e_ident". Cite the System V gABI (later editions) for bytes 7 and 8.

**E10. History box misstates its source.** Text: "Linux moved from `a.out` to ELF in the mid-1990s, partly because shared libraries were hard to build in `a.out`."
McCamant's notes say: "Linux switched to ELF c. 1995 … In part because they'd chosen a hard-to-use approach to a.out shared libraries." The difficulty was Linux's chosen *approach*, not the format: MaskRay notes that "in 1988, SunOS 4.0 got an extended a.out format with dynamic shared library support."
Fix: "partly, in McCamant's words, 'because they'd chosen a hard-to-use approach to a.out shared libraries'". Smaller corrections in the same box:
- The preface spells the committee "Tool Interface Standards (TIS) Committee".
- McCamant says PE is "Partially derived from COFF", which is weaker than "descended from".
- The TIS preface says USL "originally developed and published" ELF. Quote it rather than paraphrase.

**E11. False mechanism for the `.cfi` listing.** Text (line 92): "their counter runs 0000, 0029, … interleaved with the `.text` counter, because they are being written into `.eh_frame` at the same time."
GAS's `dw2gencfi.c` does not write `.eh_frame` as it reads the directives. Each `.cfi_*` appends a record to the current FDE's list, and `cfi_finish` writes the CIE and FDEs at the end of assembly. The listing shows each directive's bytes at its eventual position in `.eh_frame`, but they are not produced "at the same time".
Fix: "the listing shows, beside each `.cfi` line, the `.eh_frame` bytes that encode it (GAS records the directives as it reads them and writes `.eh_frame` at the end)."
You can also decode them: 0x00–0x17 is the CIE. The FDE starts at 0x18, and its start-address field at 0x20 is the hole of `.rela.eh_frame`'s `R_X86_64_PC32 .text + 0`. Then `41`=advance 1, `0e 10`=CFA offset 16, `86 02`=rbp saved at CFA−16, `43`=advance 3, `0d 06`=CFA register rbp, `50`=advance 16, `0c 07 08`=CFA = rsp+8, and three padding `00` bytes reach 0x38 = 56.

**E12. Wrong gap numbers.** Text: "Running the linker alone on `hello.o` shows both of the last two gaps at once". The `ld` output shows gap 3 (undefined `puts`) and gap 5 (no `_start`), not 4 and 5.
Fix: "shows gaps 3 and 5 at once".

**E13. Unsupported use of the FILE symbol.** Text: "the symbol of type `FILE` records the name of the source file, `hello.c`, which is how a debugger or `nm -a` can say which file a local symbol came from."
`nm -a` only lists the symbol (`a hello.c`, log 067). It attributes nothing. Debuggers use DWARF when it is present. The use visible in the reader's own logs is the **linker's** message prefix `hello.c:(.text+0xa): undefined reference to 'puts'` (log 067). With no debug information, `ld` takes `hello.c` from the FILE symbol. I verified this in my shell: after `objcopy --strip-symbol=hello.c hello.o nofile.o`, `ld nofile.o` prints `(.text+0xe): undefined reference to 'puts'` with no file name.
Fedora: `objcopy --strip-symbol=hello.c hello.o nofile.o && ld nofile.o -o x`.

**E14. Self-check 10's answer is weak and partly wrong.**
- "A 32-bit hole cannot hold a 64-bit addend" is irrelevant to `R_X86_64_PLT32`, whose −4 fits.
- "once the linker overwrote the hole, the addend would be gone if the code ever needed relocating again" does not describe a real failure: REL linkers, including `ld -r`, handle in-place addends routinely.
- In fact 32-bit x86 does exactly what the question asks. My shell: `as --32` on `call puts` gives `e8 fc ff ff ff` with `R_386_PC32 puts`; the −4 is in the hole.

The honest answer has three parts. Nothing essential is lost for a 32-bit PC-relative call. The real costs of REL are that the linker must read the section contents to learn the addend, and that a field narrower than the value cannot hold the addend at all. The reader's own AVR object has the perfect case: `R_AVR_HI8_LDI .LC0 + e`. The `ldi` field holds 8 bits, and the high byte of S + 14 depends on a carry out of the low byte, which a hole holding only the high byte of 14 cannot convey. The gABI says: "Depending on the processor architecture, one form or the other might be necessary or more convenient." (TIS 1.2 has the same sentence for Elf32.)
Rewrite the question too: "Why does x86-64 store the addend in the relocation? Find a relocation in `avr_hello.o` whose addend could not be stored in its hole."
Fedora demo for the hood box:
```
printf '.text\ncall puts\n' | as --32 -o t32.o && objdump -dr t32.o
```

## IMPROVEMENTS

**I1. Make "Why both `objdump` and `readelf`?" concrete with the log already in hand.** Log 067's `objdump -h hello.o` lists **8** sections, not 14. It hides the null entry, both `.rela` sections, `.symtab`, `.strtab` and `.shstrtab`, and turns them into BFD flags (`RELOC` on `.text` and `.eh_frame`). It renames alignment as `2**3` and adds an LMA column. That is "BFD's general model" in one picture. As written, the claim is abstract.

**I2. Close "every byte of `hello.o` accountable".** The section header table is 896 of the 1,512 bytes (59%), yet no entry is decoded.
- Decode `.text`'s entry: `xxd -s 0x2a8 -l 64 hello.o`. Entry 1 is at 0x268 + 64.
- Show `.shstrtab` (log 066 has it). Its 116 bytes are exactly 1 + `.symtab`8 + `.strtab`8 + `.shstrtab`10 + `.rela.text`11 + `.data`6 + `.bss`5 + `.rodata`8 + `.comment`9 + `.note.GNU-stack`16 + `.note.gnu.property`19 + `.rela.eh_frame`15 = 116.
- There is no separate `.text` or `.eh_frame` string: their `sh_name` points into the tail of `.rela.text` (offset 0x20) and `.rela.eh_frame`. Suffix sharing is a delightful, verifiable detail.
- The symtab hex (log 067) also shows that section symbols have name offset 0 (readelf supplies the section name), and that `ABS` is stored as `f1ff` = 0xfff1 (`SHN_ABS`) and `UND` as 0.
- `xxd -s 0x40 -l 0x22 hello.o` (log 067) shows the 34 program bytes raw.

**I3. Use `nm -a`'s output (log 067).** It shows `a hello.c`, `r .rodata`, `t .text`. That directly explains the `a` letter (absolute, here the FILE symbol), and it links the x86 file to the AVR `a`/`t` discussion. Also re-run the failed `man nm` grep (log 066 printed nothing) and quote nm's definitions. Note that the case rule has exceptions: the man page says lowercase is "usually local" and lists `u`, `v`, `w` as lowercase global symbols. Fedora: `man nm | col -b | sed -n '/^ *"A"/,/^ *"?"/p'`.

**I4. COMMON symbols.** `int zeros[1000];` is a tentative definition. GCC before version 10 (and `-fcommon` today) makes it a COMMON symbol (`C` in nm, `COM` in readelf), not `.bss`. Many books this reader may consult (CS:APP, for example) show `COMMON`. One sentence plus an experiment (`gcc -fcommon -c sections.c && nm sections.o | grep zeros`) prevents confusion. This touches §21.04, so keep it brief.

**I5. Forward references and instruction size.** "remembering each unfinished instruction and finishing it when the label turns up" omits the real x86 difficulty: the assembler does not know a forward `jmp`'s *length* (2 or 5 bytes) until it knows the distance, and that length moves every later label. GAS solves this with variable-size fragments and relaxation. §03.02's Experiment 7 already showed `eb 0a`, a short jump chosen this way. Cite a source for "the GNU assembler uses the second approach" (the GAS internals documentation), or label it as inference.

**I6. Present local-symbol conversion as GAS's practice, not a necessity.** Text: "Local symbols cannot be referred to from any other file, so the assembler expresses each reference to them as a section plus an offset". This is GAS's `adjust_reloc_syms` choice, not a necessity, and the AVR objects in this very section do the opposite (`R_AVR_13_PCREL .L2`). The "global symbols named directly" sentence is supported by `write.c`'s comment: "If the symbol is undefined, common, weak, or global (ELF shared libs), we can't replace it with the section symbol." Quote it.

**I7. Exec format error mechanism.** "The kernel refuses a file without them" is imprecise. Linux's ELF loader first rejects any type other than `EXEC`/`DYN` (`hello.o` fails there) and then requires valid program headers. It returns `ENOEXEC`, and the words "cannot execute binary file" are **bash's**: bash would otherwise try to run the file as a shell script. Source: `fs/binfmt_elf.c`, `load_elf_binary`.

**I8. The AVR VMA lesson.** In `__do_copy_data` (log 067), X is loaded with `0x0100` (`ldi r26,0x00; ldi r27,0x01`), not 0x800100. The 0x800000 exists only inside the tools, and `hi8`/`lo8` drop it. Say so: it makes "the tools add 0x800000" tangible. Also answer Hands-on A from the logs:
- Z = 0x00ce is the source in flash, X = 0x0100 the destination in RAM, and r17 = hi8(`__data_end`).
- The stop test (`cpi r26,lo8(__data_end)`/`cpc`/`brne`) is beyond `head -24`, so give it as a prediction or rerun without `head`.
- Explain the 16th byte, the "one more zero": the linker script's `. = ALIGN(2);` at the end of `.data`.

**I9. Mark unrun or inferred claims.**
- Myth box: "writing to it through a cast does fault there" was not run. Fedora: add `*(int *)&primes[2] = 9;` to a copy and run it; expect `Segmentation fault`.
- "because a `const` object with a known initializer cannot legally change" is GCC's rationale as inferred. Label it.
- Experiment 6: "the first comes from the startup files of the C library" is inference. Check with `readelf -p .comment /usr/lib64/crt1.o /usr/lib64/crti.o /usr/lib/gcc/x86_64-redhat-linux/16/crtbegin.o`. `crtbegin.o` is GCC's, not glibc's, and probably carries `-3`.
- "Choosing a first byte that is not a printable character…" is an unlabeled rationale.
- "`gcc -###` lists them… before it… after it": log 069 greps only the crt names, so the positions relative to `hello.o` are not shown. Show the full `collect2` line or soften.
- Add all of these to "Inference in this section".

**I10. Figure 03.05-1.** The legend's "kept, never executed" colors `.comment` (not loaded, no `A`) the same as `.note.gnu.property` and `.eh_frame` (loaded, `A`). The Why box makes the `A` flag the key distinction, so give loaded and unloaded bytes different colors. The padding entry in the legend is invisible at this scale (7, 5 and 4 bytes). Annotate "16 bytes of padding in three gaps".

**I11. File order versus index order.** `.rela.text` is section 2 but lies at 0x1a8, after `.symtab`. The figure shows this, and a careful reader will ask why. Say that the section header table gives each offset, so the order in the file is free. (Why BFD writes relocations late — they need the final symbol indices — is plausible inference; label it.)

**I12. Self-check 8: add the zero-addend contrast.** Experiment 3's `counter - 8` is already in the answers. In Self-check 8, add "`calls - 4` only if the instruction ends with the displacement".

**I13. EntSize of `.comment` (1).** It is unexplained in the column list. For `M` sections, EntSize is the size of each mergeable element (1-byte characters). One clause makes it complete.

## NITS

1. Line 263: "16 bytes of padding between sections". 7 + 5 bytes lie between sections and 4 lie between `.shstrtab` and the section header table.
2. Item 9: "two zero sizes and counts for the absent program headers" → "a zero entry size and a zero count".
3. Line 236: "`I` marks a relocation section". More precisely, `I` (`SHF_INFO_LINK`) says that Info holds a section index. `.symtab`'s Info (4) has a different meaning, explained later.
4. Line 238: "1 for code". That is true here because `-O0` emits no alignment. At `-O2`, and in the linked `hello` (Align 16, log 066), code is aligned.
5. Line 463: "begins one byte after the `e8`" can be read as a one-byte gap. Write "begins immediately after the `e8` byte".
6. Line 461: "placed below 4 GB (§03.04)". §03.04 does not state this. The small code model (psABI §3.5.1) places symbols in the low 2 GB, and `R_X86_64_32` itself only needs zero-extension (quote: "The linker must verify that the generated value for the R_X86_64_32 (R_X86_64_32S) relocation zero-extends (sign-extends) to the original 64-bit value.").
7. Line 263: readelf labels the `.text` dump message "NOTE", not a warning.
8. Line 398: the edited symtab line also replaces the ASCII column with `........`. Prefer quoting the full line and saying which 8 bytes belong to the entry.
9. Line 405: "Local variables… appear in no section". With `-g` they are described in `.debug_info`. Say "no symbol table entry".
10. Line 564: the parenthetical omits `__SP_H__`/`__SP_L__`, the I/O addresses of the stack pointer's two bytes.
