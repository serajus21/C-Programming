## Verdict

§03.02 is accurate, clearly written and well built. Every phase has a runnable experiment, and the experiments are good ones: the trigraph, the comment that swallows a line, `0x1E+1`, `"\x41" "BC"` and the undefined `greet`. It is not yet at the level of the high-effort sections, and the gap lies in exactly the places this reader cares about most.

**1. The "why it exists" explanations are mostly the author's general reasoning, where documented reasons exist and are better.**
- The standard's own Rationale gives the reason for the phases ("to resolve the numerous questions raised about the precedence of different parses"), for line splicing and for string concatenation. The section does not use it.
- WG14's Defect Report #003 gives the real reason for the greedy preprocessing-number rule.
- In two places the section's stated reason is wrong or incomplete: line 32 and line 101 (E2, E3).

**2. The section names the mechanisms that make the pipeline work but does not show them.**
- How the driver decides what to run (its specs) is not shown.
- What `collect2` actually runs is not shown.
- Above all, the hole the compiler leaves for `greet` is not shown. §02.06 disassembled `_start` to show what calls `main`. §03.02 prints `.text+0x5` and never shows the four zero bytes at offset 5, though that one picture explains the whole order of the pipeline.

**3. The answer to the §00.02 promise ("why it must be this order") is asserted more than demonstrated.**
- Reason 1 is circular: the order follows from the file formats chosen.
- Reason 2 states the conclusion.
- The argument never tries the alternatives (link first? a unity build?), so a demanding reader can still ask "why not?".

**4. One framing inconsistency runs through the text, the table, the figure and the answers.** The text says `as` is "GCC's way of carrying out the end of phase 7". It also says `as` "corresponds to no phase at all". And Table 03.02-2 has `-S` stopping "after phase 7" (E1).

**Rework needed: targeted, not full.** The skeleton, listings, outputs and order are sound. The section needs:
- a rewrite of "Why this order", with the relocation hole as its centerpiece (D1);
- a "why" box built on the Rationale (D4);
- short additions to phases 3, 5 and 6 and to the driver section (D2, D3, D5–D9);
- the E1 consistency fix;
- a handful of self-checks turned from recall into prediction (D12).

My estimate is 1,800–2,400 words of new text and about ten new commands for the Fedora runner.

**Counts:** 5 errors, 15 depth/teaching gaps, 17 imprecisions. §03.01 change check: passed.

## 1. Errors

**E1. Lines 228, 295, 342, 350, 386 (Table 03.02-2), Figure 03.02-1 and the answers to Self-checks 10 and 11: inconsistent placement of `as` relative to phase 7.**

**Problem.** The section says three different things:
- Line 295: the assembler step "is GCC's way of carrying out the end of phase 7".
- Line 350 and the figure: `as` "corresponds to no phase at all" / "not a phase of the standard".
- Line 342, Table 03.02-2 and Self-check 10: `cc1` carries out phases 1 to 7, and `-S` stops "after phase 7".

These cannot all be true. If `as` finishes phase 7 (the correct view), then `-S` stops *inside* phase 7. The standard's phase 7 output is a "translated translation unit", and in GCC that is the object file, not the `.s` text. A careful reader who compares the table with line 295 will see the contradiction.

**Evidence.** N3096 §5.1.1.2: phase 7 ends with the translation unit translated, and phase 8 collects "translator output" into the program image. `ld` reads `.o` files, not `.s` files. So the translated unit that phase 8 consumes is the object file.

**Fix.**
- Table 03.02-2, `-S` row, "Stops after": "`cc1`: inside phase 7 (the language work is done; the machine code is not yet encoded)". `-c` row: "the assembler: the end of phase 7, a translated translation unit".
- Line 228: "`-S` shows the assembly language that `cc1` wrote, which is phase 7's result before the assembler encodes it (§03.04 reads it in full)".
- Line 342: "…so this one program carries out phases 1 to 7, except the last step of phase 7, the encoding into machine code, which it leaves to the assembler."
- Line 350: "Second, there is a program, `as`, that has no phase of its own: it finishes phase 7's work, turning the text `cc1` wrote into the machine code of a translated translation unit. The standard has no separate phase for this because it does not say what phase 7 translates *into*."
- Figure label for `as`: "as — the assembler: finishes phase 7 (no phase of its own)".
- Self-check 10 answer: "`cc1` … carrying out phases 1 to 7 as far as assembly language; `as` … finishing phase 7 by encoding it as machine code in an object file; …".

**E2. Line 32: unlabeled and incomplete causal claim about why the standard lists phases.**

**Problem.** "When the C standard was written in the 1980s, its authors had to describe translation without favoring any particular compiler's arrangement of programs. They did it by listing eight phases…"
- This is the author's inference about motive, and it is not in the Inference bullet (line 602).
- The documented reason is different and more instructive. Pre-standard compilers disagreed about the preprocessor, and the phases were written to settle which rule wins.

**Evidence.**
- C89 Rationale §2.1.1.2: "Perhaps the greatest undesirable diversity among existing C implementations can be found in preprocessing"; "The phases of translation are spelled out to resolve the numerous questions raised about the precedence of different parses. Can a #define begin a comment? (No.) Is backslash/new-line permitted within a trigraph? (No.) Must a comment be contained within one #include file? (Yes.)"
- The same section supports the section's half-truth: "The phases need not be performed in a separate preprocessor, although the definition certainly permits this common practice."
- Ritchie (chist): the preprocessor's "interaction with the compiler had never been well-described, and X3J11 attempted to remedy the situation."

**Fix.** Replace the first two sentences of line 32: "When the committee that wrote the first C standard (X3J11, 1983–1989) came to translation, it found compilers that disagreed, above all about the preprocessor: whether a comment could begin in one file and end in another, whether a backslash at the end of a line could join a line inside a comment, and so on. It settled such questions by listing eight **phases of translation** (C23 draft N3096, §5.1.1.2; …), and by defining each phase only by what it does to the output of the one before, so that no compiler's arrangement of programs was required." Then add the "why" box of D4, and cite the C89 Rationale in Sources.

**E3. Line 101: the stated purpose of phase 2 is wrong, and its action inside names is presented as an accident.**

**Problem.**
- "Its real purpose is to let a long preprocessing directive … be written over several. But phase 2 knows nothing about tokens, strings or comments…; it acts everywhere."
- The documented purpose included continuing *string literals* (the original use) and continuing any token, deliberately.
- The committee *generalized* splicing so that any token could be continued. That splicing works inside `printf` is a design decision, not a side effect of ignorance.

**Evidence.** C89 Rationale §2.1.1.2: "A backslash immediately before a new-line has long been used to continue string literals, as well as preprocessing command lines. In the interest of easing machine generation of C, and of transporting code to machines with restrictive physical line lengths, the Committee generalized this mechanism to permit any token to be continued by interposing a backslash/new-line sequence."

**Fix.** "Phase 2 does one thing: … **logical line**. It is older than the standard. Programmers used a backslash at the end of a line to continue a long string literal, and a long preprocessing directive, which must be a single line (§22.04 uses it for long macros). The committee that wrote the first standard deliberately extended it to every token, so that programs that write C programs, and machines whose lines had a fixed maximum length, could break a line anywhere (C89 Rationale, §2.1.1.2). Phase 2 therefore needs to know nothing about tokens, strings or comments, which do not exist yet; it acts everywhere." Listing 03.02-2's split string (line 7–8) is then the historical use, and the split `printf` is the generalization. Say so in the first bullet after the listing.

**E4. Self-check 1 (line 482) and its answer (line 550): conflates the standard's phases with compiler passes, contradicting the section's own lesson.**

**Problem.**
- The question asks "Why is translation divided into phases at all? Give two reasons, one historical and one that still holds."
- The answer gives the PDP-11's memory, a reason for *compiler passes*.
- The standard's *phases* (1989) were never divided for memory. They are a specification, and line 350 itself says "the standard's division and GCC's are different answers to different questions". A strong reader will lose a mark for the very confusion the section warns against.

**Fix.**
- Question: "Translation is divided twice: into the standard's phases and into a compiler's programs. Give the reason for each division, and say which reason was partly historical."
- Answer: "The standard's phases define which rule wins when two could apply to the same text (the C89 Rationale: to resolve 'the precedence of different parses'), without requiring any arrangement of programs. A compiler's division into programs is engineering. Each program has one job with a simple input and output, which makes it easier to write, test and reuse. Historically, in the author's understanding, it also let each pass fit the small memory of machines such as the PDP-11."

**E5. Line 344: wrong evidence for what `collect2` runs, and the `-plugin` arguments attributed to `collect2`.**

**Problem 1.** "…it in effect runs `ld` once, as the `-v` output shows." The `gcc -v` output shows only the driver's command for `collect2`. It does not show what `collect2` then runs, so it cannot show that `ld` runs once.
- To see it, give `collect2` its own `-v` through `-Wl,-v`. It then prints its version and the one `ld` command it runs, and `ld` prints its own version.
- This is also the natural way to keep the TOC's promise to show `collect2` and `ld` as separate programs.

**Problem 2.** "Its `-plugin` arguments serve link-time optimization." These are `ld` options that `collect2` passes through. The `ld` command line receives `-plugin …/liblto_plugin.so`, and the plugin is loaded into the linker.

**Evidence (workspace, gcc-14):**
```text
$ gcc-14 -Wl,-v hello.c -o hv2 2>&1 | head -3
collect2 version 14.2.0
/usr/bin/ld -plugin /usr/libexec/gcc/x86_64-linux-gnu/14/liblto_plugin.so -plugin-opt=... -o hv2 .../Scrt1.o ... /tmp/ccFyfbit.o -lgcc ... -lc ... .../crtn.o
GNU ld (GNU Binutils for Ubuntu) 2.42
```

**Fix.**
- Replace the parenthesis with: "(GCC's internals manual describes `collect2` as … linking the program twice. On GNU/Linux, whose linker and startup files already provide that service, it runs `ld` once. You can see this by giving `collect2` its own `-v`: `gcc -Wl,-v hello.c -o hello` makes it print its version and then the single `ld` command it runs. The `-plugin` arguments it passes on load GCC's link-time optimizer into `ld`; see below.)"
- Run on Fedora and show two or three lines of the output.
- In the Inference bullet, change "inferred from the `-v` output" to "from the `-Wl,-v` output".

## 2. Depth and teaching gaps

**D1. Lines 367–375, "Why this order, and no other": the §00.02 promise is argued, not shown. Make the relocation hole the centerpiece.** (Highest priority.)

**What is thin.**
- Reason 1 ("the output of each is the input of the next") is admitted at line 371 to depend on the chosen formats.
- Reason 2 states that linking needs everything, but never shows *what* in the compiled code waits for the linker.
- Reason 3 is good.
- The reader has already been shown the clue, `greet.c:(.text+0x5)` (line 320), and line 326 explains it only as "at offset 5 of the machine code, there is a reference". Offset 5 is not the call instruction, which is at 4. It is the *empty address field inside it*, which is the physical mechanism of separate compilation.
- The argument also never tests the alternatives, and that is what convinces a demanding reader.

**Evidence (workspace).** gcc-14 with `-fno-pie -fcf-protection=none` reproduces Fedora's `.text+0x5`. Ubuntu's default gives `+0x9` because of the 4-byte `endbr64`:
```text
$ objdump -dr greet.o
0000000000000000 <main>:
   0:	55                   	push   %rbp
   1:	48 89 e5             	mov    %rsp,%rbp
   4:	e8 00 00 00 00       	call   9 <main+0x9>
			5: R_X86_64_PLT32	greet-0x4
   9:	b8 00 00 00 00       	mov    $0x0,%eax
   e:	5d                   	pop    %rbp
   f:	c3                   	ret
```

The contrast case shows that the assembler resolves names *within* a file. Take `int f(int n){ int s = 0; for (int i = 0; i < n; ++i) s += i; return s; }`:
- `-S` shows `jmp .L2` and `jl .L3`, which are names, not distances.
- `objdump -d loop.o` shows `eb 0a  jmp` and `7c ee  jl`, with the distances filled in.
- `objdump -r loop.o` lists no relocation for `.text`.

**Proposed rewrite** (it replaces lines 369–373; keep the separate-compilation paragraph of line 375 after it, and add a `:::metal` box for the bytes if preferred):

> §00.02 promised an explanation of why `cc1`, `as` and `collect2` must run in exactly that order. "Each needs the previous one's output" is true, but it only moves the question: why were the outputs designed so that linking comes last? The answer lies in what each program *knows* when it runs, and `greet.o` lets you see it in the machine code. Ask `objdump` (§03.05) for the code, with `-r`, which also prints the notes the assembler left for the linker:
>
> [Fedora output of `objdump -dr greet.o`]
>
> The call to `greet` is the instruction at offset 4: the byte `e8`, "call", followed by four bytes that should hold the distance from the end of the instruction to `greet`. They hold zeros. The assembler did not know where `greet` would be, so it left a hole of exactly the right size and wrote a note beside it, the **relocation** printed on the next line: "at offset 5, put in the address of `greet`" (the `-0x4` and the name `R_X86_64_PLT32` are details for §03.05). This is the `.text+0x5` of the linker's message: the linker came to fill the hole at offset 5 and found nothing to fill it with.
>
> That hole holds the whole explanation of the order.
>
> **The declaration gives the compiler everything except the address.** From `void greet(void);`, `cc1` knows that the call passes no arguments and expects no result, so it can generate the call completely. Only the destination is unknown, and this form of `call` keeps its destination in four bytes, whatever it turns out to be. So translation can finish without the definition, which is why `gcc -c greet.c` succeeded.
>
> **Each program fixes what has become known by its time, and leaves a marked hole for the rest.** `cc1` does not even compute distances inside its own file. It writes `jmp .L2`, naming a label, and the assembler, which has the whole file in front of it, measures the distance and writes the bytes in (Experiment 03.02-7 shows a loop whose jumps leave no notes behind). What the assembler cannot know, an address in another file, it leaves as a hole with a note. The linker, which has all the files, fills those holes. And on Linux even the linker does not know where the C library will be in memory when the program runs, so for `puts` it leaves one more hole, which the dynamic loader fills at run time (the `U puts@GLIBC_2.2.5` of §03.01; §03.07). Each step leaves what it cannot know to the first step that can know it.
>
> **So linking must come last, because it is the first point at which every definition exists.** Phases 1 to 7 work on one translation unit and need nothing from any other. Only phase 8 has your object files, the startup files and the libraries together.
>
> Try the alternatives, and each one fails. Could the pieces be joined *first*, all the source files pasted together and translated at once? For your own files, yes. Some projects do it (SQLite is distributed as a single C file of its whole source, called the "amalgamation"). But the C library on your machine exists only as compiled code. Nobody gave you the source of `puts`, and you would not want to compile it again with every program. Something must combine *translated* pieces, so it must come after translation. Could the assembler come before the compiler? It has nothing to read until instructions have been chosen. Could the compiler fill in `greet`'s address itself? Only by seeing every other file, which would end separate compilation.

Then continue with the existing "**That arrangement is what makes separate compilation possible.**" paragraph.

Other changes that go with D1:
- Line 326 bullet: "…there is a reference to `greet`" becomes "…the linker was to write `greet`'s address into the machine code (why offset 5, and not the 4 at which the call begins, is shown under 'Why this order' below)".
- Add Experiment 03.02-7: "Jumps that the assembler resolves. Compile `int f(int n){ int s = 0; for (int i = 0; i < n; ++i) s += i; return s; }` with `-S` and with `-c`. Find the `jmp` in the `.s` file and in `objdump -d`, and run `objdump -r`. What did the assembler do with `.L2`, and why is there no note for the linker?"

**D2. Lines 332–344: the driver is described but not opened. Show its specs, its use of exit statuses and its temporary files.**

**What is thin.** "It … decides which programs to run, in what order and with what options." How it decides is exactly what a reader who will not accept black boxes asks next. Three cheap demonstrations answer it.

(a) **Specs.** The driver's decisions are rules in a small language, printed by `gcc -dumpspecs`. Workspace, gcc-14:
```text
*startfile:
%{!mandroid|tno-android-ld:%{shared:; pg|p|profile:...; static:crt1.o%s; static-pie:rcrt1.o%s; !no-pie:Scrt1.o%s; :crt1.o%s} crti.o%s %{static:crtbeginT.o%s; shared|static-pie|!no-pie:crtbeginS.o%s; :crtbegin.o%s} ...
```
This one rule explains the `crt1.o` / `Scrt1.o` difference that line 344 and the Sources bullet now report only as a fact. Fedora's rule may be written differently, so it must be run there.

For the AVR, `avr-gcc -v` prints `Reading specs from …/device-specs/specs-atmega328p`, and that text file contains:
```text
*cpp:
	-D__AVR_ATmega328P__ -D__AVR_DEVICE_NAME__=atmega328p
*asm_arch:
	-mmcu=avr5
```
That is the answer to line 452's unasked question of *how* the driver knows to pass `-D__AVR_ATmega328P__` and `avr5`. (Workspace, avr-gcc 7.3; avr-gcc 15.3 on Fedora must be checked, including the path.)

Proposed `:::hood` box after line 344:

> How does the driver know which programs to run and what to give each one? It follows rules called **specs**, written in a small language of its own, and it will print them: `gcc -dumpspecs`. The rule that chose the startup files is named `startfile`:
>
> [Fedora output, `gcc -dumpspecs | grep -A1 '^\*startfile:' | cut -c1-…`]
>
> Read `static:crt1.o%s; … !no-pie:Scrt1.o%s; :crt1.o%s` as "with `-static`, `crt1.o`; if the program is position-independent, `Scrt1.o`; otherwise `crt1.o`" (`%s` means "find this file in GCC's own directories"). That single rule is why Fedora's link line shows `crt1.o` and Ubuntu's `Scrt1.o`. The two drivers are the same program; they differ in one default. avr-gcc goes one step further: for each chip it reads a specs file of its own (`avr-gcc -v` prints `Reading specs from …/device-specs/specs-atmega328p`), and in that file, a few lines of text, are the `-D__AVR_ATmega328P__` it gave `cc1` and the `-mmcu=avr5` it gave `as`. The driver is not magic. It is a rule book you can read.

(b) **Exit statuses.** This is a direct link back to §03.01's lesson. Proposed sentence after line 326 or line 344: "How does the driver know when to stop? The same way the shell's `&&` did in §03.01. Each program it runs returns an exit status, and the driver runs the next only if the last succeeded. When `cc1` reports an error, `as` and the linker never run. Here `ld` returned 1; `collect2` reported it in the last line, and `gcc` itself then exited with status 1, which is how `make` (§21.08) learns that a build failed." The log shows `[exit 1]` for the link.

(c) **Temporary files.** Line 342 calls `/tmp/cc3BOgpy.s` temporary but never says it is deleted. That is the reason `-save-temps` exists (line 390). Proposed sentence at line 342: "…(the random part of the name differs on each run, and the driver deletes the file when it has finished; `-save-temps`, below, keeps it)". Optionally add to the hood box of line 364: "With `-pipe`, no file is written at all. The driver connects `cc1`'s output directly to `as`'s input, and the `as` command in `-v` has no input file name." Workspace, gcc-14 `-pipe -v`: `as -v --64 -o /tmp/ccOsv4Xa.o`, with no `.s` argument.

**D3. Line 342 and the TOC bullet "cc1, which also does the preprocessing": show it, and say since when.**

**What is thin.** "In modern GCC the preprocessor is built into `cc1`" is asserted. "Modern" is undated, and the history box shows `/lib/cpp` as a separate program in 1979 without connecting the two. GCC can still split the work into two runs of `cc1`, which makes the claim visible. Workspace, gcc-14:
```text
$ gcc-14 -no-integrated-cpp -v -std=c23 hello.c -o h 2>&1 | grep -E '/cc1 | as |collect2' | cut -c1-90

 /usr/libexec/gcc/x86_64-linux-gnu/14/cc1 -fpreprocessed /tmp/ccfJhoOe.i -quiet ...

 /usr/libexec/gcc/x86_64-linux-gnu/14/collect2 -plugin ...
```

Proposed text after the numbered list (line 344):

> That `cc1` also preprocesses was not always so. The Seventh Edition ran `/lib/cpp` as a program of its own (the history box above), and so did GCC until version 3.0 (2001) built its rewritten preprocessor into the compilers. Version 3.3 (2003) removed the separate preprocessors. You can still ask for the old arrangement:
>
> [Fedora output of the command above]
>
> Four commands now. `cc1 -E` carries out phases 1 to 4 and writes a temporary `.i` file. A second `cc1`, told `-fpreprocessed` ("phases 1 to 4 are already done"), carries out the rest of the translation. Then `as` and `collect2` run as before. The same program does both halves; joining them saves writing the whole of `stdio.h` out as text and reading it back.

Sources: GCC 3.0 "Features" ("Rewritten C preprocessor, integrated into the C, C++ and Objective-C compilers"); GCC 3.3 "Changes" ("The separate ISO and traditional preprocessors have been completely removed").

**D4. Line 30 onward: no "why" box, though the topic's "why" is documented. Add one built on the Rationale.**

The benchmarks each carry a `:::why` box (§03.01 line 62). §03.02 has none, although its first TOC bullet asks for the phases "explained intuitively", and the documented reasons are vivid. Proposed box after line 32 (together with E2):

> :::why
> Why does the standard describe translation as a list of phases at all? Not to describe a compiler. The Rationale the committee published with the 1989 standard says the phases "need not actually be present in the translator, but the net effect must be as if they were". The reason was disagreement. The preprocessor, the Rationale admits, had "accreted over time, with little central direction", and compilers gave different answers to questions such as: Can a `#define` begin a comment? May a backslash and newline appear inside a trigraph? Must a comment end in the same file it began in? (No, no and yes, the committee decided.) Its purpose fits in one sentence: the phases "are spelled out to resolve the numerous questions raised about the precedence of different parses". Ritchie, looking back, said the same thing from the other side: the preprocessor's "interaction with the compiler had never been well-described". So each phase is the settlement of an argument about which rule wins when two could apply to the same characters. Listing 03.02-3 shows one of them: joining lines wins over recognizing comments, because phase 2 comes before phase 3.
> :::

This also gives the `:::precise` box's phrase "order of precedence" (line 48) the explanation it lacks (I9).

**D5. Phase 3 (lines 161–163): "each comment is replaced by one space" is stated, but why one space, and not nothing, is not.**

**What is thin.** This is one of the clearest "why" cases in the chapter, and it can be demonstrated.
- Some pre-standard preprocessors deleted comments entirely, and programmers used `a/**/b` to glue names together. Ritchie calls such things "operations, like token concatenation, previously available only by accidents of implementation".
- The standard made a comment one space, so that a comment can never change where a token ends, and it gave pasting to an explicit operator, `##`.
- GCC can still imitate the old behavior. Workspace, gcc-14:
```text
$ cat old.c
#define CAT(a,b) a/**/b
int CAT(foo,bar) = 1;
$ gcc -E -P old.c
int foo bar = 1;
$ gcc -E -P -traditional-cpp old.c | grep -v '^$'
int foobar = 1;
```

Proposed paragraph after line 163: "Why one space, and not nothing? Because deleting a comment would join the tokens on either side of it, and some preprocessors before the standard did exactly that. Programmers exploited it, writing `a/**/b` to build the name `ab`. The standard made a comment one space, so that a comment can never change where a token ends, and gave the job of pasting tokens to an explicit operator, `##` (Chapter 22). GCC keeps an imitation of the old behavior, `-traditional-cpp`, and the difference shows in two lines: [listing/terminal/output]." Sources: GCC preprocessor manual, "Traditional macros" ("an example of using a comment to effect token pasting"); Ritchie, chist ("previously available only by accidents of implementation").

**D6. Lines 165 and 187: the reason given for the greedy preprocessing-number rule is incomplete. The committee's own reason is deeper and can be demonstrated.**

**What is thin.** "The preprocessor must cut numbers out of the text without knowing all of C's rules for numbers…" That is part of the story. WG14's answer to Defect Report #003, which asked exactly whether pp-numbers were "too inclusive", gives two more reasons:
- "Garbage" sequences that begin like a number were meant to be one token, so that they cannot be turned into valid C "through obscure macro replacements".
- The simple grammar leaves room for future kinds of constant.

The C89 Rationale §3.1.8 even uses this section's example in the form `0x123E+1`, and accepts it as a known anomaly. Both points can be shown. Workspace, gcc-14:
```text
$ cat mac.c
```

**D8. Phase 5 (line 197): why there are two character sets is not explained, and phase 5 is never seen doing anything.**
