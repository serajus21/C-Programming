# Review of §02.02 "The Design Philosophy of C"

Method: every listing rebuilt with gcc-14 (14.2.0, `-std=c23`), avr-gcc 7.3.0 + avr-libc, avr-g++ 7.3.0, and run on simavr (ATmega328P, 16 MHz) with the two harnesses; all output blocks diffed character by character against the text; all Self-check and Experiment answers redone; WG14 N2611 and N3280 read; C23 draft N3096 checked for `<limits.h>`; gcc-mirror `xtensa.h`/`avr.h` checked; Spencer's 1986 Usenet post and ESA's RTEMS pages checked. Scratch files are in /tmp/r0202.

Severity: H = a careful reader learns something false; M = misleading or incomplete in a way that matters; L = minor.

## 1. Errors

**E1. Lines 24, 350, 637; Table 02.02-2; Figure 02.02-3. Category: B/C. Severity H.**
**Problem:** "`printf` cost 1,356 bytes of the Uno's flash"; "Calling `printf` adds 1,356 bytes more"; Self-check 8: "raised the program from 374 to 1,730 bytes".
**Evidence:** 1,356 = STEP 2 − STEP 1. But STEP 2 is not STEP 1 plus `printf`. STEP 1 contains code that STEP 2 does not: `avr-nm lc1.elf` shows libgcc's `__divmodhi4` (40 bytes) and `__udivmodhi4` (40 bytes), pulled in by `n % 10`. `avr-nm lc2.elf` shows neither. Measured against STEP 0, the build with no output, `printf` costs 1,730 − 276 = **1,454** bytes of text (1,458 bytes counting .data). The "+" labels in Figure 02.02-3 ("+ the library's printf, integers") wrongly suggest that each build adds to the one before.
**Fix:** "...`printf` cost about 1,450 bytes..." (line 24). Line 350: "Compared with STEP 0, calling `printf` adds 1,454 bytes, because..." Self-check 8: "from 276 bytes (STEP 0) to 1,730". In the figure, remove the "+" or label each bar "STEP n alone".

**E2. Lines 313, 350; Figure 02.02-3 label. Category: B/D. Severity H.**
**Problem:** "`uart_putchar(...)`; // our own code, no library function" and "Sending one character with our own five-line function adds about 100 bytes."
**Evidence:** `uart_putchar` (18 bytes) is already in STEP 0, because `stdout = &uart` refers to it. Line 324 says it is "present in all four versions". The +98 bytes of STEP 1 are 80 bytes of libgcc's 16-bit division routines (`__divmodhi4`, `__udivmodhi4`) for `n % 10`, plus 18 bytes of extra code in `main`. So the comment "no library function" is false: the build calls a compiler support library routine, though not a C standard library function.
**Fix:** Comment: "// our own code; % calls libgcc's division routine". Text: "STEP 1 adds 98 bytes, and 80 of them are not ours: the AVR has no divide instruction, so `n % 10` calls `__divmodhi4`, a routine from GCC's support library libgcc (`avr-nm lc1.elf` shows it). Even an operator can bring in library code."

**E3. Line 325. Category: D. Severity M.**
**Problem:** "volatile ... so it cannot compute the printed text while compiling and leave `printf` out".
**Evidence:** GCC never evaluates a `printf` format at compile time. With `volatile` removed, STEP 2 still links `vfprintf` (1,682 bytes) and STEP 3 still links it (1,702 bytes). The only build in which `volatile` really matters is STEP 1. Without it, `'0' + n % 10` is folded to the constant `'2'` and no division routine is linked (236 bytes instead of 374).
**Fix:** "...declare two variables `volatile`, which forces the compiler to read them from memory at run time, so that the work of converting them is really done by the program rather than folded into constants while compiling (§36.04)." Better still, connect this to E2.

**E4. Line 350. Category: B/D. Severity M.**
**Problem:** "Even the empty program occupies 276 bytes: the table of interrupt vectors ... and the short start-up code that prepares memory and calls `main`."
**Evidence:** STEP 0 is not empty. `avr-nm -S lc0.elf` breaks the 276 bytes into: vectors 104; start-up code (`__do_copy_data`, `__do_clear_bss`, init and `__bad_interrupt`) 62; `main` 88 (UART setup and the stores of `n` and `x`); `uart_putchar` 18; `_exit` 4. A truly empty `int main(void){}` built with the same options is 138 bytes.
**Fix:** "STEP 0 already occupies 276 bytes: 104 for the table of interrupt vectors, about 60 for the start-up code that prepares memory and calls `main` (§36.05), and about 110 for our UART set-up and `uart_putchar`. A program whose `main` is empty takes 138."

**E5. Lines 336, 338 (Table 02.02-2 caption). Category: D. Severity M.**
**Problem:** "The `text` column of `avr-size` (program code and constants in flash)"; "Flash used by Listing 02.02-4".
**Evidence:** On the AVR, string literals and other initialized data go into `.data`. That section is stored in flash and copied into RAM at start-up. For example, `lc2.elf` has data = 18 bytes: the 14-byte `FILE uart` plus `"%d\n"`. So the flash actually used is text + data: 290, 388, 1,748, 1,764 and 3,236 bytes. Format strings therefore also cost scarce SRAM, which is a fact a Uno programmer needs.
**Fix:** "The `text` column (code and read-only tables). Flash also holds the `data` column, the initial values of variables and, on the AVR, every string literal, which start-up code copies into RAM. Here `data` is only 14 to 24 bytes, so `text` is a fair measure." Retitle the table "Code size (`avr-size` text)".

**E6. Lines 100, 625. Category: D. Severity M.**
**Problem:** "The standard requires an `int` to hold at least −32,767 to +32,767".
**Evidence:** That is the C89–C17 minimum. C23, the book's baseline, requires two's complement. N3096 5.2.4.2.1 gives `INT_WIDTH` a minimum of 16 and defines the `_MIN`/`_MAX` macros as −2^(N−1) and 2^(N−1)−1, so the minimum range is −32,768 to +32,767. The Sources (line 673) cite exactly this C23 subclause.
**Fix:** "C23 requires an `int` at least 16 bits wide, so able to hold −32,768 to +32,767 (earlier standards, which still allowed other sign representations, said −32,767)." Make the same change in Self-check 2's answer.

**E7. Lines 35, 37. Category: D. Severity M.**
**Problem:** "A C expression should never hide a loop or a call to a large routine." "Nothing runs that the programmer did not write."
**Evidence:** This section itself refutes both. `n % 10` calls `__divmodhi4` (E2). `a << n` with a variable `n`, compiled for the AVR, becomes a loop (`add`/`adc`/`dec`/`brpl`). A `long` multiplication calls `__mulsi3`. All floating point on the AVR is library calls. Start-up code (line 350, §36.05) runs before `main`. `<<` is even named in item 2.
**Fix:** Item 2: "...correspond closely to what processors do. Where the processor lacks an operation (division or a variable shift on the AVR), the compiler emits a short loop or calls a small support routine, but only for an operator you wrote." Item 4: "No hidden work beyond what the operation itself requires: no checks inserted behind your back, no memory reclaimed behind your back."

**E8. Lines 267–269, 635. Category: D. Severity M.**
**Problem:** "a garbage collector must be able to ... tell which words are pointers ... That requires the type of every value to be known at run time ... Every one of these requirements conflicts with C's design". Self-check 7: "a collector could not tell pointers from other data".
**Evidence:** Conservative collectors work with C, with no type information, by treating every word that could be an address as one. The Boehm–Demers–Weiser collector (bdwgc, used for years by GNU Guile and others) is the standard example. What C rules out is a *precise* collector, and any collector built *into the language*.
**Fix:** "A *precise* collector must know which words are pointers... C values carry no such information. A *conservative* collector, such as the Boehm collector, can still be linked into a C program: it treats any word that looks like an address as a pointer, so it sometimes keeps garbage alive. But it remains an optional library, and it still pauses the program at moments the program does not choose." Adjust Self-check 7 to match.

**E9. Lines 529, 651 (Experiment 02.02-1 answer). Category: B. Severity M.**
**Problem:** The experiment asks the reader to rerun *both* sanitizer builds with `checksum` first. The answer reports the unsanitized build and ASan, and says nothing of what `-fsanitize=bounds` does.
**Evidence:** With `checksum` first, GCC 14.2 `-O0 -fsanitize=bounds` prints only `checksum = 1234` and **no runtime error**. A trailing array member is treated as a possible flexible array member (`-fstrict-flex-arrays=0` is the default), so it gets no bound. With `-fstrict-flex-arrays=1`, `2` or `3`, the report `ov2.c:11:16: runtime error: index 4 out of bounds for type 'int [4]'` returns. The reader will see a silent bounds sanitizer even though the array's size is "visible in its type", which contradicts the box at line 192 with no explanation.
**Fix:** Add to the answer: "`-fsanitize=bounds` now reports nothing: GCC assumes that an array at the *end* of a structure may be an old-style variable-length 'flexible' array, and does not check it. `-fstrict-flex-arrays=3` restores the check (Chapter 28)." In the hood box, add "...visible in its type (unless the array is the last member of a structure)".

**E10. Line 540 (Experiment 02.02-3). Category: B. Severity M.**
**Problem:** "Compile ... `-c`, and search each disassembly for calls to a function whose name contains `ubsan`."
**Evidence:** In an unlinked object, `objdump -d ovs.o` shows only `call 32 <store+0x32>`. The name `__ubsan_handle_out_of_bounds` appears only with `objdump -dr` (the relocation), with `nm`, or in `gcc -S` output. Following the book's usual `objdump -d`, the reader finds "ubsan" in neither file.
**Fix:** "...and run `objdump -dr` on each (the `-r` shows the names of called functions the linker has yet to fill in, §02.01), then search for `ubsan`."

**E11. Lines 9–14. Category: B. Severity L.**
**Problem:** "Run this on your laptop and you can see it in four lines".
**Evidence:** The block has two lines and is not a program. It cannot be run as shown.
**Fix:** "Here is the whole idea in two lines (Listing 02.02-2 makes it a program you can run):".

## 2. Likely errors

**L1. Lines 538, 653 (Experiment 02.02-2). Category: B. Severity M.**
**Problem:** "Which C operation costs one instruction on x86-64 but two on the AVR". The answer gives only `int` addition.
**Evidence:** Measured: `fetch` (`*p`) is also 1 on x86-64 (`movzbl`) and 2 on the AVR (`movw`, `ld`). The pointer must first be copied into Z, because only X/Y/Z can address memory, whereas x86-64 can use any register as a base. (`mask` goes the other way: 2 on x86-64, 1 on the AVR.)
**Fix:** Ask "Which C operations..." and answer: "`a + b` (16-bit `int` done a byte at a time with a carry) and `*p` (the AVR must first move the address into its pointer register Z; x86-64 can use any register as an address)."

**L2. Line 24. Category: C. Severity M.**
**Problem:** "You will see ... your ESP32 disagree with your laptop about whether a character can be negative."
**Evidence:** Lines 455, 607 and 670 state that the ESP32 was not run. That outcome is a prediction from `xtensa.h` (`DEFAULT_SIGNED_CHAR 0`, confirmed in GCC source).
**Fix:** "...and see why your ESP32 is expected to disagree with your laptop..."

**L3. Lines 150 vs 192. Category: D. Severity M.**
**Problem:** "It does not, and in C cannot be made to automatically, check that `i` is between 0 and 3."
**Evidence:** Line 192 and the run show that `-fsanitize=bounds` inserts exactly that check into `store` (the run reports `overrun.c:11:16`).
**Fix:** "C does not check that `i` is between 0 and 3; nothing in the language requires it (a compiler option can add a check here, as the box below shows)."

**L4. Line 285. Category: C. Severity M.**
**Problem:** "This was a deliberate break with the languages of §02.01 ... C took a third path".
**Evidence:** C inherited input and output through library routines from BCPL (`wrch`, `rdch`, `writef`) and B, whose library already had a `printf`. ALGOL 60 received standard I/O procedures in IFIP's 1964 report. What was new in C89 was a *standardized* library that every hosted implementation must supply.
**Fix:** "C kept the approach of BCPL and B: input and output are ordinary library functions, not statements. What the 1989 standard added was a library defined once, which every hosted implementation must supply in the same form."

**L5. Lines 354, 503. Category: D. Severity M.**
**Problem:** "On a machine with no operating system ... the standard calls such an environment **freestanding**"; Terms: "Freestanding implementation: an implementation without an operating system".
**Evidence:** Freestanding is defined by what the library must provide and by how the program starts, not by the absence of an operating system. avr-gcc for the bare ATmega328P defines `__STDC_HOSTED__` as 1 (checked with `avr-gcc -dM -E`), and avr-libc supplies `printf`. §02.06's TOC bullets (`__STDC_HOSTED__`) will expose the conflict.
**Fix:** Terms: "an implementation that need provide only a small part of the library (a few headers) and in which program start-up is implementation-defined; typical of, but not the same as, running without an operating system (§02.06)." Make the matching change at line 354.

**L6. Lines 275, 481. Category: D. Severity L.**
**Problem:** "A program with no allocation in flight cannot run out of memory in flight"; "prove ... cannot ... run out of memory in flight".
**Evidence:** Banning heap allocation bounds only the heap. The stack can still overflow, which is why Holzmann's rule 1 forbids recursion and why §35.04 does static stack analysis.
**Fix:** "...cannot exhaust its heap in flight...; with recursion also forbidden (another of the rules), the stack can be bounded too (§35.04)."

**L7. Lines 257 vs 677. Category: C. Severity L.**
**Problem:** The body says "roughly a quarter". The Sources say "the estimate that a check adds 'a quarter to a third'". The Sources also list as inference "the statement that ARM and Xtensa chose unsigned `char` for reasons like the PDP-11's", but the body never makes that statement.
**Fix:** Align the two estimates (3 of 11 instructions is 27%, so "roughly a quarter"). Either add the ARM/Xtensa reasoning to the body (see I8) or delete it from the Sources.

**L8. Lines 260, 633 (Ariane 5). Category: C. Severity L.**
**Problem:** "the check raised an exception that nothing handled".
**Evidence:** The Inquiry Board report says that, by specification, *any* exception was to be signalled on the databus, its context stored in EEPROM, and the SRI processor shut down. The exception had no local handler, and the system-wide response, shutdown, was carried out as designed. The book's own next sentence ("what failed was the engineering decision about what to do when the check fired") depends on this.
**Fix:** "...and the check fired. That conversion had no handler of its own, so the system-wide rule for any exception applied: report the failure and shut the processor down. Both inertial reference units, running identical software, did exactly that."

**L9. Line 352. Category: C. Severity L.**
**Problem:** "This is also why the Arduino environment provides its own `Serial.print` rather than `printf`: a lighter ... set ..., also written in C++".
**Evidence:** No source is given for the causal claim, and the Sources do not mark it as inference. "Also written in C++" implies that `printf` is C++, but avr-libc's `printf` is C and assembly.
**Fix:** "The Arduino environment, for its part, offers `Serial.print`, a set of printing functions written in C++ and likewise linked only if used." Drop "This is why", or mark it as inference.

## 3. Improvements

**I1. Line 95. Category: D.** "the AVR has no faster way". The AVR's `lsl Rd` *is* `add Rd,Rd`: the same opcode (0x0F88 here), which is why the disassembler prints `add`. Suggested wording: "...(the AVR's 'logical shift left', `lsl r24`, is literally this instruction under another name)".

**I2. Line 189. Category: D.** "rearranged the loop on that assumption; the fifth store simply did not happen where the literal reading puts it" is vague. Measured with `gcc-14 -O2 -S`: `main` contains no loop and no stores, only `movl $1234, %edx` and the call to `printf`. Say so, and suggest `gcc -O2 -S overrun.c` to see it. Also note that GCC counts iterations from 0 ("iteration 4" = the fifth).

**I3. Line 324. Category: B.** "Lines 6–12 are the serial-port connection". The connection also includes lines 15–17, the UART set-up and `stdout = &uart`.

**I4. Lines 187, 425. Category: B.** The AVR runs of Listings 02.02-2 and 02.02-5 show no build command, and the harness is not in the book, so the reader cannot reproduce them. Point to Listing 02.01-5's `#ifdef __AVR__` lines as the way to do it. Also add §02.01's note that simavr's coloring and trailing `.`/line endings are omitted; this section has no such note.

**I5. Table 02.02-2, line 343. Category: B.** "Prints `2`" is true on hardware. Under simavr nothing appears, because no newline is sent and simavr prints UART output line by line. Add "(on simavr, nothing appears until a newline)" or send `'\n'` too.

**I6. Lines 348, 546. Category: A.** Figure 02.02-3 is never referenced in the text. Listing 02.02-6 is referenced by number only in the Sources. Add "(Figure 02.02-3)" after "Read it from the top" and "this program (Listing 02.02-6)" in Experiment 02.02-5.

**I7. Lines 116, 118, 285. Category: D.** Terms are used before they are defined: "sanitizers" and "Annex K" (line 116), "undefined behavior" (line 118, defined at 189), "hosted" (line 285). Gloss Annex K as "optional bounds-checked library functions such as `strcpy_s`", and note that it is optional and that glibc does not provide it, since the reader may try it.

**I8. Line 440. Category: D.** Make the first-principles link explicit. Xtensa's only byte load is `L8UI`, which zero-extends (there is no `L8SI`). Early ARM's `LDRB` also zero-extended. This is the PDP-11 argument reversed, and it is what the Sources line 677 claims the text says.

**I9. Line 285–287. Category: D.** "joined to your program only if you call them" holds for static linking, as on the Uno. On the laptop, `printf` lives in the shared `libc.so`, which is mapped into every process whether called or not. One sentence would prevent a wrong generalization.

**I10. Table 02.02-4, line 469. Category: D.** "old code still compiles" is too strong for a C23-baseline book. C23 removed K&R-style function definitions and changed the meaning of `int f()`. GCC 14 made implicit function declarations errors. The reader's GCC 16 defaults to gnu23. Suggested wording: "most old code still compiles".

**I11. Line 100. Category: C.** "It produces smaller, faster code". The GCC manual says only smaller code. Consider adding that avr-libc is not built for `-mint8`, so it is impractical with the standard library.

**I12. Line 270. Category: D.** "a bare chip with 2 KB of memory" should be "2 KB of RAM (and 32 KB of flash)".

**I13. Line 360. Category: C.** "Programmers who knew Ritchie later reported..." The cited source is one hedged post: Spencer, comp.lang.c, 23 April 1986, "I believe Dennis has said that he now regrets the concession to the hardware...". Suggested wording: "One C expert, Henry Spencer, recalled that Ritchie regretted..." "But the choice had been the machine's, not his" is the author's gloss.

**I14. Line 278. Category: C.** "systems that ran for decades in space and in medical devices" has no source. Name one example or soften it to "for many years".

**I15. Line 257. Category: D.** Mention code-size cost too. The check adds 3 instructions to the executed path but 6 instructions to the code (16 → 28 bytes), counting the `return 0` path.

**I16. Lines 32, 47, 358. Category: D.** "Demand" means both the two masters (line 32, "each demand") and the six list items ("demand 2", "the sixth demand"). Call the six items "requirements" or "design decisions".

**I17. Lines 9, 30. Category: A.** "§02.01 followed C from B" understates: §02.01 starts at FORTRAN, COBOL, ALGOL, CPL and BCPL. "§02.01 ended with C serving two masters" does not match its actual ending, which is the "quirky, flawed, and an enormous success" passage and four lessons. Suggested wording: "§02.01 showed C serving two masters".

**I18. Line 675 vs line 649 and §02.01.** Use one form of Holzmann's title throughout ("Power of 10" vs "Power of Ten").

**I19. Line 669.** The Sources should also list the x86-64 runs behind Experiment 02.02-2 and the line 257 claim about the laptop's three-instruction check.

**I20. Line 673.** "deprecated alternative spellings such as `_Bool`": C23 calls these "alternative spellings". Line 283's wording is already correct.
