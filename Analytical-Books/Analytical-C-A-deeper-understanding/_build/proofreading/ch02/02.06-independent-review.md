# Review of §02.06 "Hosted and Freestanding Implementations"

Line numbers refer to /home/claude/review0206/target/02.06.md. All commands were re-run with gcc-14 (14.2.0, Ubuntu 24.04, glibc 2.39), binutils, avr-gcc 7.3.0 + avr-libc 2.0.0, simavr, and the supplied core.a. Scratch: /tmp/r0206/b.

## 1. Errors

**E1. Line 52, C (fact), medium.**
**Problem:** "`<stdbit.h>` ... operations on bits: counting, rotating, finding the leading one".
**Evidence:** C23 (N3096) §7.18 has only the endian macros, leading/trailing zeros/ones counts, first leading/trailing zero/one, count zeros/ones, single-bit check, bit width, bit floor and bit ceiling (7.18.1–7.18.16). It has no rotate. glibc 2.39's /usr/include/stdbit.h has no rotate either. Rotations (`stdc_rotate_left/right`) were added after C23 (C2y).
**Fix:** "operations on bits: counting zeros and ones, finding the first or leading one, bit width, the byte order of the machine".

**E2. Line 49, C/D, low–medium.**
**Problem:** The C23 table gives the contents of `<stdbool.h>` as "type names and macros: ... `bool`".
**Evidence:** In C23, `bool`, `true` and `false` are keywords. `<stdbool.h>` keeps only the obsolescent macro `__bool_true_false_are_defined` (§7.19). §02.05 teaches `bool` as a C23 keyword (promise to §05.05). The same applies to `<stdalign.h>`, since `alignas`/`alignof` are now keywords. `uint8_t` is also optional (exact-width types).
**Fix:** "`<stdint.h>`, `<stddef.h>`: type names and macros (`uint8_t` where the machine has 8-bit bytes, `size_t`, `NULL`); `<stdbool.h>`: since C23 nearly empty, because `bool`, `true` and `false` became keywords".

**E3. Lines 58 and 118, C/D, medium.**
**Problem:** "This is why bare-metal code and operating-system kernels are compiled with `-ffreestanding`". Line 58 also says "An operating-system kernel, such as Linux itself, is compiled as a freestanding program".
**Evidence:** In current Linux master, `-ffreestanding` appears only in arch/x86/Makefile `REALMODE_CFLAGS` (16-bit boot code) and in arm/arm64 `CC_FLAGS_FPU` (NEON units). The main x86-64 and arm64 kernel is compiled without it (it uses `-nostdinc`). The top Makefile adds only `-fno-builtin-wcslen`. The kernel deliberately keeps GCC's built-in knowledge of `memcpy` and similar functions. GCC's manual does call a kernel a program in a freestanding *environment*, and that part of the text is correct.
**Fix (118):** "This is why much bare-metal code is compiled with `-ffreestanding`. Linux, interestingly, is not: it supplies its own headers (`-nostdinc`) and its own `memcpy`, and keeps GCC's built-in knowledge of them on purpose." **Fix (58):** "An operating-system kernel, such as Linux, runs in a freestanding environment (GCC's manual's own example), even though..."

**E4. Line 199, D, medium.**
**Problem:** "The whole program is 173 bytes of code."
**Evidence:** `readelf -S bare` shows `.text` = 0x23 = **35 bytes**. `size`'s "text" column adds up every read-only allocated section: .note.gnu.property 32 + .note.gnu.build-id 36 + .text 35 + .rodata (the message) 26 + .eh_frame 44 = 173.
**Fix:** "`size` counts 173 bytes of read-only contents: 35 bytes of instructions, the 26-byte message, and about 110 bytes of notes and unwinding tables that GCC adds. The static build of Listing 02.06-1 has 680,006 bytes in the same column."

**E5. Lines 258, 261–262 (and 235), D, medium.**
**Problem:** "Read it as a list of everything C needs that the hardware does not provide at reset", applied to clearing SREG and setting SP to 0x08FF.
**Evidence:** On the ATmega328P a hardware reset already clears SREG (initial value 0x00) and loads SPH/SPL with RAMEND (datasheet, "Stack Pointer": initial value RAMEND). The startup code sets them again for two reasons. First, address 0 can be reached without a hardware reset: `__bad_interrupt` is literally `jmp 0` (line 235), and a bootloader or debugger can also jump there. Second, avr-libc's crt is generic across AVRs whose SP resets to 0. Only r1 (the register file is not initialized) and .data/.bss are truly missing after a power-on reset. Line 235's "jumps back to 0 and restarts the program" is a software restart in which peripherals keep their state.
**Fix:** "Read it as a list of what C needs to be true before main, whether the chip has just been reset or code has simply jumped to address 0. On the ATmega328P a hardware reset already clears SREG and sets SP to the top of SRAM, but the startup code does not rely on that. `__bad_interrupt` reaches address 0 by a jump, not a reset, and older AVRs reset SP to 0." At 235: "...which jumps to 0 and runs the startup code again. This is not a reset: the peripherals keep their settings."

**E6. Lines 235, 320, 340, 395, 518 (and answer 528), C, medium.**
**Problem:** "the startup code, which avr-libc supplies for every program". Table: "avr-libc's startup code". Self-check 10: "avr-libc's startup code does".
**Evidence:** The link map (`-Wl,-Map`) shows `.vectors`, `.init2` (r1, SREG, SP) and `.init9` (call main / jmp exit) come from avr-libc's `crtatmega328p.o`. `.init4` `__do_copy_data` comes from **libgcc.a(_copy_data.o)**, `__do_clear_bss` from **libgcc.a(_clear_bss.o)**, and `_exit`/`__stop_program` from **libgcc.a(_exit.o)**. The avr-libc manual ("Memory Sections", .init4) says the same. The mechanism behind Experiment 02.06-3 is that the compiler writes `.global __do_copy_data` / `.global __do_clear_bss` into the assembly of any file that has .data/.bss (verified with `-S`), and the linker then extracts those pieces from libgcc.
**Fix (235):** "...the startup code, assembled by the linker from avr-libc's start file (the vector table, r1, SREG, the stack pointer, the call to main) and from GCC's support library libgcc (the copy and clear loops, `_exit`)". Table row: "vector 0, then the startup code (avr-libc + libgcc)". Answer 528: "...the compiler marks each file that has initialized or zeroed variables with a reference to `__do_copy_data` or `__do_clear_bss`, and the linker takes those loops from libgcc only when referenced."

**E7. Line 294 (metal box), D, medium.**
**Problem:** "vfprintf(stdout, ...), whose first act is to check the stream's flags..." and "A different register value would have made printf write through a stream at address 0, into the registers."
**Evidence:** Disassembly of noout.elf at `vfprintf`: `movw r6,r22` (format pointer), then `std Z+7, r1`, `std Z+6, r1` (`stream->len = 0`), *then* `ldd r24, Z+3` / `sbrs r24,1` (`__SWR`). With Z = 0, the program has already written 0 into data addresses 6 and 7, which are registers r6 and r7, before it checks the flags. It writes into registers whatever r3 holds. The offset-3 / r3 / bit-1 explanation of the −1 is correct.
**Fix:** "...whose first acts are to zero the stream's character count (offsets 6–7) and then check its flags (offset 3) for permission to write. With `stdout` null, the first act wrote zeros into data addresses 6 and 7, which are registers r6 and r7. The second read address 3, register r3... Had r3's 'may write' bit been set, printf would have gone on to read and call through the rest of a 'stream' made of registers."

**E8. Lines 454 and 470, D, medium-high.**
**Problem:** "`Serial.flush()` waits until every character has left, because the program then stops in an endless loop." Also: "the core's serial code sends characters by polling when interrupts are off."
**Evidence:** An endless loop does not stop transmission when interrupts are on: normal.ino's empty `loop()` runs forever and its output completes through the UDRE interrupt. In ownmain, interrupts are off because `init()` never ran `sei()`. HardwareSerial.cpp polls only when the 64-byte ring buffer is full (`write`) or inside `flush()`. Test: ownmain without `flush()` printed nothing under simavr. A variant printing 9 lines without flush printed only the first ~25 characters. The last ≤63 characters stay in the buffer forever.
**Fix (454):** "Line 12, `Serial.flush()`, is essential here. With interrupts off, the core sends a buffered character only when the 64-byte buffer is full or while `flush()` is waiting, so without it the last characters (up to 63) would never leave." **(470):** "...and because, with interrupts off, the core's serial code sends from its buffer by polling, but only when the buffer is full or inside `flush()`."

**E9. Line 320, D, medium.**
**Problem:** "So on an Uno, the chain from reset is: vector 0, avr-libc's startup code, Arduino's main..."
**Evidence:** The Uno ships with Optiboot. boards.txt has `uno.bootloader.high_fuses=0xDE`: BOOTRST is programmed and the boot section is 256 words, so every reset starts at the bootloader (byte address 0x7E00), which then jumps to address 0. The ESP32 discussion counts its bootloaders, so omitting the Uno's is inconsistent. "Bare ATmega328P" (Table, line 205) is correct for a chip with BOOTRST unprogrammed.
**Fix:** "So on an Uno, the chain from reset is: the Optiboot bootloader (the Uno's fuses make reset start there, so that it can accept an upload), then vector 0, the startup code, Arduino's main..." Add to the Table ATmega column: "(on an Uno, Optiboot runs first)".

**E10. Line 514 (also 124 and question 393), D, medium.**
**Problem:** Self-check 8: "The kernel starts the entry point, `_start`". Line 124: entry point = "the address where the kernel starts executing it".
**Evidence:** `life` is a dynamically linked PIE (`-dynamic-linker /lib64/ld-linux-x86-64.so.2` in `gcc -###`). The kernel starts the interpreter `ld.so` at *its* entry point. `ld.so` loads libc and then jumps to the program's `_start`. The text's own line 151 and Table 02.06-2 ("kernel, then ld.so, then _start") say this, so Self-check 8 contradicts them. Only the static `bare` is entered by the kernel directly.
**Fix (124):** "...records an entry point: the address at which its own code begins." **Answer 514:** "The kernel loads the program and the dynamic loader and starts `ld.so`. After loading the C library, `ld.so` jumps to the program's entry point, `_start`, from a startup file..."

**E11. Line 453, D, low–medium.**
**Problem:** "With the sketch's own `main`, Arduino's `main`, and therefore `init()`, never become part of the program."
**Evidence:** `init()` lives in wiring.c.o, not main.cpp.o. wiring.c.o *is* extracted, because the sketch calls `millis()`. Linking ownmain.o without `--gc-sections` puts `T init` at 0xcb6 in the ELF. It disappears only because the IDE compiles with `-ffunction-sections` and links with `--gc-sections`, which drops the unreferenced `.text.init`. With the IDE's options the observable claim holds, but the reason given is wrong.
**Fix:** "...Arduino's `main` never becomes part of the program. So nothing calls `init()`. Its code, in wiring.c, is pulled in with `millis()` but then discarded by the linker's `--gc-sections`, because nothing refers to it."

**E12. Line 328 vs 381 (cross-reference), A, low.**
**Problem:** "a FreeRTOS **task** (an independently scheduled thread of execution, §38.01)".
**Evidence:** In the TOC, §38.01 is "Threads and Data Races" (`<threads.h>`, pthreads). FreeRTOS tasks are §38.03 "Tasks on the ESP32 with FreeRTOS".
**Fix:** "§38.03".

**E13. Line 372 (Terms) and Self-check 7 / line 118, D, low–medium.**
**Problem:** "`-ffreestanding`: ... making no assumptions about functions with library names."
**Evidence:** This contradicts the box at line 58 (GCC requires memcpy/memmove/memset/memcmp). Test: with `-O2 -ffreestanding`, a 100,000-byte struct assignment compiles to `call memcpy@PLT`. With `-ftree-loop-distribute-patterns` (default at -O3 in hosted builds), a zeroing loop becomes `jmp memset@PLT`. The option stops GCC from *recognizing* library names as built-ins (`-fno-builtin`). It does not stop GCC from *assuming* `memcpy`/`memset` exist and behave as specified.
**Fix:** "...asserting a freestanding environment: `__STDC_HOSTED__` becomes 0 and GCC stops treating calls to functions with library names (`printf`, `strlen`) as the library's functions. GCC still expects `memcpy`, `memmove`, `memset` and `memcmp` to exist, and may call them itself."

**E14. Figure 02.06-1, ESP32 column, E, low.**
**Problem:** The box reads "FreeRTOS scheduler starts; the main task is created".
**Evidence:** The text (line 328) and ESP-IDF "Application Startup Flow" say the main task is created and then the scheduler is started. The figure reverses the order.
**Fix:** "the main task is created; the FreeRTOS scheduler starts". Also, in the Linux column, "_exit system call" should be "exit_group system call" (see I10).

## 2. Likely errors

**L1. Lines 205, 409, 532, B/C, medium.**
**Problem:** "vector 0, is the reset". Experiment 02.06-5 asks the reader to compare with the datasheet table; its answer says "Vector 0 is RESET".
**Evidence:** The ATmega328P datasheet table ("Reset and Interrupt Vectors") numbers RESET as **Vector No. 1**, INT0 as 2 and INT1 as 3. Its "Program Address" column is in 16-bit words (INT0 at 0x0002, INT1 at 0x0004), while avr-objdump shows byte addresses (0x4, 0x8). A reader doing the experiment will find no "vector 0" and addresses that differ by a factor of 2.
**Fix:** At 205: "...of which the first, at address 0, is the reset (the datasheet numbers it vector 1; avr-libc's names count from 0)". In the experiment, add: "Note that the datasheet numbers vectors from 1 and gives addresses in words, so its 0x0002 is objdump's 0x4." Answer: "The first entry (datasheet vector 1) is RESET; the next two are INT0 and INT1."

**L2. Lines 120 and 297, D, medium.**
**Problem:** avr-gcc "reports 1 because its library tries to be as complete as a chip without devices allows". `__STDC_HOSTED__` is "a statement by the implementation about the promises it intends to keep".
**Evidence:** GCC defines `__STDC_HOSTED__` from `-fhosted`, which is the default on every target unless `-ffreestanding` is given (GCC manual, C Dialect Options). Neither avr-gcc nor avr-libc decides it from the library's completeness. avr-libc is a separate project, and GCC does not know what library will be linked. The "because" is presented as part of a judgment, but it is a causal claim, and it is false.
**Fix (297):** "...which reports 1 simply because GCC assumes a hosted environment on every target unless told `-ffreestanding`. Nobody checked the claim against avr-libc." (120): "It is a claim made by default, not a measurement and not a guarantee."

**L3. Line 330, D, medium (not run: no Xtensa toolchain here).**
**Problem:** "This is exactly the freedom the standard grants a freestanding environment".
**Evidence:** ESP-IDF compiles with GCC's default `-fhosted` (no `-ffreestanding` in its standard flags), so its compiler reports `__STDC_HOSTED__ == 1`. A hosted implementation must call `main` at startup (§5.1.2.2.1), so ESP-IDF, like avr-gcc, claims hosted while behaving as freestanding. Inferred from GCC's default; confirm on an ESP-IDF build.
**Fix:** "This is the freedom the standard grants a freestanding environment, although ESP-IDF's compiler, like avr-gcc, reports itself hosted. That is a second example of the claim and the reality parting company."

**L4. Lines 42 and 44, C, low–medium.**
**Problem:** "A conforming freestanding implementation is obliged to provide only the headers listed in Table 02.06-1 ..."
**Evidence:** N3096 §4p7: a freestanding implementation that defines `__STDC_IEC_60559_BFP__` or `__STDC_IEC_60559_DFP__` must also accept programs using `<fenv.h>`, `<math.h>` and the `strto*` floating-point conversion functions of `<stdlib.h>`.
**Fix:** Add: "and, if it claims IEC 60559 (IEEE) floating point, also `<fenv.h>`, `<math.h>` and the `strtod` family (§4)". Add a matching note under the table.

**L5. Throughout (lines 124–151, 203–267), A (TOC scope), medium.**
**Problem:** §02.06 never mentions §03.07 "Loading and Running", whose approved bullets are exactly `_start → __libc_start_main → main`, "reset vector → .data copy → .bss clear → main", and "what happens when main returns on a microcontroller". It also points to §03.06 for the startup files (correct) and to §36.05 for a startup routine.
**Evidence:** toc-draft-v1.md, §03.07. §02.06's own TOC bullet does cover "the meaning of main" on the three machines, so some overlap is approved. The full disassembly walk-through pre-empts §03.07, and the reader gets no pointer to it.
**Fix:** At line 149, add "(§03.07 follows this path step by step)". At line 267, add "§03.07 returns to this sequence". Alternatively, trim the startup disassembly here to the essentials and leave the detail to §03.07.

## 3. Improvements

**I1. Line 31, D.** C23 §5.1.2.2.1 allows `main` with no parameters, with two, "or in some other implementation-defined manner" (e.g. glibc's third `envp`, which line 149's `main(argc, argv, ...)` hints at). Add: "(or in another way the implementation documents, such as a third parameter for the environment on Linux)".

**I2. Line 35 and answer 502, D.** The standard says "a return from the *initial* call to `main`". A recursive return is an ordinary return. N3096 also notes a difference: with `return`, main's automatic objects are already dead when the atexit functions run, and with `exit` they are not. Wording: "returning from the initial call of `main` is equivalent to calling `exit` with the returned value (except that main's local variables no longer exist)".

**I3. Line 32, C.** "from `<stdio.h>` to `<threads.h>` (where not marked optional)": `<threads.h>` is itself optional (`__STDC_NO_THREADS__`). Use "from `<assert.h>` to `<wctype.h>`, except the parts the standard marks optional (such as `<threads.h>` and `<complex.h>`)".

**I4. Line 58, C.** "the headers ... that contain only macros and types come with the compiler": `<stdbit.h>` declares functions. GCC 14 does not ship it (it comes from glibc 2.39), and avr-libc 2.0 has none. Add: "`<stdbit.h>`, new in C23, declares functions and comes with the C library (glibc 2.39 has it; avr-libc 2.0 does not)."

**I5. Line 58, C.** The GCC manual states the memcpy/memmove/memset/memcmp requirement but not the reason. Attribute the "because..." to the author, or write: "GCC's manual states that GCC requires...; the reason is that GCC itself emits calls to them, for instance to copy a large structure (Experiment ...)."

**I6. Line 149, D.** "which the compiler added to your program": the gcc *driver* told the linker to add Scrt1.o (visible in Experiment 02.06-4). Wording: "which gcc asked the linker to add".

**I7. Line 184, D.** "`__builtin_unreachable()` confirms it": it is a promise to the compiler that control never gets there (undefined behavior if it does). It also keeps GCC from warning that a `[[noreturn]]` function returns, because GCC cannot see that the `syscall` does not come back. Wording: "promises the compiler that control never reaches that point; without it GCC would warn that a `[[noreturn]]` function can return."

**I8. Line 289 and 456, B.** "the simulator, which shows everything the UART transmits": simavr prints UART output line by line, so a partial line without '\n' never appears (seen in the E8 tests). Wording: "which prints each complete line the UART transmits".

**I9. Experiment 02.06-2 (line 403), B/A.** Rebuilding produces `warning: 'sys_exit' defined but not used [-Wunused-function]`. Warn the reader. The signal itself belongs to §33.02 ("SIGSEGV"); §27.02 explains what a segmentation fault is. Cite both. The answer is verified: ret pops argc = 1, gdb shows `rip 0x1`, status 139.

**I10. Lines 151 and Figure, D.** glibc's `_exit` makes the `exit_group` system call (strace: `exit_group(0)`), not a system call named `_exit`. Wording: "and finally makes the `exit_group` system call (through `_exit`)".

**I11. Experiment 02.06-4 (line 407), B.** The last line `gcc -###` prints is `COLLECT_GCC_OPTIONS=...`, not a command. The linker command is the `collect2` line before it. "Your own" object appears as `/tmp/ccXXXX.o`. Say so.

**I12. Line 542, B.** The TOC says bare-metal work uses Fedora's avr-gcc 15. Add the AVR disassembly addresses, the 1626/1748-byte sizes and the Arduino output to "for the reader to confirm" (avr-libc 2.2 / avr-gcc 15 may differ).

**I13. Line 363, D.** "C was born to write an operating system on a machine with no standard" is unclear. "Four kinds of behavior marking what is fixed, what is chosen and what is forbidden" names three, omits unspecified, and calls undefined behavior "forbidden" (the standard imposes no requirements). Suggest: "...four kinds of behavior: fixed by the standard, chosen and documented by each implementation, left open without documentation, and outside any requirement at all (§02.04)".

**I14. Line 63, D.** "three more things that a hosted environment provides": the constructor is a GCC extension, not a hosted-environment provision (it works on the AVR too). Wording: "along with argc/argv and atexit, which a hosted environment provides, and a constructor, a GCC extension".

**I15. Line 330, D.** "so a typical `app_main` starts a few tasks and ends" is an overstatement. Many ESP-IDF examples loop in `app_main`. Wording: "so an `app_main` may simply start a few tasks and end".

**I16. Lines 316–320 (optional), D.** ArduinoCore-avr main.cpp also defines `int atexit(void (*)()) { return 0; }`, so registered functions never run. This is a concrete AVR instance of "what runs after main", and would sharpen the Table's ATmega column.
