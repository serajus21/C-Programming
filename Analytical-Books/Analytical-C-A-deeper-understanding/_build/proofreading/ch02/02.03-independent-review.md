# Review of §02.03 "The C Abstract Machine"

Reviewed file: /home/claude/review0203/target/02.03.md (line numbers refer to it). Every command was re-run with GCC 14.2.0 (Ubuntu 24.04, glibc 2.39), avr-gcc/avr-g++ 7.3.0 and simavr. Scratch work is in /tmp/r0203/x. Primary sources consulted: N3096 (§5.1.2.3, §6.7.3 p8, §7.26.6.2 with footnote 383), N1570 §5.1.2.3, the C99 text of §5.1.2.3, N3220's clause list, the ISO/IEC 9899:2024 table of contents (publisher preview), the Ubuntu ToolChain/CompilerFlags wiki, the Red Hat developer blog on GCC flags (2018), the Fedora GNUToolchainF44 change page, and the Phoronix report on the glibc 2.43 release.

Severity scale: **High** (a reader would learn something false about a central point); **Medium** (false or misleading, but limited in scope); **Low** (a small inaccuracy or inconsistency).

## 1. Errors

**E1. Line 76. Category D/C. Severity: Medium.**
**Problem:** "The standard states the consequence directly, as an example: an actual implementation need not evaluate part of an expression…"
**Evidence:** In N3096, §5.1.2.3 paragraph 4 ("In the abstract machine, all expressions are evaluated as specified by the semantics. An actual implementation need not evaluate…") is a numbered normative paragraph, not an EXAMPLE. The section's EXAMPLEs start later ("An implementation might define a one-to-one correspondence…"). The same holds in C11. Because the book teaches the reader to tell normative text from examples, this matters.
**Fix:** "The standard states the permission directly, in a normative paragraph of the same clause: an actual implementation need not evaluate part of an expression if…"

**E2. Line 586. Category C. Severity: Medium.**
**Problem:** "in C99 and C11 it was §5.1.2.3, with volatile objects required to be stable at sequence points."
**Evidence:** That wording is C99 only. C11 (N1570 §5.1.2.3 p6) reads "Accesses to volatile objects are evaluated strictly according to the rules of the abstract machine"; the "stable at sequence points" sentence does not appear in C11's §5.1.2.3. C23 then reworded it to "Volatile accesses to objects…".
**Fix:** "In C99 the first requirement read that volatile objects are stable at sequence points; C11 replaced this with accesses to volatile objects being evaluated strictly by the abstract machine's rules, and C23 rephrased it in terms of volatile accesses."

**E3. Lines 36, 76, 586; Figure 02.03-1. Category A/C. Severity: Medium.**
**Problem:** The section cites "C23, §5.1.2.3" and "C23, §6.7.3" as if those were the clause numbers of C23.
**Evidence:** These are N3096 (April 2023 draft) numbers. The published ISO/IEC 9899:2024 renumbered:
- Its table of contents has 5.1 "Introduction", 5.2 "Conceptual models", 5.2.2 "Execution environments", 6.7.3 "Type specifiers" and 6.7.4 "Type qualifiers".
- In N3220, the free draft closest to the published text, the material is §5.1.2.4 "Program semantics" (line 586 notes this).

A reader who opens the real C23 at §6.7.3 finds *type specifiers*. Sibling §02.02 line 677 has the same problem ("ISO/IEC 9899:2024 (C23), §§5.2.4.2.1, 6.3.1.3, 6.5.5, 6.5.7").
**Fix:** Cite the draft explicitly in the text and the figure, for example "(C23 draft N3096, §5.1.2.3)" and "(N3096 §6.7.3)". Add to Sources: "In the published ISO/IEC 9899:2024 these are in 5.2.2 (Execution environments) and 6.7.4 (Type qualifiers); in N3220, §5.1.2.4 and §6.7.4." Also adopt a house rule for all sections.

**E4. Line 160. Category D. Severity: Low.**
**Problem:** "it may compute that value itself, merge two calls with the same arguments into one, or, if the value is not used, delete the call entirely. Listing 02.03-2 tests all three."
**Evidence:** Listing 02.03-2 never merges two calls whose values are both used. The loop's four calls have different arguments, and the second `gate_nand(1, 1)` is deleted because its value is unused, not merged. Merging is shown only by Listing 02.03-5 (`checked_compute`).
**Fix:** "Listing 02.03-2 tests the first and the third; Listing 02.03-5 will show the second."

**E5. Line 283. Category C. Severity: Low.**
**Problem:** "so the whole loop "need not be evaluated", and is not."
**Evidence:** The standard's words are "need not evaluate part of an expression". The quoted string is not in the source. It is also a second direct quotation from the same source (line 36 already quotes "issues of optimization are irrelevant"), which breaks the one-quotation-per-source rule. In addition, deleting a whole loop rests on the observable-behavior requirements as a whole, not only on the expression-evaluation paragraph.
**Fix:** "so, under the as-if rule, the whole loop may be omitted, and is."

**E6. Line 394; Self-check 10 answer (line 562); Experiment 02.03-3 answer (line 572). Category B. Severity: Medium.**
**Problem:** "it genuinely computes twice and compares".
**Evidence:** In the verified `-O2` output of `checked_compute_vin`, `x*x + 3*x` is computed twice (two `imull`) and compared, but the `+ 1` is factored out and done **once, after** the comparison:
```
cmpl %eax, %edx ; setne %dl ; addl $1, %eax
```
So part of `compute` is still shared, which is exactly the section's lesson (the optimizer removes duplication it can prove redundant). The reader will see this in Experiment 02.03-3.
**Fix:** Add after "(two `imull` instructions in the output)": "Look closely, though: the compiler compares `x * x + 3 * x` from the two reads and adds the final 1 only once, after the comparison, because that step is provably the same for both. Even here, whatever can be shared is shared."

**E7. Line 396. Category D. Severity: Medium.**
**Problem:** "an upset in a register between the two computations may still escape it".
**Evidence:** In the generated code, an upset *between* the two computations is the case most likely to be caught. Such an upset changes either the first result (held in `%eax`) or the stored `in` before the second read, so the comparison differs. Upsets escape in two windows:
- **before the duplication:** `x` in `%edi` before it is stored to `in`, which corrupts both computations alike;
- **after the comparison:** the shared `+ 1`, the store to `*fault`, and the returned register.

**Fix:** "Even the third version is a compromise: an upset that strikes before the input is stored, or after the comparison (in the shared final addition or in the returned value), still escapes it, and the duplication slows the code."

**E8. Figure 02.03-1 (fig_machines.png), bottom box. Category E. Severity: Low.**
**Problem:** "…unused work deleted; nothing kept that cannot be observed".
**Evidence:** Read as a description of the real machine, this is false. The `-O0` build in Listing 02.03-1 and Figure 02.03-2 keeps every unobservable store and load. The as-if rule permits deletion; it does not require it.
**Fix:** Replace with "…unused work may be deleted; whatever cannot be observed is free to change".

**E9. Line 587. Category C. Severity: Low.**
**Problem:** "Ubuntu's default `_FORTIFY_SOURCE` and Fedora's different default are from the distributions' compiler documentation (Ubuntu's "ToolChain/CompilerFlags" page)".
**Evidence:** The Ubuntu ToolChain/CompilerFlags page does not mention Fedora. The Fedora claim (no `_FORTIFY_SOURCE` in the driver) is supported by Red Hat's developer blog "Recommended compiler and linker flags for GCC" (2018): the toolchain is "very close to upstream defaults", and hardening is injected through RPM build flags (redhat-rpm-config). It is not supported by the Ubuntu page.
**Fix:** "…Ubuntu's ToolChain/CompilerFlags page (level 3 since 24.04, only with -O1 or higher); for Fedora, Red Hat's 'Recommended compiler and linker flags for GCC' (2018) and redhat-rpm-config's buildflags documentation, which apply hardening only in package builds."

**E10. Line 288 (output block). Category B. Severity: Low.**
**Problem:** `plain: 0 ticks, volatile: 7031 ticks (1 tick = 64 us).`
**Evidence:** The harness prints `…(1 tick = 64 us)\n`. The final `.` is simavr's rendering of the newline, not program output. In the same section, the Hands-on block at line 532 shows `plain loop: 0 us` with the simavr dots (`..` for `\r\n`) removed, and §02.02 states that simavr's line endings are omitted. The reader will think `printf` printed a period.
**Fix:** Delete the final period: `plain: 0 ticks, volatile: 7031 ticks (1 tick = 64 us)`.

**E11. Line 432; line 590; Experiment 02.03-4 (line 489). Category C. Severity: Medium.**
**Problem:** "Library support for `memset_explicit` arrived only recently, so on today's Linux systems `explicit_bzero` is the dependable choice". The sources line says glibc support is only "expected" in 2.43.
**Evidence:**
- glibc 2.43, released in January 2026, added `memset_explicit` (Phoronix release report; Debian's glibc 2.43 source contains `string/memset_explicit.c`).
- Fedora 44 ships glibc 2.43 (Fedora GNUToolchainF44 change: "gcc 16.1, binutils 2.46, glibc 2.43"). The reader's Fedora laptop therefore very likely has it.
- The man-pages lag cited at line 590 makes `man memset_explicit` an unreliable test.

**Fix:**
- Line 432: "`memset_explicit` reached glibc only in version 2.43 (January 2026), so it is available on current Fedora but not on older systems such as Ubuntu 24.04 (glibc 2.39); where it is missing, `explicit_bzero` is the choice."
- Experiment 02.03-4: replace "check with `man memset_explicit`" with "check with `grep memset_explicit /usr/include/string.h`, or simply compile with `-std=c23`".
- Line 590: cite the glibc 2.43 NEWS.

## 2. Likely errors

**L1. Line 106 (and the hood box, line 155). Category B/D. Severity: Medium.**
**Problem:** "The four options after `-S` only remove bookkeeping and extra protection code that some Linux distributions add by default (Ubuntu adds more than Fedora), so that the output is short and the same on both."
**Evidence:**
1. `-fasynchronous-unwind-tables` (the `.cfi` bookkeeping) is upstream GCC's default on x86-64 Linux, not something distributions add.
2. Position independence is not neutralized. Ubuntu's GCC is built with `--enable-default-pie` (Ubuntu wiki). Red Hat documents Fedora's driver as "very close to upstream defaults", i.e. without default PIE; I could not fetch Fedora's current gcc.spec to confirm. If so, the reader's output differs from every listing. With `-fno-pie`, GCC 14 gives `movl $.LC0, %edi` and `call printf` instead of `leaq .LC0(%rip), %rdi` and `call printf@PLT` (verified). In `login`, the calls become `call read_password` without `@PLT`.
3. The reader has GCC 15/16, not 14.2, so "the same" cannot be promised; line 584 itself says the outputs may differ.

**Fix:**
- Option A: add `-fPIE` to the printed commands, so that both distributions generate position-independent code.
- Option B: replace the sentence with: "The four options after `-S` remove the unwind-table bookkeeping that GCC emits by default and the protection code that Ubuntu adds by default (`-fcf-protection`, the stack protector and `_FORTIFY_SOURCE`), so that the output is short. Your Fedora compiler may still differ in small ways: if you see `movl $.LC0, %edi` and `call printf` without `@PLT`, your GCC is not building position-independent code by default (§21.06), which changes nothing in what follows."

**L2. Line 67; Table 02.03-1 (line 246); Terms (line 458); Self-check 3 answer (line 548); Figure 02.03-1 item 3. Category D. Severity: Medium.**
**Problem:**
- Line 67: "in particular, output that prompts the user appears before the program waits for the user's input."
- Terms: an interactive device is one "whose input and output must occur in the order the program specifies".

**Evidence:** N3096 §5.1.2.3 p6 requires only that "the input and output dynamics of interactive devices" take place as specified in §7.23.3, then adds: "The intent of these requirements is that unbuffered or line-buffered output appear as soon as possible, to ensure that prompting messages actually appear prior to a program waiting for input." Prompt-before-input is the stated **intent**, and §7.23.3 itself says support for the buffering characteristics is implementation-defined. Nowhere does the standard define an interactive device as one whose I/O "must occur in the order the program specifies".
**Fix:**
- Line 67: "take place as the library's rules for streams specify (§31.01); the standard says the intent is that prompting output appear before the program waits for input."
- Terms: "**Interactive device**: an implementation-defined class of devices, such as a terminal, whose input and output dynamics must follow the library's rules for streams."
- Adjust the Self-check 3 answer and the figure ("prompts intended to appear in time") to match.

**L3. Line 46. Category D. Severity: Medium.**
**Problem:** "And in a few places it leaves the order of events open … Each implementation picks one instance of the abstract machine, documents its parameters, and must then behave *as if* it were that instance."
**Evidence:** Implementation-defined choices must be documented, but unspecified choices, such as the order of `f()` and `g()`, need not be documented. They need not be consistent either: the implementation may choose differently at each evaluation, or in each build. A reader who infers "the order is fixed and written down somewhere" has learned something false. §02.04 depends on this distinction.
**Fix:** "Each implementation fixes and documents the parameters. Where the order is left open, it may choose differently each time and need not tell you, so a correct program must give acceptable results for every permitted order (§02.04)."

**L4. Line 432. Category D/C. Severity: Medium.**
**Problem:** "`memset_explicit`, whose stores must be performed even though nothing reads them."
**Evidence:** N3096 §7.26.6.2 normatively says only that the function copies the value and that its purpose "is to make sensitive information stored in the object inaccessible". The never-elided property is in footnote 383: "The intention is that the memory store is always performed (i.e., never elided), regardless of optimizations." That is non-normative. It cannot be a requirement, because by this very section's rules ordinary stores are not observable behavior. This is a good teaching point that the text currently gets backwards.
**Fix:** "…`memset_explicit`, whose purpose, the standard says, is to make the data inaccessible; a footnote states the intention that its stores are never removed. Since stores are not observable behavior, the standard can only state this as intent, and the guarantee in practice comes from the library and compiler."

**L5. Lines 252 and 291. Category D. Severity: Medium.**
**Problem:** "No C program, however written, can demand that something take a certain time, using only the language." Also "not by making time observable, which nothing in C can do."
**Evidence:** Time is indeed not observable behavior. But hosted standard C has `clock()`, `time()` and `timespec_get()`, and, where threads are supported, `thrd_sleep()`, which "suspends execution of the calling thread until either the interval specified by duration has elapsed or a signal…" (C11 §7.26.5.7). Calls to these library functions are not removable in practice, so a delay built on them is reliable to the extent that the implementation's clock is. A strict reader will find `thrd_sleep` and conclude the book is wrong.
**Fix:**
- Line 252: "Time is not observable behavior: the abstract machine has no clock, and nothing in the core language can demand that a computation take a certain time. (A hosted C library offers clocks and, with threads, `thrd_sleep`, but how accurate they are is up to the implementation, and avr-libc provides none of them for this purpose.)"
- Line 291: "not by making time observable, which the language cannot do".

**L6. Line 233 (myth box) versus Self-check 12 answer (line 566). Category D. Severity: Medium.**
**Problem:** "If a program prints different results at `-O0` and `-O2` … the fault is in the program, not in the optimizer: the program has no single meaning".
**Evidence:**
- This is absolute, and the section's own Self-check 12 answer says "Usually … Compiler bugs exist".
- A correct program with **unspecified** behavior (for example, printing an address, or `f() + g()` where both print) can legitimately print different results at the two levels without any fault.

**Fix:** "…the fault is almost always in the program, not the optimizer: either its behavior is undefined, so it has no meaning at all (§02.04), or it depends on something the standard leaves unspecified, so several outputs are all correct. Compiler bugs exist, but suspect the program first." Mention unspecified behavior in the Self-check 12 answer too.

**L7. Experiment 02.03-1 answer (line 568). Category B. Severity: Low.**
**Problem:** "At `-O1`, GCC 14.2 likewise put the constant 5050 directly into the `printf` call."
**Evidence:** Verified. At `-O1` GCC 14.2 does pass `$5050`, but it **keeps an empty 100-pass loop** (`movl $100,%eax; .L2: subl $1,%eax; jne .L2`). "Likewise", right after the `-O2` result, implies that no loop remains. The reader will see a loop and think the answer is wrong. The leftover loop is also a good illustration that the as-if rule permits deletion but does not require it.
**Fix:** "At `-O1`, GCC 14.2 also passed the constant 5050 to `printf`, but left behind an empty loop that counts down from 100 and does nothing: it computed the result without deleting the now-useless loop. The as-if rule permits removal; it never requires it."

**L8. Experiment 02.03-2 and its answer (lines 485, 570). Category B/D. Severity: Low.**
**Problem:** "Is the call on line 16 still removed? Why not?" The answer says: "The call on line 16 can no longer be removed".
**Evidence:** In the verified `-O2` output there is no `call gate_nand` at all. Every call, line 16 included, is inlined, leaving five `call printf@PLT` and the constant 14. The call is still removed; what cannot be removed is its side effect. The section itself says (line 73) that whether a body is copied into the caller is not observable.
**Fix:** In the question: "Is the work of line 16 still removed?" In the answer: "The fifth `nand(1, 1)` line appears in both builds: at `-O2` GCC still copies the function's body into `main` (there is no `call gate_nand`), but the `printf` inside it is observable behavior and must happen, even though the return value is unused."

**L9. Experiment 02.03-4 answer (line 574). Category B. Severity: Low.**
**Problem:** "With `-std=gnu23` … the `-O2` output contains `call explicit_bzero@PLT`".
**Evidence:** The experiment (line 489) says "compile with `-O2 -S`" without the four options. On Ubuntu that gives `call __explicit_bzero_chk@PLT` (and `__stack_chk_fail`), which I verified. The quoted line appears only with `-U_FORTIFY_SOURCE`. On a non-PIE default, `@PLT` is absent.
**Fix:** In the experiment, say "with `-O2 -S` and the four usual options", as Experiment 02.03-3 does. Or add to the answer: "(without `-U_FORTIFY_SOURCE`, Ubuntu shows the checking version `__explicit_bzero_chk`)".

**L10. Line 396. Category C. Severity: Low.**
**Problem:** "This is why serious software fault-tolerance techniques, such as … EDDI (2002) and SWIFT (2005), insert their duplicated instructions inside the compiler, after optimization, rather than in C source where the optimizer would undo them."
**Evidence:** Line 589 admits that the motive ("to avoid the optimizer's removing redundancy") is the author's reading, but the main text states it as fact ("This is why"). "After optimization" is not cited for EDDI. The secondary literature does describe compiler optimizations such as common-subexpression elimination undoing duplication (Princeton TR-830-08); a citation like that would support it.
**Fix:** "This is one reason why published software fault-tolerance techniques, such as EDDI (2002) and SWIFT (2005), insert their duplicated instructions inside the compiler, late in compilation, rather than in C source, where an optimizer would undo them."

**L11. Line 293. Category D. Severity: Low.**
**Problem:** "The right tools work by leaving the abstract machine's rules entirely … And Arduino's `delay()` reads a hardware timer".
**Evidence:** Arduino's `delay()` is ordinary C/C++. It stays *inside* the rules: it repeatedly calls `micros()`, which reads Timer 0's count and an overflow counter, both through volatile accesses. Only `__builtin_avr_delay_cycles` leaves the language. The difference is the point of the section: make the accesses observable, and let hardware supply the time.
**Fix:** "The right tools take time from the hardware, not from counting C operations. avr-libc's `_delay_ms` … (a promise about the real machine, made by the compiler, not by the language). Arduino's `delay()` stays within C's rules: it repeatedly reads a hardware timer through `volatile` accesses until enough ticks have passed (§37.02)."

## 3. Improvements

**I1. Line 291.** "(loads and stores take two cycles each on the AVR, and the taken branches two)" leaves out `adiw` (2 cycles) and calls `rjmp` a branch. With only the listed items, the total is 35, not 36. `std` is also 1 cycle on newer AVRxt cores.
Fix: "(on the ATmega328P, `ldd`, `std`, `adiw`, `rjmp` and a taken `brlo` take two cycles each; the others take one)".

**I2. Hands-on A (lines 529–536).** The sketch measured 437,504 µs, not the 0.45 s of Listing 02.03-3, on the same simulator with the same compiler family. The reason: avr-g++ laid the loop out with the exit test `brsh .L18` *not taken* (1 cycle) instead of `brlo` taken (2 cycles). That gives 35 cycles per pass, 7,000,000 cycles in all, i.e. 6,836 ticks of 64 µs = 437,504 µs (verified). One sentence explaining this would show the reader that "the same source, a different layout, a different time" is real.

**I3. Line 228.** "does the addition, and the zero extension it no longer needs, in one `lea`" reads as if `lea` extends.
Fix: "does the addition in one `lea` and skips the zero extension: only the low 8 bits of the result are returned, and the calling rules let the upper bits of `%eax` hold anything."

**I4. Line 392.** "the `leal`s the additions": the first `leal (%rdi,%rdi,2)` computes `3 * x`.
Fix: "the first `leal` computes `3 * x`, and the second adds the parts and the 1".

**I5. Line 339.** "keeps the value 0 permanently in register r1". The avr-gcc ABI lets `mul` clobber r1 temporarily and restore it.
Fix: "keeps 0 in register r1 at all times between instructions". Also gloss `tst r24` ("set the flags from r24") and `breq` ("branch if equal, that is, if zero") for `wait_volatile`.

**I6. Line 339 (precision).** Under N3096 §6.8.5 (C11 §6.8.5 p6), a loop such as `while (!ready) { }` (non-constant condition, no I/O, no volatile access, no atomics) may be *assumed to terminate*. The standard would even allow deleting the loop entirely; GCC's infinite `rjmp .L4` is only one permitted outcome. One sentence or a forward reference to §09/§34 would complete the picture.

**I7. Terms (lines 461–462).** "Constant folding" never appears in the body, and "dead store" appears only in an answer.
Fix: name them where they occur. Line 148: "…worked out, while compiling (**constant folding**, §09.05)". Line 432: "…the stores are **dead stores**: modifications of an object whose value is never used again".

**I8. Experiment 02.03-5 (line 491).** "(§01.06's Table 01.06-1 has several)": that table has only `sbci` and `rjmp` of the nine distinct instructions in the loop (`brne` only by analogy with `brlo`).
Fix: "(Table 01.06-1 has `sbci` and `rjmp`; find the rest in the manual)". Also make the answer's arithmetic explicit: "4 × 2 (ldd) + 2 (adiw) + 1 + 1 (adc) + 4 × 2 (std) + 2 (rjmp) = 22".

**I9. Line 36.** "The standard was written to serve the AVR, the x86-64, the Xtensa and machines not yet built" is anachronistic: the abstract-machine approach dates from C89 (1989), before all three.
Fix: "The standard was written to serve machines as different as the AVR, the x86-64 and the Xtensa, and machines not yet built".

**I10. Line 233.** "the implementation whose internal steps happen to resemble the abstract machine's" contradicts line 230, which says this is GCC's stated goal.
Fix: "are designed to resemble".

**I11. Line 63.** "Programs would run several times slower" is unsourced.
Fix: "Programs would run much slower, as `-O0` builds, which come close to this, typically do."

**I12. Orbit box (line 435).**
- Scrubbing: many EDAC memories correct the *data read* but need the corrected word written back to repair memory. Fix: "reads every word (and, where the hardware does not do it, writes the corrected value back)".
- Watchdog: on the reader's AVR the watchdog is reset by the `wdr` instruction (`wdt_reset()`), not by a register write. Fix: "…by writing to a hardware register (or, on the AVR, executing `wdr`) works only because that access cannot be removed".
- Line 76: add a support for "an implementation may promise more": §5.1.2.3's EXAMPLE 1 itself describes an implementation with a one-to-one correspondence between abstract and actual semantics.

**I13. Figure 02.03-2.** The caption "100 passes: load i, add to total in memory, store, compare, jump" leaves out the increment of `i` and has an unclear "store".
Fix: "100 passes: load i, add it to total in memory, add 1 to i in memory, compare, jump".

**I14. Output blocks at lines 278 and 322.** "comment lines removed" (line 320). In fact `.global`, `.type`, `.size` and `.L__stack_usage = 0` directive lines were also removed, and the block at line 279 has no note at all.
Fix: "(comments and assembler directives removed)", in both places.

**I15. Self-check 2 (line 469).** "the four kinds of side effect the standard defines": N3096 footnote 12 also makes changes to floating-point status flags and control modes count as side effects (Annex F).
Fix: "the four kinds of side effect this section listed".

**I16. Hands-on B (line 540).** "because the same rules apply to every implementation": the rules *permit* removal, and the result depends on the ESP32 core using `-Os` or another optimizing level.
Fix: "because the same rules permit it, and the ESP32's GCC, optimizing, uses that permission".

**I17. Line 230.** "-Og … some optimization, without destroying the correspondence a debugger relies on" overstates: at `-Og`, variables can still be shown as "optimized out".

## 4. Checked and found correct

- **x86-64 output blocks, character for character:** the blocks at lines 108, 136, 189, 207, 222, 382 and 418 match GCC 14.2.0 with the printed options. Two `call gate_nand` appear at `-O0`. Both programs print `total = 5050` and `truth table as a number: 14` at `-O0` and `-O2`.

- **AVR output blocks:** the block at line 278 (`delay_plain: ret`) and the instructions in the block at line 322 match avr-gcc 7.3.0 at `-Os` (apart from the directive lines noted in I14).

- **Timing measurements:** the harness gives 7031 ticks, i.e. 449,984 µs ≈ 0.45 s and 35.997 cycles per pass. The Hands-on sketch gives `plain loop: 0 us` / `volatile loop: 437504 us`.
- **Instruction readings:**

  - AVR: `cpse` (compare, skip if equal) and the `wait_plain` control flow; `lds`; r1 as `__zero_reg__`.
- **Line references in the prose:** sum.c lines 6–9 and 10; nand.c lines 5–7, 11–15 and 16; twice.c lines 24–25; secret.c line 12.
- **Experiment answers 02.03-3, 02.03-4 and 02.03-5:**
