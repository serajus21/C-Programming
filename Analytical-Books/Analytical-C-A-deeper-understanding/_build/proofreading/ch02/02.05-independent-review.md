Scope: /home/claude/review0205/target/02.05.md (line numbers refer to it). I re-ran every command with gcc-14 (14.2.0), gcc-13 (13.3.0), clang 18, avr-gcc/avr-g++ 7.3.0 and simavr. I rebuilt Table 02.05-2 from feat/ and redid every Self-check and Experiment. Facts were checked against the GCC manual, release notes and porting pages, a GCC commit, glibc 2.39 headers, the ISO catalogue, the N3096 front matter, ArduinoCore-avr on GitHub, the ESP-IDF docs and forum reports. ## 1. Errors

**E1. Line 236. Category C/D (internal inconsistency). Severity: medium.**
**Problem:** "its choice has changed four times", but the paragraph lists three changes: gnu89→gnu11 (GCC 5), gnu11→gnu17 (GCC 8) and gnu17→gnu23 (GCC 15). Figure 02.05-1 also shows four bands, which means three changes.
**Evidence:** The GCC 5 release notes ("The default mode has been changed to -std=gnu11") and the C status page (C17 was the default from GCC 8 to 14; C23 since GCC 15) document only these three changes.
**Fix:** "…and its choice has changed three times."

**E2. Line 236. Category C (overstatement / false generalization). Severity: medium.**
**Problem:** "Each change also broke some old programs, which is why GCC's release notes for these versions include porting advice."
**Evidence:** "Porting to GCC 8" has no C section at all (only C++ and Fortran). The GCC 8 change (gnu11→gnu17) moved to an edition that, as line 131 itself says, "added no features at all", so it could hardly break programs. The claim holds for GCC 5 (inline semantics) and GCC 15 (`bool` keyword, `()` meaning `(void)`).
**Fix:** "The changes to gnu11 (GCC 5) and to gnu23 (GCC 15) broke some old programs, and GCC's 'Porting to' notes for those versions explain how to repair them; the change to gnu17 broke almost nothing, because C17 only corrected C11."

**E3. Line 258. Category C (wrong number). Severity: low-medium.**
**Problem:** "Why would a manufacturer keep shipping a seven-year-old compiler?"
**Evidence:** Line 253 and the figure date avr-gcc 7.3 to January 2018. The book's present is November 2026 (the Sources say "checked 26 November 2026"), so the compiler is almost nine years old.
**Fix:** "a compiler released in January 2018, almost nine years ago?" (or "a compiler nearly nine years old").

**E4. Lines 224, 381, 465 (also 475). Category B (command fails as printed). Severity: medium.**
**Problem:** Line 224 says "GCC 13 still compiles the same call with a warning". Experiment 02.05-5 says "compile the `-std=c23` version with it", and the answer says "GCC 13 reports the same message as a warning and produces a program."
**Evidence:** `gcc-13 -std=c23 -c secret.c` gives `gcc-13: error: unrecognized command-line option '-std=c23'; did you mean '-std=c2x'?`. The spelling `-std=c23` arrived in GCC 14 (PR107954). With `gcc-13 -std=c2x -Wall -Wextra -pedantic -O2 -S secret.c` the result is `warning: implicit declaration of function 'explicit_bzero'` and exit status 0. Also, Listing 02.03-6 has no `main`, so neither compiler "produces a program". The result is an object file or assembly.
**Fix:** Line 224: "GCC 13 (which spells the option `-std=c2x`) still compiles the same call with only a warning." Experiment 02.05-5: "…compile it with `-std=c2x` (GCC 13 does not yet know the name `c23`) and compare the message." Answer: "GCC 13 with `-std=c2x` reports the same message as a warning, and the compilation succeeds (an object or assembly file is produced; the listing has no `main`)." Also tell the reader to compile with `-c` (or `-O2 -S`, as in §02.03) in all three builds.

**E5. Line 179 (Under the hood box). Category D (wrong mechanism). Severity: medium.**
**Problem:** "A header belongs to the implementation, and GCC's versions of these two do not check which edition was requested."
**Evidence:**
(a) GCC 14's `<stdbool.h>` does check the edition. Line 33 of the header is `#if defined __STDC_VERSION__ && __STDC_VERSION__ > 201710L`.
(b) On the verification machine `<stdint.h>` is mostly glibc's. `gcc -E` shows GCC's wrapper pulling in `/usr/include/stdint.h` and `bits/stdint-*.h`.
(c) The real reason is different. `feat/stdbool.c` passes under `-std=c89 -pedantic-errors` although `bool` expands to `_Bool`, yet `int main(void){ _Bool ok = 1; return !ok; }` written directly fails: `error: ISO C90 does not support boolean types [-Wpedantic]`. I reproduced the cause. With `#define B _Bool` in a header reached by `-isystem`, the program compiles (rc=0). The same header reached by `-I` gives the error. GCC suppresses pedantic diagnostics for code that comes from system headers, including macros defined there.
(d) `uint8_t` is just a typedef for `unsigned char`, so nothing in stdint.c is non-C89 in the user's own text.
**Fix:** Replace the second sentence: "Their contents are not the reason: `uint8_t` is only a typedef for `unsigned char`, which C89 has. And GCC does not issue pedantic diagnostics for code that comes from system headers, including the expansion of macros defined there. So `bool`, which `<stdbool.h>` defines as `_Bool`, passed, although `_Bool` written directly in the program is rejected under `-std=c89 -pedantic-errors` (try it)." Keep the box's final lesson.

**E6. Line 144. Category D (overstatement; contradicts line 231). Severity: medium.**
**Problem:** "`-pedantic-errors`, which turns every departure from the chosen edition into an error".
**Evidence:** The *Precisely speaking* box (line 231) and §00.02 (line 131) say the opposite: even `-std=… -pedantic` "do[es] not detect every program that steps outside ISO C". The GCC manual (Warning Options, -Wpedantic) says it finds only the non-ISO practices for which ISO C requires a diagnostic, plus some others.
**Fix:** "…with `-pedantic-errors`, which turns the diagnostics of `-pedantic` (those the chosen edition requires, and warnings about GNU extensions) into errors."

**E7. Line 477 (Sources). Category C (wrong source location). Severity: low.**
**Problem:** "the forewords of C99, C11, C17 and C23 (N3096), which list the major changes"; "their removal in C23 (N3096, §6.9.1 and foreword)".
**Evidence:** N3096's Foreword contains no list of changes. It says "This fifth edition cancels and replaces the fourth edition, ISO/IEC 9899:2018" and refers to Annex M for the change history. The list of C23 changes is in Annex M (M.2).
**Fix:** "the forewords of C99, C11 and C17, and Annex M (change history) of N3096 for C23"; "(N3096, §6.9.1 and Annex M)".

## 2. Likely errors

**L1. Line 429 (Hands-on B). Category C. Severity: medium.**
**Problem:** "Expect a C++ value of 201703 or later". The sentence just before says the values depend on the installed core, but this expectation is unconditional.
**Evidence:** Users of Arduino-ESP32 core 2.x report `__cplusplus` = 201103 (forum.arduino.cc, "How to use C++17 for ESP32-S3": "ESP32 Arduino Core 2.x is at C++ 2011", test printed 201103). Core 1.0.6 used `-std=gnu++11` (PlatformIO community, "Which C++ standard am I using?"). For core 3.1.1, the cpp_flags contained `-std=gnu++2b` overridden by a later `-std=gnu++17` (forum.arduino.cc "Espressif ESP32 core 3.1.1 no C++20 support"), giving 201703. I could not confirm the "reported 202100" claim from accessible sources.
**Fix:** "With core 3.x (built on ESP-IDF 5.x), expect a C++ value of 201703 or later and a C value of 201710. Older 2.x cores report 201103, C++11."

**L2. Lines 176, 290, 327 (and §00.02 line 115). Category C/D (inference presented as cause). Severity: low-medium.**
**Problem:** Line 176 says "A compiler's support for an edition is often incomplete for years, which is one reason GCC 14 reports the provisional value 202000". Line 290 says "GCC 14 reports the provisional 202000 for its incomplete C23".
**Evidence:** GCC changed the value in commit r15-62-ga2452a68917 ("libcpp: Adjust __STDC_VERSION__ for C23", 30 April 2024), just after GCC 14 branched. The commit message gives as context that C23 was not yet officially released and that Clang 18 already used 202311L. It did not wait for complete support: `#embed` came later in the GCC 15 cycle. So the value depends on when GCC adopted the final number, not on how complete its support was. `__STDC_VERSION__` never certified completeness, and the text's own point (line 320) is exactly that.
**Fix:** Line 290: "GCC 14 reports the provisional 202000, the placeholder GCC used for C23 until the final value was settled". Line 176: drop "which is one reason…" and keep the lesson: "a compiler's support for an edition is often incomplete for years, and the value it reports does not tell you how complete it is." Align §00.02 when it is next revised.

**L3. Lines 93, 103, 139, 173. Category D (misleading about GCC behaviour). Severity: medium.**
**Problem:** "And the 1978-style definition is gone from the language. The program … does not compile at all under C23." The output is described as including "two errors about the definition itself", and the Table row "definition in the 1978 style" shows "no" under c23.
**Evidence:** The two errors (`number of arguments doesn't match prototype`, `prototype declaration`) come from the clash with `int area();`, which in C23 means `(void)`. They are not caused by the old syntax. On its own, `int area(w, h) int w, h; { return w * h; }` compiles and runs under `gcc-14 -std=c23`, even with `-Wall -Wextra`, with only `warning: old-style function definition [-Wold-style-definition]`. The Table's "no" comes only from `-pedantic-errors`. Clang 18 `-std=c23` rejects it outright ("unknown type name 'w'"). The statement about the standard is right, but a reader will conclude that GCC rejects old-style definitions in C23, which GCC 14 does not.
**Fix:** After line 93, add: "The errors about the definition arise because, in C23, it conflicts with `int area(void)`. A 1978-style definition on its own is still accepted by GCC 14 in C23 mode with a warning, as an extension; `-pedantic-errors` makes it an error, and Clang rejects it outright." Add a footnote to the Table row: "(GCC: warning only, error with `-pedantic-errors`)".

**L4. Line 346 (Terms) with line 107. Category C. Severity: low.**
**Problem:** "**Wide character**: … (C95)".
**Evidence:** C89 already had `wchar_t` (`<stddef.h>`), wide literals `L'x'`/`L"…"` and the multibyte/wide conversion functions (`mbtowc`, `mbstowcs`, … in `<stdlib.h>`). AMD1 added the wide-character *library* `<wchar.h>`/`<wctype.h>`. Line 107 says "added a library", which is correct, but the term attributes wide characters to C95.
**Fix:** "Wide character: a character value wider than a byte (type `wchar_t`, C89), for writing systems with many characters; C95 added most of the library for handling them."

## 3. Improvements

**I1. Lines 31, 142, 435. Category C (promise "how they are named"). Severity: medium.** The section never says that C17 is also called **C18** (GCC accepts `-std=c18` and `-std=iso9899:2018`), yet its own Sources (line 481) say MISRA added "C11 and C18". It also never explains provisional names (C9X, C1X, C2X → `-std=c2x`, C2Y), which the reader needs for GCC 13 (E4) and which line 142 uses. Add: "C17 is also called C18, after its ISO year; GCC accepts both names. Before publication an edition goes by a provisional name, such as C2X for C23 (GCC 13 knows only `-std=c2x`) and C2Y for the next."

**I2. Line 29. Category C. Severity: low.** "Since 1990 the committee has been ISO's working group for C, known as WG14." WG14 already took part in producing C90. Since C90, the *standard* is an ISO document maintained by WG14, with the US committee (X3J11, later J11/PL22.11) as a national member. Suggested wording: "Since C90, the standard has been an ISO document, maintained by ISO's working group for C, WG14."

**I3. Line 107. Category D (terminology). Severity: low.** "It was also the first edition to define `__STDC_VERSION__`." By the section's own definition (line 29, line 340: "a complete revision"), an amendment is not an edition. Use "the first document of the standard to define…". Likewise, Table 02.05-1's title "The editions of C" covers K&R and C95. Consider "Versions of C".

**I4. Line 126 (Why box). Category D. Severity: low.** C99 also added the plain-named keywords `inline` and `restrict`, which could break programs using those names. Add one sentence: "C99 did add `inline` and `restrict` under plain names, judging them rare as identifiers (and `inline` already familiar from C++); for `bool`, used everywhere, the risk was too great." Also mention that C11 offered `static_assert` as a macro in `<assert.h>`. Self-check 6's answer relies on this, but the body never states it.

**I5. Line 224 and Self-check 9 answer. Category D. Severity: low.** "in every mode except C89". `-std=gnu89` (and `-ansi`) are also exempt (verified: `feat/implicit_decl.c` compiles silently with `-std=gnu89`). "Porting to GCC 14" names `-std=gnu89` and `-std=c89`. Write "except the C89 modes (`-std=c89`, `-std=gnu89`, `-ansi`)".

**I6. Line 219. Category D. Severity: low.** "In ISO mode GCC defines only the reserved spellings `__linux__` and `__unix__`". The `-std=c23 -dM -E` output also contains `__linux`, `__unix` and `__gnu_linux__`. Write "defines only reserved spellings, such as `__linux__` and `__unix__`".

**I7. Line 221. Category D. Severity: low.** "enables its BSD and System V additions (the set it calls `_DEFAULT_SOURCE`) only when `__STRICT_ANSI__` is not defined". In glibc 2.39 `<features.h>` (lines 229–239), `_DEFAULT_SOURCE` is defined only if `__STRICT_ANSI__` *and* `_ISOC99_SOURCE`, `_POSIX_C_SOURCE`, `_XOPEN_SOURCE`, etc. are all undefined. It also turns on POSIX.1-2008 (lines 282ff), not only `__USE_MISC` (4.3BSD/System V). Suggested wording: "enables its default extensions (the set it calls `_DEFAULT_SOURCE`: POSIX.1-2008 plus BSD and System V additions) only when neither `__STRICT_ANSI__` nor another feature test macro is defined". `explicit_bzero` is declared under `__USE_MISC` (string.h line 460).

**I8. Line 186. Category D. Severity: low.** "the keywords `asm` and `typeof` in editions where they are not standard". `asm` is standard in no edition (it is a common extension). Write "the keywords `asm` (never standard) and `typeof` (standard only from C23)".

**I9. Line 138. Category D. Severity: low.** "`_BitInt(N)`, integers of any width N". The width is limited by `BITINT_MAXWIDTH` (at least the width of `unsigned long long`). Write "of any width N up to an implementation limit, `BITINT_MAXWIDTH`".

**I10. Line 139. Category D (garbled). Severity: low.** "which the other representations had not been, on any new machine, for decades" does not parse. Write "no new machine had used another representation for decades".

**I11. Line 114. Category D. Severity: low.** The exact-width types are *optional*: they are provided only where the implementation has such types. Add "(provided wherever the machine has types of those widths, which in practice is everywhere; §05.04)" and point to §05.04, the TOC section on exact-width types.

**I12. Lines 63, 75. Category D. Severity: low.**
- Line 63: "`//` comments did not exist in C until 1999". Write "in *standard* C". Many compilers accepted them earlier: `gcc -std=gnu89 -pedantic` only warns about them.
- Line 75: "before 1989 … simply not checked". Write "not checked by the compiler (lint, §02.01, could check it separately)". The C17 run just shown proves that such calls stayed unchecked after 1989 for every declaration without a prototype, so make that explicit.

**I13. Line 93. Category D. Severity: low.** Explain why the *one*-argument call `area(6)` also gets "too many arguments": in C23, `int area();` declares zero parameters. Otherwise the reader meets a puzzling message.

**I14. Line 103. Category D. Severity: low.** "They were removed in C23". Strictly, old-style definitions were removed, while the empty-parentheses declaration was *redefined* to mean `(void)`. Write "removed or redefined".

**I15. Line 238. Category D (tautology). Severity: low.** "It depends on the compiler's version, and the version depends on which compiler you are running." Write "It depends on which compiler, and which version of it, you are running."

**I16. Lines 107, 236, 254, 258. Category C (inference stated as fact). Severity: low.** The following are stated as fact but are inference:
- "a problem the American committee had underestimated" (line 107)
- "Each change followed the same reasoning" (line 236)
- "Arduino keeps this fixed so that a library written years ago still compiles today" (line 254)
- "a rule that is absolute in flight software… qualifies one exact compiler version" (line 258)

Only the Arduino motive and the orbit box are listed in "Inference in this section", and the text itself gives no signal. Hedge each ("probably", "Arduino's evident reason…"). Line 258 also overstates: in DO-178C practice, compilers are usually not qualified as tools; their version and options are fixed under configuration control and the object code is verified. Write "a flight-software team fixes one exact compiler version and set of options…".

**I17. Line 326. Category D. Severity: low.** "as it did above for statement expressions": no listing used a statement expression; they were only discussed and tested in Experiment 02.05-6. The same bullet's "Every listing … is compiled with `gcc -std=c23 …`" is contradicted in this very section by Listings 02.05-1 (`-std=c17`) and 02.05-2 (`gnu23`). Write "…unless the text says otherwise, as it did in this section".

**I18. Line 244 (Table 02.05-3). Category C. Severity: low.** Evidence "observed: Listing 02.05-3 prints C17" cannot distinguish `gnu17` from `c17` (line 308 says so). Write "observed: Listing 02.05-3 prints C17, and `gcc -dM -E` shows `linux` defined and no `__STRICT_ANSI__`" (verified).

**I19. Lines 255, 75. Category A. Severity: low.**
- Line 255: "As §00.02 and §39.04 note". §39.04 is in the future; write "as §00.02 noted and §39.04 explains".
- Line 75: "§27.02 explains why". §27.02's TOC bullets do not yet name address randomization (already an open CHECK in promises.md). Keep the CHECK open.

**I20. Whole section. Category A. Severity: low-medium.** There is no pointer to §18.04 "Declarations and Prototypes", which builds on §02.05 and covers old-style declarations, implicit `int`/implicit declarations and "`()` against `(void)` through C17, and in C23". Add "(§18.04)" after the prototype discussion (line 99) or line 93.

**I21. Line 350 (Terms) vs line 231. Category D. Severity: low.** "Dialect: a compiler's version of an edition, including its own extensions" does not fit "`-std=c23` selects the *ISO dialect*" (line 231). Define it as "a compiler's mode for an edition: ISO (conflicting extensions off) or GNU (all extensions on)".

**I22. Experiment 02.05-1 answer (line 457). Category B. Severity: low.** The experiment asks the reader to try `-std=c2y` on GCC 15+, but the answer says nothing. Add: "With GCC 15 or 16, `-std=c2y` prints 'C23 or later' with a value above 202311 (the provisional C2y value); GCC 14 rejects the option."

**I23. Figure 02.05-1. Category E. Severity: low.** I measured the dates: every edition dot and every band edge is correct to within a month (GCC 5.1 at 2015.3, 8.1 at 2018.3, 15.1 at 2025.3; C17 at 2018.5; C23 at 2024.8). Two items to fix:
- The "avr-gcc 7.3 (Jan 2018)" arrow sits at about 2016.8, the centre of the gnu11 band, not at January 2018. Move it to 2018.0, just left of the gnu17 band edge.

## Disposition (author, November 26, 2026)

Every finding was checked before it was applied.
- **Reproduced in the workspace:** E4 (GCC 13.3 rejects `-std=c23` and suggests `-std=c2x`; with `-std=c2x -c` it warns and produces the object), E5 (`_Bool` written directly fails under `-std=c89 -pedantic-errors`, while `<stdbool.h>`'s `bool` passes), L3 (GCC 14 `-std=c23` accepts a 1978-style definition with a warning and rejects it with `-pedantic-errors`; Clang 18 rejects it), and I5 (`-std=gnu89` gives no error).
- **Accepted as reported:** E7 against N3096's structure, and L2 (GCC commit r15-62), both consistent with the author's own observations.

**Applied as proposed or with light rewording:**
- Errors: E1, E2, E3, E4, E5, E6, E7.
- Likely errors: L1, L2, L3, L4.
- Improvements: I1 to I22, and I23 (avr-gcc 7.3 arrow moved to January 2018; first band starts at GCC 1.0 in 1987, labeled "GNU C, later named gnu89 / gnu90").

**Not changed elsewhere:** §00.02's precise box says that GCC 14 was released while C23 awaited publication and with its C23 support incomplete, and that it reports 202000. It states both facts without claiming one causes the other, so it was left as it is. §02.05 now gives the correct cause.
