2. **"Memory: many cells, one address", line 197: "your laptop's addresses are 64 bits wide (§01.01)"**. Category: cross-reference + technical. Severity: **likely error**.
   Problem: (a) §01.01 never says addresses are 64 bits. It says the laptop's *word*/registers are 64 bits (01.01.md line 220, Self-check 9 at line 334). (b) The claim is imprecise in exactly the sense this paragraph is about ("a pattern of voltages on wires"). x86-64 pointers are 64-bit *values*, but only 48 (or 57 with 5-level paging) virtual-address bits are significant. The physical address that reaches the memory system is narrower again: typically 39–52 bits, depending on the CPU.
   Fix: "your laptop's pointers are 64-bit numbers (§01.01's 64-bit word), although fewer bits of each actually reach the memory chips (§27.02)".

3. **Line 197: "When you meet pointers in Chapter 24, a pointer will be exactly such a number, ready to be placed on the address wires."** Category: cross-reference + technical. Severity: **likely error**.

The TOC covers that in §27.02 "Virtual Memory on Linux". A reader who values precision will later have to unlearn "exactly".
   Fix: "On the ATmega328P a pointer will be exactly such a number (Chapter 24). On your laptop the processor first translates it (§27.02)."

14. **Hands-on A, Listing 01.04-5 (setup, listing lines 22–29) and line 441: "nobody set the latch at power-up, so which state did it fall into? … You are watching the race of Experiment 01.04-2"; Answer "Hands-on A", line 542.** Category: program / technical. Severity: **error**.
    Problem: the sketch itself puts the latch into a known state before the first `report`, so the "power-up" line can never show the race. After any reset the PORTD bits are 0, and Arduino's `pinMode(pin, OUTPUT)` only sets the DDR bit. So the sequence is:
    - Listing line 24: S̄ is driven LOW.
    - Listing line 25: R̄ is driven LOW, which is the forbidden state (Q = Q̄ = 1).
    - Listing line 28: S̄ goes HIGH while R̄ is still LOW, which is a *reset*.
    - Listing line 29: R̄ goes HIGH, so the latch holds Q = 0.

    The "power-up" line is therefore always `Q = 0  Q' = 1`, whatever the gates did when power arrived.

    Also, pressing the Uno's reset button does not remove power from the 74HC00, so the latch keeps its state. Pressing reset can never repeat the race, even in principle.

    In addition, Uno pins 2 and 3 are floating inputs from reset until `setup` runs (including Optiboot's ~0.5 s after an external reset), which leaves CMOS inputs floating.

    Evidence: I compiled the unmodified sketch against a host model of Arduino pin semantics (DDR/PORT) driving a cross-coupled NAND pair, starting from Q = 1. It printed `power-up        Q = 0  Q' = 1`, with pin trace `[S=0 R=float] [S=0 R=0 -> Q=1 Q'=1] [S=1 R=0 -> Q=0 Q'=1] [S=1 R=1 -> Q=0 Q'=1] …`.

    Fix:
    - Add 10 kΩ pull-up resistors from S̄ and R̄ to 5 V.
    - In `setup`, call `digitalWrite(pin, HIGH)` *before* `pinMode(pin, OUTPUT)`, so the pins go straight from pulled-up to driven-HIGH. Then read Q and Q̄ before any pulse.
    - Tell the reader that only removing and restoring the 5 V supply (unplugging USB) re-runs the race, and that the reset button does not.
    - Rewrite Answer A to match.

15. **Hands-on B, line 469 ("Upload it, open the Serial Monitor …") and Answer line 544 ("On a board whose EEPROM byte 0 was never written, the first value is 0").** Category: program behavior. Severity: **likely error**.

    Fix: warn that the run after upload and each opening of the Serial Monitor are boots too, and predict "0 is consumed by the run right after upload, so you will probably first see 1".

## C. Technical facts

17. **Hands-on B, line 471: "a sketch that wrote the EEPROM on every pass of `loop()`, thousands of times a second, could wear that byte out in under a minute"; repeated in Sources line 553.** Category: technical / arithmetic. Severity: **error**.
    Problem: an ATmega328P EEPROM write takes 3.3 ms (3.4 ms for the atomic erase-and-write that `eeprom_write_byte` uses). avr-libc waits for the previous write to finish, so a loop can write at most ≈ 300 times a second, not thousands. 100,000 cycles / ~300 per second ≈ 330 s, which is about **5½ minutes**, not "under a minute". (Also, 100,000 is the guaranteed minimum, not a failure point.)
    Evidence: ATmega328P datasheet: "EEPROM write (from CPU) 26,368 3.3ms" (Table 12-2); EEPM = 00 "3.4ms Erase and Write in one operation" (Table 12-1); "Write/Erase Cycles: 10,000 Flash/100,000 EEPROM" (https://cse.unl.edu/~jfalkinburg/cse_courses/2021/236/Atmega328p_full_datasheet.pdf). Calculation: 1/3.3 ms = 303 writes/s; 100,000/303 = 330 s.
    Fix: "…could wear that byte past its rated endurance in about five or six minutes, because each write takes about 3.3 ms". Update the Sources line to match.

18. **Line 245: "The AVR has no instruction that adds a constant to a single 8-bit register"; also Self-check 11 answer (line 495) and Experiment 01.04-4 answer (line 538): "So the AVR does have an add-constant instruction after all, but only for these 16-bit pairs."** Category: technical. Severity: **error**.
    Problem: the AVR has `INC Rd`, which adds the constant 1 to any single 8-bit register in one cycle (and `DEC`). The true statement is that the AVR has no general *add-immediate* (ADDI) for 8-bit registers. `count + 1` could equally be `inc r24`. GCC chose `subi` here, which is equally fast for r16–r31 (and leaves the carry flag meaningful).
    Fix: "The AVR has no general 'add immediate' instruction for an 8-bit register (only `inc`, which adds exactly 1), so the compiler subtracts minus one…". Correct Self-check 11 and the adiw remark the same way.

19. **"The clock and the D flip-flop", line 155: "On the Arduino Uno it comes from a 16 MHz crystal oscillator".** Category: technical. Severity: **likely error**.
    Problem: on the Uno R3 the ATmega328P is clocked by a 16 MHz *ceramic resonator*. The 16 MHz crystal on the board belongs to the ATmega16U2 USB interface.
    Evidence: Adafruit Uno FAQ: "the Atmega328p chip that is the core processor in the Arduino now has a 16mhz ceramic resonator" (https://learn.adafruit.com/arduino-tips-tricks-and-techniques/arduino-uno-faq).
    Fix: "from a 16 MHz ceramic resonator (a cheaper cousin of a quartz crystal)". Also, "in your laptop, from a much faster on-chip source" would be more precise as "from an on-chip circuit (a PLL) that multiplies a slower crystal's frequency".

20. **:::precise box, line 172: "Within a synchronous design the clock period guarantees the rules are met."** Category: technical. Severity: **likely error**.
    Problem: a long enough clock period guarantees *setup* time only. *Hold* time does not depend on the period at all. A hold violation occurs when a path is too *fast*, and no amount of slowing the clock fixes it, so designers guarantee it with minimum path delays. The reader explicitly wants imprecise reasoning corrected.
    Fix: "Within a synchronous design, a long enough clock period guarantees the setup time, and careful design of the shortest paths guarantees the hold time."

21. **Line 169: "The clock period must be longer than the slowest path through the combinational logic"; Self-check 7 answer, line 487.** Category: technical precision. Severity: **improvement**.
    Problem: the period must also cover the flip-flop's own clock-to-output delay and the next flip-flop's setup time (T ≥ t_clk→Q + t_logic + t_setup). The section introduces setup time just below, so the full statement is within reach.
    Fix: add "…plus the flip-flop's own small delays (its clock-to-output time and setup time)".

22. **DRAM paragraph, line 211: "The JEDEC standard for DDR4 memory requires every row to be refreshed at least once every 64 milliseconds"; Sources line 551.** Category: technical / sourcing. Severity: **improvement**.
    Problem: 64 ms applies up to 85 °C. Above 85 °C (to 95 °C) DDR4 requires 32 ms. The source given ("research literature … RowHammer") is second-hand for a JEDEC figure, when a vendor datasheet or JESD79-4 states it directly. Also, "the charge drains away within milliseconds" overstates the leak: most cells hold for far longer, and 64 ms is the guaranteed worst case.
    Evidence: Micron 8Gb DDR4 datasheet, Features: "64ms, 8192-cycle refresh up to 85°C"; "32ms, 8192-cycle refresh at >85°C to 95°C" (https://classes.engineering.wustl.edu/cse362/images/0/0c/8Gb_DDR4_SDRAM.pdf). DDR5's 32 ms window (tREFW) agrees with my knowledge of JESD79-5, but I did not fetch it.
    Fix: "…at least once every 64 ms (32 ms when the chip is hotter than 85 °C)". Cite JESD79-4 or a DDR4 datasheet. Say "the weakest cells can lose their charge in tens of milliseconds".

23. **:::orbit box, line 258: "scrubs the memory: it reads every word at regular intervals, which corrects single errors"; Terms line 292 ("periodically reading all memory to correct errors"); Self-check 12 answer, line 497.** Category: technical. Severity: **likely error**.
    Problem: reading a word through EDAC corrects only the *copy delivered to the processor*. The flipped bit stays in the memory cell unless the corrected word is **written back**. Write-back is what makes scrubbing work.
    Fix: "it reads every word at regular intervals and writes back the corrected value". Change Terms and Self-check 12 to match.

24. **Self-check 12 answer, line 497: "EDAC can correct only one flipped bit per word."** Category: technical precision. Severity: **improvement**.
    Problem: this is true of the common SECDED code that the box describes ("A common code…"), not of EDAC in general. Stronger codes (for example Reed–Solomon / chipkill) correct more.
    Fix: "The common code described can correct only one…".

25. **:::metal box, line 230: "the bootloader, the small program that receives new sketches over USB".** Category: technical precision. Severity: **improvement**.
    Problem: the ATmega328P has no USB. Optiboot receives the sketch over the serial UART (pins 0/1). The Uno's separate ATmega16U2 converts USB to serial. The 512-byte / 32,256-byte figures are correct.
    Fix: "…over the serial line, which a second chip on the Uno connects to USB".

26. **Line 227: "SRAM, which pressing reset does not wipe but which the program's start-up code reinitialises".** Category: technical precision. Severity: **improvement**.
    Problem: the start-up code (avr-libc crt) re-initializes only the *variables*: it copies .data and zeroes .bss. The rest of SRAM (stack area, unused space) keeps its old contents across a reset.
    Fix: "…but whose variables the program's start-up code re-initializes".

27. **Line 227: "The datasheet rates the non-volatile contents to be kept for 20 years at 85 °C, or 100 years at 25 °C. Those numbers explain the questions that opened this section."** Category: logic / wording. Severity: **improvement**.
    Problem: the retention figures do not explain why reset loses variables. Table 01.04-1 (which memory is volatile) does. The retention figures themselves are correct per the datasheet ("Data Retention: 20 years at 85°C/100 years at 25°C").
    Fix: "Table 01.04-1 explains the questions that opened this section."

28. **Line 197: "The ATmega328P's 2048 bytes need 11 address bits".** Category: technical precision / internal consistency. Severity: **improvement**.
    Problem: 11 bits select a byte *within* the SRAM array. The :::metal box then says SRAM occupies data addresses 0x0100–0x08FF, which need 12 bits, and `lds`/`sts` carry a 16-bit address. A careful reader will see an apparent contradiction.
    Fix: add "(inside the SRAM array; §27.03 shows how the chip maps those bytes to data addresses 0x0100–0x08FF)".

29. **Self-check 8 answer, line 489: "32 KB = 32 768 = 2^15 bytes, so 15 address bits".** Category: technical precision. Severity: **improvement**.
    Problem: the answer is right for byte addresses, but the ATmega328P's flash is organized as 16K 16-bit words. Its program counter is 14 bits, which §01.05 (program counter, modified Harvard) will show.
    Fix: add "(the AVR actually fetches 16-bit words, so its program counter needs only 14 bits; see §01.05)".

30. **"Registers: rows of flip-flops", line 179: "A processor therefore has only a few of them" and the flip-flop cost argument.** Category: technical precision. Severity: **improvement**.
    Problem: for the laptop this is the architectural view only. Modern x86-64 cores have about 180+ physical (renamed) integer registers held in multi-ported SRAM-like register files, not rows of flip-flops.
    Fix: "only a few that the program can name" (optionally with a footnote).

31. **Hands-on heading, line 383: "Hands-on (AVR / ESP32)".** Category: content. Severity: **improvement**.

The Arduino-ESP32 `EEPROM` library emulates it in flash and needs `EEPROM.begin(size)` and `EEPROM.commit()`.

32. **Hands-on A, line 387: "A NAND latch behaves like the NOR latch of this section with its inputs inverted".** Category: technical precision. Severity: **improvement**.
