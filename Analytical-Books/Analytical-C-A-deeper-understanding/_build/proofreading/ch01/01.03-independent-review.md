## A. Errors

1. **L333, "Checking everything in C": "the flags are variables declared outside any function so that every function can see them (§20.02)".**
   Category: cross-reference. Severity: **error**.
   Problem: The sentence is about visibility, which is *scope*. In toc.json §20.02 is "Storage Duration" (bullets: automatic, static, allocated and thread storage; static local variables; where each kind lives). File scope is in §20.01 "Scope" (bullets: "Block, file, function and prototype scope. | Shadowing.").
   Evidence: toc.json, refs 20.01, 20.02, 20.03.
   Fix: change to "(§20.01)". If you also want to point to how other files can see them, use "(§20.01, §20.03)".

2. **L559, Answers, Self-check 6: "the 256 appears as the carry out of the top column."**
   Category: technical / internal consistency. Severity: **error**.
   Problem: This is true only when A ≥ B. When A < B, A − B + 256 is less than 256, so no carry goes out. The 256 stays inside the eight result bits, and that is exactly the two's complement pattern. The section's own example 3 − 5 (L208: "1111 1110, which is 254, and no carry goes out") and L214 ("when A < B … it produces 0") contradict this answer.
   Evidence: `./adder8` row `3 -   5  = 254    | 0 0 1 0 |`, where C = 0 means there was no carry out.
   Fix: "If A ≥ B, A − B + 256 is at least 256, so the extra 256 leaves as the carry out (C = 1) and the eight bits hold A − B. If A < B, the sum is less than 256 and there is no carry out: the 256 stays in the result, which is the pattern 256 − (B − A), the two's complement form of the negative answer."

3. **L569, Answers, Experiment 01.03-1: "(adding 128 to each of the three arrays and changing `6` to `7` in the loop)".**
   Category: internal consistency / program. Severity: **error**.
   Problem: The third array is `sub[]`. Adding 128 to it would make `subtract = 128`, which breaks `alu_add`: the carry-in becomes 128, and so does the XOR mask. The correct edit is 128 to `xs` and to `ys`, and **0** to `sub`. The supplied verification file `a7.c` does exactly that: `sub[] = {0, 0, 0, 0, 1, 1, 0}`.
   Evidence: `diff a7.c adder8.c` shows that only `xs`, `ys` (128), `sub` (0) and the loop bound change.
   Fix: "(appending 128 to `xs` and `ys`, 0 to `sub`, and changing `6` to `7` in the loop)".

4. **L169–175, "What happens when the sum does not fit": the carries row `carries in:   1 1 1 1 1 1 1 1` over `255`.** The same misalignment occurs at L69–73 (6 + 7).
   Category: technical (worked example) / layout. Severity: **error**.
   Problem (a): In the 6 + 7 example the row lists the carry *into* each of columns 3..0, giving `1 1 0 0`, with column 0's carry-in = 0. By that convention, 255 + 1 must show `1 1 1 1 1 1 1 0` under columns 7..0, because nothing is carried into column 0. The ninth carry, out of column 7, belongs above the leading `1` of the result. As printed, the row claims a carry into column 0, and the two examples follow different conventions.
   Problem (b): In both examples every carry digit sits one character to the left of the digit columns. Carry digits are at character positions 15, 17, 19…, and operand digits are at 16, 18, 20…. This is visible in the PDF (pp. 2 and 7), so a reader cannot tell which column a carry belongs to.
   Evidence: character positions computed from L69–73 and L170–174: carries [15,17,19,21,…], operands [16,18,20,22,…].
   Fix: Align the carries over the operand digits, and for 255 + 1 write the carries into columns 8..0 as `1 1 1 1 1 1 1 1 0`, with the leftmost 1 above the result's ninth bit. You could also add a label such as "carry into each column".

5. **L305–313 with L253, L338, L358: "compares every result and flag with what C's own arithmetic says"; "compare each result and flag"; "the flags mean what Table 01.03-4 says".**
   Category: program description. Severity: **error**.
   Problem: The exhaustive check compares the result, C and V only. `flag_z` and `flag_n` are never compared with anything, so "0 mismatches" says nothing about Z and N.
   Evidence: lines 50–51 and 56–57 of Listing 01.03-2 test only `s`/`d`, `flag_c` and `flag_v`.
   Fix: Either add `|| flag_z != (s == 0) || flag_n != (s >= 128)` and the matching subtraction test (the output is unchanged; the reviewer checked this by reasoning, since Z and N are pure functions of the result), or say "every result and the C and V flags".

6. **PDF p. 16 (Self-check 4) and p. 20 (answer to Self-check 4): "A ≠ B".**
   Category: PDF layout (glyph). Severity: **error**.
   Problem: The ≠ sign is rendered as "=/" with a detached slash ("A =/B"). In the body font it reads as a different symbol.
   Evidence: page 16 rendered at 130 dpi: "cases A = B and A =/B separately".
   Fix: Use a font with U+2260 for math runs, or write "A different from B".

7. **L612, Sources: "do not depend on the compiler, since they use only small non-negative integers."**
   Category: fact. Severity: **error** (minor).
   Problem: Listing 01.03-2 computes and prints negative values: `as_signed`, `ssum`, `sdiff`, and the outputs −106 and −2.
   Fix: "since they use only small `int` values, far from any overflow, and no implementation-defined behavior".

## B. Likely errors

8. **L425, L469, L591, Experiment 01.03-3: "the longest run of columns through which a carry travels without stopping"; hint "how many pass one on?"; answer "each of the other seven columns must pass a carry on, which (0, 1), (1, 0) and (1, 1) all do".**
   Category: technical / internal consistency. Severity: **likely error** (conceptual).
   Problem: The section defines propagate as p = A ⊕ B, "this column passes an incoming carry on" (L153). Under that definition (1, 1) does **not** propagate: it *generates* a new carry whatever comes in, and its carry out settles without waiting for C<sub>in</sub>. The program counts consecutive columns whose carry *out* is 1. That is not the distance a carry travels. Example: 255 + 255 scores 8, yet no carry ripples at all, because every column generates. So the answer (2187 pairs, "one pair in thirty needs the full length") measures something other than what the experiment title, L148 ("how rare the worst case actually is") and the timing discussion claim.
   Evidence: the reviewer computed a propagate-based metric over all 65,536 pairs (generate starts a run; a column with p = 1 and a carry in extends it). Result: {0: 6561, 1: 15727, 2: 20208, 3: 12864, 4: 6080, 5: 2560, 6: 1024, 7: 384, 8: 128}. A true 8-stage ripple (column 0 generates, columns 1–7 propagate, 2<sup>7</sup> = 128 pairs) occurs for 1 pair in 512, not 1 in 30. `longest_chain(255,255)` = 8 with the book's code, and 1 with the propagate metric.
   Fix: Either (a) rename the measure honestly, for example "the longest run of consecutive columns that produce a carry out", and change "pass a carry on" in the answer to "produce a carry out when one comes in", noting that (1, 1) makes a fresh carry; or (b) change the code to restart the run at a generating column (`if (a & b) run = 1; else if ((a ^ b) && carry) ++run; else run = 0;`) and update the output block, the 2<sup>7</sup> = 128 count and "one pair in 512".

9. **L234: "Four of them appear on almost every processor".**
   Category: technical fact. Severity: **likely error**.
   Problem: Several widely used ISAs have no condition-code flags at all. MIPS, Alpha and RISC-V store comparison results in general-purpose registers. The book's own ESP32 (Xtensa LX6) uses compare-and-branch instructions and Boolean registers instead of condition codes. Because the ESP32 is one of the book's three machines, a reader who looks for "the flags" on it will find none.
   Evidence: Wikipedia, "Status register": "Some CPU architectures, such as the MIPS and Alpha, do not use a dedicated flag register… MIPS, AMD 29000, DEC Alpha, and RISC-V … store the comparison result in a general-purpose register" (https://en.wikipedia.org/wiki/Status_register). Xtensa ISA Reference Manual §1.1.7: "A complete set of compare-and-branch instructions, eliminating the need for separate comparison instructions"; §4.3.10.2: "Compared to condition codes used by other ISAs, these Booleans eliminate the bottleneck" (https://cdn.hackaday.io/files/1960678388530528/isa-summary.pdf).
   Fix: "Four of them appear on most processors that keep flags, including the AVR, x86-64 and ARM. Some designs, among them RISC-V and the ESP32's Xtensa, keep no flags at all and compare registers directly in their branch instructions." This also gives the "Hands-on (AVR / ESP32)" heading some ESP32 content (see item 18).

10. **L217 (precise box) and L614 (Sources): "the ATmega328P's datasheet describes its C flag after `SUB` as set when the second operand is larger than the first"; Sources: "Microchip, *ATmega328P Datasheet*: … the instruction descriptions of ADD, ADC and SUB (including the C flag after SUB being set when the second operand is larger), as summarised in the *AVR Instruction Set Manual*."**
    Category: source attribution. Severity: **likely error**.
    Problem: The per-flag conditions for SUB come from the **AVR Instruction Set Manual**, not the datasheet. The datasheet only has an Instruction Set Summary table listing which flags each instruction affects, and the reviewer has seen no flag-condition text in it. The Sources line also gets the relationship backwards: the datasheet summarizes the manual, not the other way round. (The datasheet PDF itself could not be downloaded here; the proxy refused the request, so this rests on the summary table's known format.)
    Evidence: AVR Instruction Set Manual §6.119.2 (SUB): "C: Set if the absolute value of the contents of Rr is larger than the absolute value of Rd; cleared otherwise." "H: Set if there was a borrow from bit 3; cleared otherwise." (https://onlinedocs.microchip.com/oxy/GUID-0B644D8F-67E7-49E6-82C9-1B2B9ABE6A0D-en-US-23/GUID-7376A183-0B47-4321-A7B5-A07A684E056C.html)
    Fix: L217: "Microchip's *AVR Instruction Set Manual* describes the C flag after `SUB` as set when …". L614: split into "ATmega328P Datasheet: SREG bit definitions; instruction timing (ADD 1 cycle)" and "AVR Instruction Set Manual (Microchip DS40002198): flag definitions for ADD, ADC, SUB."

11. **L199: "the result it shows is exactly **A − B**."**
    Category: technical precision. Severity: **likely error** (imprecise statement in bold).
    Problem: For A < B the adder shows A − B + 256 (for example 254 for 3 − 5), not A − B. The text corrects this only implicitly in L212. It is the same flaw as item 2.
    Fix: "the result it shows is A − B modulo 256: exactly A − B when A ≥ B, and, when A < B, the 8-bit pattern that (as shown below) stands for the negative number A − B."

## C. Improvements: technical and consistency

12. **L381: "The AVR uses S for its signed comparison instructions."**
    Severity: improvement. The compare instructions (`CP`, `CPC`, `CPI`) are the same for signed and unsigned comparison. It is the signed conditional *branches* (`BRLT`, `BRGE`) that test S. The manual's own wording for S is "N ⊕ V, for signed tests". Fix: "the AVR's signed conditional branches (`BRLT`, `BRGE`) test S".

13. **L374 (Table 01.03-5, H row) with L543 ("paying special attention to … the H flag").**
    Severity: improvement. The C row says "(after subtraction: borrow)", but the H row gives only "a carry out of bit 3 into bit 4". After `SUB`, H is a *borrow* from bit 3, as the manual says (item 10). A reader asked to predict H for 3 − 5 from the table would reason from the adder's raw half-carry (0011 + 1010 + 1 gives no carry out of bit 3, so H = 0) and get it wrong (simavr: H = 1). Fix: H row: "Half carry: a carry out of bit 3 into bit 4 (after subtraction: a borrow from bit 3)".

14. **L599–606, Hands-on output block.**
    Severity: improvement (exactness rule). The sketch prints `" "` after *every* bit, including the last, so each real output line ends with a trailing space before CR LF. The block has none.
    Evidence: `simavr -m atmega328p -f 16000000 flags.elf | cat -A`: `6 + 7 = 13    I T H S V N Z C = 0 0 0 0 0 0 0 0 ..$`, with a space before the line end. All six lines otherwise match character for character.
    Fix: Print the separator before bits 6..0 only (`if (bit > 0) Serial.print(" ");`), or accept the trailing space in the block.

15. **L569: the quoted output line `` `128 + 128  =   0    | 1 1 0 1 |     0    |    0` ``.**
    Severity: improvement. The program prints it with a leading space (`%4d`): `" 128 + 128  =   0 …"`. Inline code also wraps badly in the PDF (p. 20). Fix: show it as a one-line ```output block with the leading space.

16. **L184 (hood box): "GCC notices that the same circuitry can add two numbers and place the result in a third register in one step, without disturbing the status flags".**
    Severity: improvement (fact vs inference). Whether LEA uses "the same circuitry" as ADD is a microarchitectural claim and is not labeled as inference. The main reason for using LEA here is that it is a three-operand add (destination ≠ either source), which saves a `mov`. Fix: "LEA can add two registers and put the sum in a third, in one instruction; `add` would need a `mov` first. It also leaves the flags alone."

17. **L217: "Both designs use the same adder; they differ only in what they store."**
    Severity: improvement. This is the author's inference about undisclosed internals, yet it is stated as fact. Label it ("in effect …") or add it to "Inference and assumptions" (L617).

18. **L483 heading "Hands-on (AVR / ESP32): watching the flags"; PDF p. 6 box label "ON THE METAL (AVR / ESP32)".**
    Severity: improvement. Neither contains anything about the ESP32. Either retitle them "(AVR)" or add a short ESP32 note. Item 9 supplies the content: Xtensa has no flags, so the same C on the ESP32 compiles to compare-and-branch instructions.

19. **L361, orbit box: "Chapters 04 and 10 are devoted to it."**
    Severity: improvement. Ariane's fault was an out-of-range float → 16-bit integer conversion. No chapter is "devoted" to that lesson. The relevant TOC entries are §04.05 "Width, Sign Extension and Truncation" and §10.05 "Casts: Conversions on Purpose" (float topics in Chapter 07). Fix: "and §04.05 and §10.05 return to it."

20. **L162, metal box: "How Microchip actually built the AVR's adder".**
    Severity: improvement. The AVR core was designed at Atmel, which Microchip acquired in 2016. Fix: "How Atmel (now part of Microchip) built …".

21. **L393, Terms: "Carry-lookahead (parallel-prefix) adder: … in time growing with the logarithm of the width."**
    Severity: improvement. A classic single-level carry-lookahead adder (for example 4-bit groups rippling between groups) is not logarithmic. Only hierarchical or parallel-prefix forms are. L159 keeps the two names separate, but the Terms entry merges them. Fix: give separate entries, or write "Carry-lookahead and parallel-prefix adders: … in the best designs, in time growing with the logarithm of the width."

22. **L385–404, Terms introduced.**
    Severity: improvement. "Inline assembly" (bold at L485) and "carry flag" (bold at L181) are introduced but not listed. "Propagation delay" is reused from §01.02, which is fine.

23. **L224: "A multiplexer choosing between two bits X and Y with a select signal S is simply (S′ · X) + (S · Y)".**
    Severity: improvement. In this section S already means the sum bit (L82) and, later, the AVR sign flag (L375). Use another letter, for example "Sel" or "M".

24. **L411 and L555 (Self-check 4) use "C" for C<sub>in</sub>.**
    Severity: improvement. C is also the carry output of the half adder (L82) and the carry flag. Use C<sub>in</sub> as in L122–124.

25. **L35: "with avr-gcc 7.3.0 and GCC 14.2 using `-O2`".**
    Severity: improvement. Readers can take this as "both using -O2". The AVR run used `-Os` (L18). Fix: "avr-gcc 7.3.0 with `-Os` and GCC 14.2 with `-O2`".

26. **L613, Sources, Hands-on: "compiled with avr-g++ 7.3.0".**

The only dot on that wire is at its upper corner (y ≈ 180), where nothing branches. Readers taught "dot = connection" may think the XOR 1 output is unconnected. Fix in `fig_adders.py`: move `elm.Dot()` from `(7.2, x2.in2[1])` to `(7.2, x1.out[1])`.
