## Summary

The section is strong, and its arithmetic is clean. I re-derived every conversion, table cell, self-check answer and experiment answer, and all are correct:
- Table 04.01-3 (32,769/0x8001, 185/0xB9, 4,104/0x1008).
- Table 04.01-4 (3/6/11/22 octal digits; 3/5/10/20 decimal digits).
- The two CCSDS decodings (APID 100, count 42, 16 bytes; APID 44, count 5, 4 bytes).
- The 0xCCCCCCCD derivation via 1/5 = 0.333…₁₆.
- MOV R2,R3 = 010203.
- The three §03.07 bases (0x55ffbc6cb000, 0x560134e40000, 0x555555554000, all multiples of 0x1000).
- 0x8FF = 2,303; 0x12C = 300; NOT 0x39 = 0xC6.
- The Intel HEX checksum (D0 checks).
- 3735928559 = 0xdeadbeef = 033653337357.

All x86-64 output blocks match logs 099/100/101 character for character. All eight listings are byte-identical to their files, and every "Line N" reference is right. The C23 printf text, B's octal rule and its `09` remark, `printn` and its ASCII comment, and GCC 4.3's `0b` constants are all confirmed. No converter-rule violations were found.

The errors cluster in three places:
- **The opening "promises" list.** Two of the listed numbers (`0x1E+1`, `0777777`) are never returned to. Several others were already explained by the sections that used them, and the recaps of §01.05, §01.06 and §02.01 are inexact.
- **Historical claims.** Early C was exactly as relaxed about `09` as B; that changed only with C89. The PDP-7's 9-bit characters were hedged in §02.01 but are stated as fact here. *Algoritmi de numero Indorum* is an 1857 editorial title.
- **One misleading simplification.** "Dividing by 2 needs no arithmetic at all" is true only for unsigned values.

The rendering also labels the `simavr` command as a "Fedora terminal", although Fedora has no simavr. On pedagogy: several C constructs in the listings (`static`, `const`, a cast, `++`/`--`, `\"`, `%s`/`%c`/`%lu`, `sizeof`, `NULL`) are used without a word of explanation.

Counts: **11 errors, 12 improvements, 13 nits.**

## Errors

**E1. Two of the "promises" listed in the opening are never kept (lines 15–16, 21).**
Line 21 says: "Each of these was a promise. This section keeps them all."

What is wrong:
- **`0x1E+1` (line 16).** It is never mentioned again in the section; `grep 0x1E` finds only line 16. Yet this section is exactly where the puzzle can finally be explained from first principles. In hexadecimal, `E` is a *digit* (fourteen). §03.02's preprocessing-number rule treats `E` (or `e`) followed by `+` as the start of a floating-point exponent, because it does not know that it is inside a hexadecimal numeral. `0x1F+1` has no `E`, so the rule never fires.
- **`0777777` (line 15).** It is never decoded. The history box explains only `150145`. "Six octal 7s are eighteen 1 bits" is one sentence, and §02.01 line 217 already said it. So either it was never an open promise, or this section must say it.

Correction:
- Add to habit 4 (or to "Writing numbers in C") a short paragraph: "Now §03.02's puzzle. In `0x1E`, the `E` is a hexadecimal digit, fourteen: 0x1E = 1 × 16 + 14 = 30. But the preprocessor's rule for numbers knows nothing of bases, and an `E` followed by `+` might begin a floating exponent (`1.5E+10`), so it swallows `0x1E+1` whole. `0x1F` contains no `E`, which is why `0x1F+1` compiled. With a space, `0x1E + 1`, the `E` is safely inside the numeral."
- Add after line 448: "and §02.01's mask `0777777` is six octal 7s, six groups of `111`: eighteen 1 bits, exactly one PDP-7 word."

**E3. Early C was as relaxed as B about `09`; and Table 04.01-5 dates the bases wrongly (lines 464, 561–563).**
Line 464 says: "(B was more relaxed than C about it: its manual notes that `09` was legal there, and equal to `011`.)" Table 04.01-5 gives decimal as "the first C (K&R, 1978)" and hexadecimal as "the first C (K&R, 1978)".

What is wrong:
- **Early C accepted 8 and 9 too.** Ritchie's *C Reference Manual* (the 1974/75 Unix manual, cman.pdf) §2.3.1 says: "An integer is taken to be octal if it begins with 0, decimal otherwise. The digits 8 and 9 have octal value 10 and 11 respectively." K&R C (1978) kept the same rule, so `019` was 17. It was the 1989 ANSI standard that limited octal digits to 0–7. C was not stricter than B until C89.
- **The same 1975 manual has no hexadecimal constants.** Hex is in K&R 1978, but decimal and octal were in C from the start (1972–73), inherited from B, years before K&R. Calling K&R 1978 "the first C" is wrong for decimal and misleading for octal.

Correction:
- Line 464: "(B, and C itself until the 1989 standard, were more relaxed: B's manual notes that `09` was legal and equal to `011`, and Ritchie's C Reference Manual of the mid-1970s said the same of 8 and 9. ANSI C (1989) made them errors.)"
- Table, decimal row: "C from the start (1972–73); inherited from B".
- Table, octal row: "C from the start; inherited from B (8 and 9 accepted until C89)".
- Table, hexadecimal row: "by K&R (1978); absent from the 1975 C Reference Manual".
- Self-check 13 / Answer: optionally add "and so would C before 1989".
- Sources: cite the C Reference Manual.

**E4. "Dividing by 2 needs no arithmetic at all" is true only for unsigned values (lines 366–373, Experiment 04.01-4 answer line 816).**
Line 366: "so dividing by 2 needs no arithmetic at all: every bit simply moves one place to the right … Ask GCC to divide by 2 and by 16 …, and that is exactly what it does". The block that follows reads `x / 2: shrl %eax`.

What is wrong: `x` is never said to be unsigned. A beginner will apply the rule to `int`, and for a signed `x` it is false: C's division truncates toward zero, while a shift rounds toward −∞. **[workspace]** gcc-14 `-O2`:
```
int h(int x){return x/2;}    ->  movl %edi,%eax; shrl $31,%eax; addl %edi,%eax; sarl %eax
int s(int x){return x/16;}   ->  testl %edi,%edi; leal 15(%rdi),%eax; cmovns %edi,%eax; sarl $4,%eax
unsigned u(unsigned x){...}  ->  movl %edi,%eax; shrl %eax
```
The TOC lists exactly this for §10.02: "Shifts in place of powers of two, and the trap with signed values."

Correction:
- Line 366: "Ask GCC to divide an `unsigned` number by 2 and by 16 …".
- Block labels: `x / 2 (x unsigned):`.
- After line 373: "(This is for unsigned numbers. For a signed `int`, C rounds the quotient toward zero, and a shift alone would round −7 / 2 to −4, so GCC adds a correction first; §10.02 shows the trap.)"

**I1. Explain the C that the listings use but the text never mentions.** The section promises (line 219) that "each piece is explained here as far as this section needs, and the chapter that teaches it fully is named". It does not explain the following:
- **Listing 04.01-2.**

  - `const char *text` (§06.06, §24.04).
  - The cast `(unsigned)d` on line 17. Explain why it is there: comparing a signed `int` with an `unsigned` draws `-Wsign-compare` under `-Wextra`, and the cast is safe because `d >= 0` has just been checked (§10.05).
  - `return;` in a `void` function (§18.02).
  - The escape `\"` on line 14 (§08.02).
  - The conversions `%s`, `%c`, `%lu` and `%u` (§31.02).
- **Listing 04.01-3.** `count++` and `--count`. Explain that `reversed[count++] = …` stores and *then* counts, while `reversed[--count]` counts down and *then* reads (§11.03). Also `putchar` (§08.04).
- **Listing 04.01-5.**
  - `FILE *`, `fopen(…, "wb")` (the `b` meaning binary) and `fclose` (§32.02).
  - Line 7, `if (f == NULL) return 1;`: "if the file cannot be opened, stop with exit status 1 (§03.07)".
  - `sizeof bytes`: the number of bytes in the array, here 10.
  - `fwrite`'s three numbers.

One bullet per listing would do.

**I2. Separate the octal digit 0 from C's prefix 0 (Figure 04.01-1; lines 448, 796; 464).** For 57 the coincidence hides the difference. The top two bits `00` form an octal *digit* 0, so the octal numeral is "0 7 1", and the figure labels it "written 071 in C" as if that digit were the prefix. Line 448 says "the octal numeral is 071", and Self-check 9's answer writes "00 111 001 = `071`". A beginner can conclude that the C prefix *is* the leading group. Use a counterexample:
- 0xFF = 11 111 111 = octal 377, written `0377` in C (prefix plus three digits).
- 0x39 = 00 111 001 = octal 071 or 71, written `071` or `0071` in C (`071` is not "prefix 0 + digit 0 + 71").

Say this once after line 448. It also explains the leading 0 of the PDP-11's `010203`, which is the top bit and not a prefix.

**I3. Say that "flip every bit" is for a stated width (line 446; Self-check 10).** "So to flip every bit of a hexadecimal numeral, subtract each digit from F … the NOT of 0x39 is 0xC6". This is right for an 8-bit byte. A reader who tries `printf("%x\n", ~0x39)` gets `ffffffc6` **[workspace]**, because `0x39` is a 32-bit `int`. Write "the 8-bit NOT of 0x39 is 0xC6 (in a 32-bit `int`, every one of the eight digits flips: 0xFFFFFFC6; Chapter 13)".

**I4. Permissions: twelve bits, and why your `same.c` may say 644 (lines 469–480).**
- **Twelve bits.** "Linux records who may read, write and execute a file as nine bits" omits the set-user-ID, set-group-ID and sticky bits, which form a fourth octal digit. The author's own job 100 shows `4755 -rwsr-xr-x` for `/usr/bin/passwd` and `1777 drwxrwxrwt` for `/tmp`. A reader who runs `stat` on those files will see four digits. Add one sentence: "Three more bits (set-user-ID, set-group-ID, sticky) make a fourth octal digit on the left; `stat -c '%a' /usr/bin/passwd` prints 4755."
- **600 versus 644.** `same.c` showed `600` on the reader's Fedora, presumably because of how the runner created the file. A file made in an editor under the usual umask 022 shows `644 -rw-r--r--`. Say "(yours may show 644, the usual default; §32.01)" so the reader is not puzzled.

**I5. Give the Intel HEX line something new: its checksum (line 543).** Since §01.06 already decoded the fields (E2), let this section teach the checksum, which is pure hexadecimal arithmetic. The sum of all the bytes of a record, the checksum included, is 0 modulo 256. Here 0x10 + 0x00 + 0x00 + 0x00 + 0x25 + … + 0x40 = 0x430, whose low byte is 0x30, and 0x30 + 0xD0 = 0x100 (I verified that D0 is correct). A self-check could ask the reader to verify `:04001000E1F7F7CF4E`.

**I6. CCSDS: make the field descriptions exact (line 637; Self-check 15).**
- The 3-bit field `000` is what CCSDS 133.0-B-2 calls "Version 1" (the Packet Version Number field is '000' for a Version-1 CCSDS Packet). "version 0" will confuse a reader who opens the standard. Write "version field 000 (which CCSDS calls Version 1)".
- "2 sequence flags" reads as two separate flags. Write "a 2-bit sequence-flags field".
- The length counts the whole *packet data field*, secondary header included, minus one. Since the example has a secondary header, write "so 16 bytes follow the primary header (secondary header and data together)". Do the same in the Self-check 15 answer.
- Chapter 13 is right for shifts and masks; §28.06, "Structures for Protocols and Telemetry", is also worth naming.

**I7. Hedge the SEAC/A–F claim to what the source says, and use Leibniz (line 466).**
- **SEAC.** As I could access Strickland & Jones, they antedate *hexadecimal* to 1950 for SEAC's input notation. Separately, they say that the digits "chosen by the National Bureau of Standards were … 0–9 and … A–F, and these have remained standard ever since". The summary I obtained says they do not state that SEAC used A–F in 1950; please check the paper's exact sentence.
- **SWAC.** The SWAC, which used u–z, was also an NBS machine, so "NBS chose A–F" needs care.
- **The 1966 convention.** Wikipedia credits the A–F convention's general adoption to IBM's FORTRAN IV manual for System/360, "beginning in 1966".
- **Suggested wording.** "…the US National Bureau of Standards, whose SEAC used the word *hexadecimal* for its input notation in 1950, chose A to F, the convention that survives; it became universal with IBM's System/360 manuals of the mid-1960s."
- **Leibniz.** He wrote base-16 conversions as early as 1679 (Strickland & Jones), which would make "Base sixteen had been proposed long before computers" concrete and justify the Leibniz citation in Sources.

- **For the record.** **[workspace, avr-gcc 7.3]** The single `__udivmodhi4` call is inside `print_in_base`, and `__ultoa_invert` contains the internal `rcall`s, consistent with the Fedora log.

**I9. Tie the tally to the rule "base b ≥ 2" (lines 70, 118).** "In every base *b*, the same four facts hold" is true only for b ≥ 2. One sentence makes the tally, the opening example, part of the theory instead of a curiosity: "(With b = 1 there would be no exchange at all, only one mark per unit: the child's tally.
