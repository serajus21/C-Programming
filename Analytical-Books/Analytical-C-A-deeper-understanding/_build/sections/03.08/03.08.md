## The question

Most programs in this chapter were compiled with the same four options, `-std=c23 -Wall -Wextra -pedantic`, and earlier sections of this chapter have shown messages from the compiler: §03.01's `noinclude.c`, `glued.c` and `indent.c`, §03.02's trigraphs and §03.03's `#warning`. This last section of Chapter 03 turns to the messages themselves: what kinds there are, who prints them, how to read them precisely, and what the four options do. It keeps three promises. §03.01 promised a close reading of its three messages. §03.05 promised to show where debugging information describes local variables. §03.07 promised the option `-g`, which gave `gdb` the source lines that it could not show for `hello`.

Six puzzles, all from your Fedora:

- Listing 03.08-1, `bugs.c`, has six mistakes. Compiled with plain `gcc -std=c23`, it builds in silence, and it runs and prints `0 1 11 30 30` and then `-86833936`: wrong in five places out of six. With `-Wall -Wextra`, the compiler names five of the six mistakes, each at its exact line and column.
- The sixth mistake, a variable used before it is given a value, is not reported at `-O0`, GCC's default; it is reported as soon as an optimization level such as `-O1` or `-O2` is added.
- One missing line in `noinclude.c` produced an `error`, a `warning` and two `note`s, and no program.
- In `brace.c`, a `}` is missing at line 8. The compiler's error points at line 15, the last line of the file, and it adds a warning that `main` "is normally a non-static function", although `main` in the file is perfectly ordinary.
- `-Wall` does not enable all warnings. On the reader's machine, GCC's list of warning options for C has 215 lines; 41 warnings are on with no option at all, and `-Wall` turns on 53 more, 94 in all.
- With `-Werror` added, the five warnings of `bugs.c` become five errors, and no program is produced.

The questions are:

- What does the C standard require a compiler to say, and what decides whether GCC calls a message an error or a warning?
- How is a message built, and what does each of its parts tell you?
- Which program in the chain of §03.02 is speaking, and how can you tell?
- Why does an error sometimes point far from the mistake?
- What do `-Wall`, `-Wextra`, `-pedantic` and `-Werror` really enable, and why are some warnings found only with optimization?
- Why insist on a program that compiles with no warnings at all?

## The journey

### What the standard requires, and what GCC adds

The C standard says very little about messages. In C11 (ISO/IEC 9899:2011), §5.1.1.3, "Diagnostics":

"A conforming implementation shall produce at least one diagnostic message (identified in an implementation-defined manner) if a preprocessing translation unit or translation unit contains a violation of any syntax rule or constraint, even if the behavior is also explicitly specified as undefined or implementation-defined. Diagnostic messages need not be produced in other circumstances."

Its footnote 9 adds the intent: "The intent is that an implementation should identify the nature of, and where possible localize, each violation. Of course, an implementation is free to produce any number of diagnostics as long as a valid program is still correctly translated. It may also successfully translate an invalid program."

Read the requirement closely, because it is narrower than most programmers assume.

- **Only two kinds of violation must be diagnosed.** A *syntax rule* is the grammar, the rules in the sections headed "Syntax". A *constraint* is a rule in a section headed "Constraints" (§02.04). Everything else needs no message, in particular undefined behavior that breaks no syntax rule or constraint (§02.04). None of the six mistakes in `bugs.c` (below) breaks such a rule, so the standard requires no message for any of them: three are undefined behavior, and three are well-defined code that does exactly what was written, not what was meant.
- **"At least one diagnostic", not "an error".** The standard does not say that the translation must stop, or that the message must be called an error; the footnote even allows an invalid program to be translated. A compiler that prints a warning and goes on to produce a program has satisfied it. (The one case where the standard requires translation to fail is the directive `#error`.)
- **The form is the implementation's to choose.** The words "error", "warning" and "note" are GCC's, not the standard's.

GCC's manual divides its messages into two kinds. In its section "Warnings and Errors", *errors* report problems that make it impossible to compile the program, and *warnings* report unusual conditions that may indicate a problem, while compilation goes on. Most warnings are off until an option such as `-Wall` turns them on. GCC deliberately compiles what it can: it does not reject a program merely because the program does not strictly conform to the standard. Where the standard requires a diagnostic for one of GCC's extensions, `-pedantic` produces it as a warning and `-pedantic-errors` as an error.

So a GCC message belongs to one of two groups, and its label does not tell you which:

1. **A diagnostic the standard requires**, for a constraint or syntax violation. GCC labels some of these errors (`int n = ;`) and some warnings (the `-Wpedantic` messages below). Since GCC 14, six required diagnostics that used to be warnings, all for code relying on rules that C99 removed (among them implicit `int` and implicit function declarations), are errors by default; GCC calls them *permerrors*, and `-fpermissive` turns them back into warnings ("Porting to GCC 14"; §03.01).
2. **A diagnostic the standard does not require**, about a program that is valid but probably not what you meant (`if (x = 0)`). These are most warnings.

### The anatomy of a message

§03.01 showed the messages for `noinclude.c`, `hello.c` without its `#include`. Here they are again from the reader's machine, read now part by part:

```terminal
$ gcc -std=c23 -Wall -Wextra -pedantic -c noinclude.c; echo gcc-exit $?
```

```output
noinclude.c: In function ‘main’:
noinclude.c:4:5: error: implicit declaration of function ‘printf’ [-Wimplicit-function-declaration]
    4 |     printf("hello, world\n");
      |     ^~~~~~
noinclude.c:1:1: note: include ‘<stdio.h>’ or provide a declaration of ‘printf’
  +++ |+#include <stdio.h>
    1 | // noinclude.c
noinclude.c:4:5: warning: incompatible implicit declaration of built-in function ‘printf’ [-Wbuiltin-declaration-mismatch]
    4 |     printf("hello, world\n");
      |     ^~~~~~
noinclude.c:4:5: note: include ‘<stdio.h>’ or provide a declaration of ‘printf’
gcc-exit 1
```

Every message follows one pattern, `file:line:column: kind: text [option]`, and the lines around it add context and pictures:

- **`noinclude.c: In function ‘main’:`** A context line: the messages that follow concern the function `main`. Only the first message in a new function or scope gets one.
- **`noinclude.c:4:5:`** The position: file, line 4, column 5. Columns count from 1, and line 4 begins with four spaces, so column 5 is the `p` of `printf`. The position is where the compiler *noticed* the problem, which (as `brace.c` will show) is not always where the mistake is.
- **`error:`** The kind. `error` means that no output file will be produced; `warning`, that this message by itself does not stop the build; `note`, that this line explains the message before it and is not a separate problem; and `fatal error`, that the compiler stopped at once.
- **The text**, `implicit declaration of function ‘printf’`. The curly quotation marks enclose things as the compiler names them: names and tokens from your text, but also types in the compiler's own spelling (in `bugs.c` below, ‘unsigned int’ for the `unsigned` you wrote) and the compiler's suggestions.
- **`[-Wimplicit-function-declaration]`** The name of the option that controls this message. It tells you which entry of the manual explains it, and how to change its treatment: `-Wno-...` turns a warning off, `-Werror=...` makes it an error. This one is shown in brackets although it is an error, because since GCC 14 it is an error by default that the option can still control.
- **The source excerpt**, `    4 |     printf("hello, world\n");`: the line, with its number in a margin.
- **The caret line**, `^~~~~~`: the `^` marks the column of the position, and the `~` characters underline the whole range concerned, here the name `printf`.
- **The fix-it hint**, `+++ |+#include <stdio.h>`, printed with the note at `1:1`: a proposed edit. The `+` marks a line to insert, before line 1. The note says the same in words.

The second message is a consequence of the first. Having assumed a declaration for `printf` that C89 would have assumed, the compiler compares it with what it knows of the real `printf`, a *built-in* function (§03.04), and the two disagree: `[-Wbuiltin-declaration-mismatch]`. One missing line, two messages, and the first is the one to fix. And the last line, `gcc-exit 1`, is the driver's exit status (§03.01): 0 if no error occurred, warnings or not, and non-zero otherwise (1 for ordinary errors). That number is what `make` (§21.08) uses to decide whether a build step failed.

The format can be changed. Under `LANG=C`, which selects plain ASCII output, the curly quotes become straight ones: `this 'if' clause does not guard...`. `-fno-diagnostics-show-caret` leaves out the excerpt and the caret. And for programs that read diagnostics, such as editors, GCC (since version 13) can write them in SARIF, a standard format based on JSON, with `-fdiagnostics-format=sarif-stderr`. On the reader's machine it begins `{"$schema": "https://docs.oasis-open.org/sarif/sarif/v2.1.0/...`; the older value `json` is refused, and GCC lists the accepted ones: `sarif-file sarif-stderr text`.

Two further features of the pictures appear in `bugs.c` below. In the message for `printf("%d\n", 3.5)`, *labels* under the underlined parts name their types, `int` and `double`, and a suggested replacement, `%f`, appears beneath. In the message for the missing `break`, a `note: here` points at the second place involved.

### Who is speaking

A message can come from any of the programs that §03.02 showed the driver running. Listing 03.08-2 contains one deliberate failure for each, selected with a macro.

```c Listing 03.08-2  phases.c: one failure for each stage of the build
// phases.c
// Which program complains? Build with -DSTAGE=1, 2, 3 or 4.
#if STAGE == 1
#include <stdoi.h>                      // preprocessor: no such header
#endif
#include <stdio.h>

void undefined_elsewhere(void);         // declared, never defined

int main(void) {
#if STAGE == 2
    int n = ;                           // compiler: not C
#elif STAGE == 3
    __asm__("movq %rax, %rbx, %rcx");   // assembler: no such instruction form
#elif STAGE == 4
    undefined_elsewhere();              // linker: no definition anywhere
#endif
    puts("built");
    return 0;
}
```

The four builds, on the reader's machine, each with `gcc -std=c23 -Wall -Wextra -pedantic -DSTAGE=`*n*` phases.c -o phases`*n*:

```output
phases.c:4:10: fatal error: stdoi.h: No such file or directory
    4 | #include <stdoi.h>                      // preprocessor: no such header
      |          ^~~~~~~~~
compilation terminated.
```

```output
phases.c: In function ‘main’:
phases.c:12:13: error: expected expression before ‘;’ token
   12 |     int n = ;                           // compiler: not C
      |             ^
phases.c:12:9: warning: unused variable ‘n’ [-Wunused-variable]
   12 |     int n = ;                           // compiler: not C
      |         ^
```

```output
/tmp/ccMtC5uv.s: Assembler messages:
phases.c:14: Error: number of operands mismatch for `movq'
```

```output
/usr/bin/ld.bfd: /tmp/ccebmwlI.o: in function `main':
phases.c:(.text+0x5): undefined reference to `undefined_elsewhere'
collect2: error: ld returned 1 exit status
```

Each build failed (exit status 1), and each message shows its author:

1. **The preprocessor** (phase 4 of §03.02, inside `cc1`): a `fatal error`, and GCC stops at once: `compilation terminated.` (Presumably because without the header everything after it would produce a cascade of messages; this reason is the author's.)
2. **The compiler proper**: an `error` at line 12, column 13, the `;` where an expression was required. Then the compiler *continued*, and found a second problem in the same line: the variable `n` is never used. A compiler that stopped at the first error would be simpler, but a programmer would then see one problem per build. GCC recovers from the error, as best it can, and reads on.
3. **The assembler**, `as`: a different format altogether. `Assembler messages:` names the temporary assembly file, `Error:` has a capital E, there is no column and no picture, and the quotes are the backquote and apostrophe of older GNU tools. The instruction text came straight from your `__asm__` string, which the compiler copied into the assembly file without checking it (§03.04); only the assembler understands instructions. It can still name `phases.c:14`; according to the independent reviewer of this section, who looked at the assembly file, because the compiler surrounds the `__asm__` text with a line marker naming `phases.c` and line 14.
4. **The linker**, `ld.bfd`: §03.06's undefined reference, with the position given as a section and an offset in the object file, `(.text+0x5)`: the call's 4-byte hole begins after `push %rbp` (1 byte), `mov %rsp,%rbp` (3) and the `e8` of `call` (1). The object file contains no line table, so the linker cannot name a line; built with `-g` (end of this section), the same link reported `.../phases.c:16:(.text+0x5): undefined reference to ...`. The final line comes from `collect2`, GCC's helper, which ran `ld` and reports its failure.

The rule that follows: before reading a message, see who wrote it. A message about a header is the preprocessor's; one about types and expressions, the compiler's; one with `Error:` and no column, the assembler's; one about references and sections, the linker's. The fix belongs at that stage: a missing header is an `#include` or a missing package; an undefined reference is a missing file or library on the link command, not something a change inside the function can repair.

### Reading errors: where the mistake is, and where it is noticed

The parser (§03.04) reads tokens from left to right and reports an error at the first token that cannot continue anything grammatical. That is the position you are given: the place where the program became impossible, which may be after the place where it went wrong. Listing 03.08-3 omits one `;`.

```c Listing 03.08-3  cascade.c: one missing semicolon
// cascade.c
// One missing character, how many messages?
#include <stdio.h>

struct point {
    int x;
    int y;
}                       // the ';' that ends the declaration is missing

int main(void) {
    struct point p = {1, 2};
    printf("%d\n", p.x + p.y);
    return 0;
}
```

```output
cascade.c:10:1: error: expected ‘;’, identifier or ‘(’ before ‘int’
   10 | int main(void) {
      | ^~~
```

The mistake is at the end of line 8; the message is at line 10, column 1. After `struct point { ... }`, a declaration usually goes on with a name (`struct point { ... } origin;`) or ends with `;`. The next token, two lines later, is `int`, and `int` cannot be added to `struct point` as a second type, so this is the first token at which the program can no longer be valid. GCC recognizes the familiar pattern of a `struct` definition followed by the start of a new declaration, and suggests the likely repairs: `expected ‘;’, identifier or ‘(’`. (The grammar would also allow `*`, `const` and other continuations; the message is GCC's best guess, not a list of everything possible.) The parser can only report where it *noticed*, and here the message is still a good guide: the missing token is "before `int`", and the place before `int` is the end of line 8.

Listing 03.08-4 shows how far apart the two places can drift.

```c Listing 03.08-4  brace.c: a missing closing brace
// brace.c
// A missing closing brace, reported far from where it is missing.
#include <stdio.h>

static int twice(int x) {
    if (x > 0) {
        return 2 * x;
                        // the '}' of the if is missing
    return 0;
}

int main(void) {
    printf("%d\n", twice(21));
    return 0;
}
```

```terminal
$ gcc -std=c23 -Wall -Wextra -pedantic brace.c -o brace
```

```output
brace.c: In function ‘twice’:
brace.c:12:1: warning: ISO C forbids nested functions [-Wpedantic]
   12 | int main(void) {
      | ^~~
brace.c:12:5: warning: ‘main’ is normally a non-static function [-Wmain]
   12 | int main(void) {
      |     ^~~~
brace.c:15:1: error: expected declaration or statement at end of input
   15 | }
      | ^
brace.c:16: warning: control reaches end of non-void function [-Wreturn-type]
brace.c: At top level:
brace.c:12:5: warning: ‘main’ defined but not used [-Wunused-function]
   12 | int main(void) {
      |     ^~~~
```

Every message is correct, given what the compiler saw. Without the `}` of the `if`, the `}` on line 10 closes the `if`, and `twice` is still open. So `int main(void) { ... }` on line 12 is, to the compiler, a function defined *inside* `twice`: a *nested function*, which standard C forbids and GCC accepts as an extension. The first message says so outright, thanks to `-pedantic`: "ISO C forbids nested functions". Seen that way, the others fall into place:

- A nested function is local to its enclosing function, so `main` is not an ordinary, visible function: "‘main’ is normally a non-static function".
- At the end of the file, `twice` has still not been closed: "expected declaration or statement at end of input", at line 15, the last line.
- `twice` therefore ends without a `return` on that path: line 16, the end of input, has no column.
- And the nested `main` is never called inside `twice`: "defined but not used".

(The context line `In function ‘twice’` before a message about `main` was already the clue.) The rules for reading errors follow. **Fix the first error first**, because later messages may be consequences of it, and rebuild; here, one inserted `}` should make all five messages disappear (a prediction; the corrected file was not built for this section). **Read the position as "noticed here", and look at and before it.** **Believe the compiler's view of your program.** A message that seems absurd is an exact report on the program the compiler read, which may not be the one you think you wrote. `glued.c` in §03.01 was another instance: two missing spaces gave a function called `intmain` with no type and a name `return0` with no declaration, and its third message, `control reaches end of non-void function`, followed from both glued pairs: `intmain` made a function whose type defaulted to `int` (the first message), and `return0;` is not a `return` statement (the token behind the second).

### Warnings: the earliest detector of bugs

Errors stop you; warnings do not, and that is why they need attention. Listing 03.08-1 contains six common mistakes, each marked in a comment.

```c Listing 03.08-1  bugs.c: six small mistakes
// bugs.c
// Six small mistakes. How many does the compiler mention?
#include <stdio.h>

static int is_zero(int x) {
    if (x = 0)                          // meant: x == 0
        return 1;
    return 0;
}

static unsigned count_below(const int *a, int n, unsigned limit) {
    unsigned c = 0;
    for (int i = 0; i < n; ++i)
        if (a[i] < limit)               // int compared with unsigned
            ++c;
    return c;
}

static int sum(const int *a, int n) {
    int total;                          // never set to 0
    for (int i = 0; i < n; ++i)
        total += a[i];
    return total;
}

static int sign(int x) {
    if (x > 0) return 1;
    if (x < 0) return -1;
}                                       // no return when x == 0

static int days(int month) {            // 1 = January
    int d = 31;
    switch (month) {
    case 2: d = 28;                     // forgot break: falls through
    case 4: case 6: case 9: case 11: d = 30; break;
    }
    return d;
}

int main(void) {
    int a[3] = {-1, 5, 7};
    printf("%d %u %d %d %d\n", is_zero(0), count_below(a, 3, 6),
           sum(a, 3), sign(0), days(2));
    printf("%d\n", 3.5);                // wrong conversion for a double
    return 0;
}
```

The intended output is `1 2 11 0 28` and, for the second line, `3.500000` (which needs `%f`). Compiled with nothing but `-std=c23`, on the reader's machine:

```terminal
$ gcc -std=c23 bugs.c -o bugs && ./bugs
```

```output
0 1 11 30 30
-86833936
```

Not a single message, and five wrong results. Now with `-Wall -Wextra`:

$ gcc -std=c23 -Wall -Wextra bugs.c -o bugs

Three of the results deserve a closer look, because they show why the standard does not promise anything here.

- **The 30 from `sign(0)`.** A function returns a value by leaving it in a register, `eax` (§03.04). When `sign` runs off its end, nothing is put there, and the caller reads whatever was left. In the author's reading of this run, GCC evaluated the arguments of the first `printf` from right to left (C leaves the order unspecified), so `days(2)` ran just before `sign(0)` and left its 30 in `eax`. Built with `-O2`, the same call printed `0`. Using the value of a function that ended without `return` is undefined behavior (§02.04), and both 30 and 0 are within its rights.
- **The `-86833936`.** By the calling convention (§19.02), a `double` argument travels in a vector register, `xmm0`, while `%d` makes `printf` read the next integer register, `rsi`, which no one set. In the author's reading, the number is a leftover value of `rsi` read as an `int`; with `-O2` it was `-1125812560`.
- **The 11 from `sum`.** Correct, and still a bug: the program depended on a value that no line of it supplied. That is the most dangerous kind of mistake, the one that passes every test until something changes on the stack.

### Why one warning needs optimization

With `-O2` added, a sixth message appeared:

```output
In function ‘sum’,
    inlined from ‘main’ at bugs.c:42:5:
bugs.c:22:15: warning: ‘total’ is used uninitialized [-Wuninitialized]
   22 |         total += a[i];
      |         ~~~~~~^~~~~~~
bugs.c: In function ‘main’:
bugs.c:20:9: note: ‘total’ was declared here
   20 |     int total;                          // never set to 0
      |         ^~~~~
```

The first two lines say what happened: at `-O2`, the code of `sum` had been copied into `main` at line 42, the optimization called *inlining* (§03.04), and there `n` is known to be 3. Counting warnings at each level on the reader's machine gave 5 at `-O0` and 6 at `-O1`, `-O2`, `-O3` and `-Og`. Why not at `-O0`? GCC does check for uninitialized values without optimization: a function `int f(void) { int x; return x; }` drew `‘x’ is used uninitialized` at `-O0`. But that early check reports only reads that certainly happen, and in `sum` the read is inside a loop that runs zero times when `n` is 0. Once `sum` has been inlined where the loop certainly runs, the read is certain. The manual is explicit that these warnings depend on the optimizer: of `-Wuninitialized`, "Because these warnings depend on optimization, the exact variables or elements for which there are warnings depend on the precise optimization options and version of GCC used", and of `-Wmaybe-uninitialized`, "These warnings are only possible in optimizing compilation, because otherwise GCC does not keep track of the state of variables." The practical rule: compile with warnings at the optimization level you will ship, not only at `-O0`.

GCC has a further tool for mistakes that need deeper analysis, its *static analyzer*, enabled by `-fanalyzer`. On `bugs.c` it reported the uninitialized `total` even at `-O0` (`use of uninitialized value ‘total’ [CWE-457]`, three times) and the value returned by `sign` (`use of uninitialized value ‘<return-value>’`). The `CWE-457` is the number of this kind of weakness in a public catalog of software weaknesses.

### What the options turn on

`-Wall` sounds like "all warnings". The manual's description is more modest: "This enables all the warnings about constructions that some users consider questionable, and that are easy to avoid (or modify to prevent the warning), even in conjunction with macros." Of `-Wextra`: "This enables some extra warning flags that are not enabled by -Wall." GCC can list every warning option and say whether it is on (`gcc -Q --help=warnings,c`). Counting the lines marked `[enabled]` on the reader's machine:

```output
[]                         41
[-Wall]                    94
[-Wall -Wextra]            112
[-Wall -Wextra -pedantic]  116
```

So `-Wall` adds 53 to the 41 that are on by default, and `-Wextra` 18 more. The full list has 215 lines, including variants and aliases. (The counts are approximate in one respect: options that take a level, such as `-Wformat=1`, show the level instead of `[enabled]`, and some options show no mark at all. The level explains the `=` in `[-Wformat=]` and `[-Wimplicit-fallthrough=]`: the bracket names the option family.) Warnings outside these sets must be named one by one; for instance `-Wshadow` (a local name hides an outer one) and `-Wconversion` (an implicit conversion may change a value), which, in the author's reading of the manual's criterion, are left out because they also fire on much correct code. With both added, `bugs.c` gave the same five warnings, no more.

`-pedantic` (also spelled `-Wpedantic`) concerns the standard, not likely mistakes. The manual: "Issue all the warnings demanded by strict ISO C and ISO C++; diagnose all programs that use forbidden extensions, and some other programs that do not follow ISO C and ISO C++. This follows the version of the ISO C or C++ standard specified by any -std option used." Listing 03.08-5 uses two GNU extensions.

```c Listing 03.08-5  pedantic.c: two GNU extensions
// pedantic.c
// Two GNU extensions: accepted in silence until -pedantic is given.
#include <stdio.h>

int main(void) {
    int empty[0];                                      // zero-length array
    int max = ({ int a = 3, b = 4; a > b ? a : b; });  // statement expr.
    printf("%zu %d\n", sizeof empty, max);
    return 0;
}
```

Built with `gcc -std=c23` alone, it compiles in silence and prints `0 4`. With `-pedantic`:

```output
pedantic.c: In function ‘main’:
pedantic.c:6:9: warning: ISO C forbids zero-size array ‘empty’ [-Wpedantic]
    6 |     int empty[0];                                      // zero-length array
      |         ^~~~~
pedantic.c:7:15: warning: ISO C forbids braced-groups within expressions [-Wpedantic]
    7 |     int max = ({ int a = 3, b = 4; a > b ? a : b; });  // statement expr.
      |               ^
```

With `-pedantic-errors`, the same two messages say `error:` and no program is built. With `-std=gnu23 -pedantic`, GCC's own dialect of C23 with extensions, the warnings still appear, because `-pedantic` measures the program against the ISO standard underneath the dialect. A zero-length array violates a constraint (an array's size must be greater than zero), and a statement expression is not in the grammar at all, so both warnings are diagnostics the standard requires; GCC labels them warnings, as its manual says it will. This book uses `-std=c23 -pedantic` so that GCC reports the uses of its extensions that the standard requires it to report, which helps keep the programs within ISO C. It is not a complete check of portability: `-pedantic` does not detect undefined behavior, nor most code whose meaning depends on the implementation.

### `-Werror` and the warning-free discipline

`-Werror` turns every warning into an error. The manual's entry is one line: "Turn all warnings into errors." On `bugs.c`, the five messages are the same, each now `error:` with the option shown as `[-Werror=parentheses]` and so on, and a final line explains:

```output
cc1: all warnings being treated as errors
```

No `bugs` program was written, and the driver's exit status was 1 instead of 0. The selective form, `-Werror=return-type`, makes only that one warning an error, and leaves the others warnings.

Why build every program so that the compiler has nothing to say? The reasons are practical.

- **A new warning must be visible.** In a build that prints twenty old warnings, the twenty-first, the one about the mistake you made this morning, goes unnoticed. In a build that prints nothing, any message stands out.
- **Warnings are cheap, and bugs are not.** Each warning in Table 03.08-1 cost a few seconds to read and fix. The same mistakes, found later by a wrong result, cost the time to notice the wrong result, find its cause and trust the fix. §03.01's `indent.c` recalled one that shipped in an operating system's security library.
- **Silence must mean something.** A program that compiles without warnings under `-Wall -Wextra -pedantic` has passed a check; one that compiles with "only a few harmless warnings" has passed none.

Fixing a warning means changing the program so that it says what you mean, not hiding the message. When the compiler warns about something you intended, C and GCC provide ways to say so explicitly, and Listing 03.08-6 shows three. It compiled on the reader's machine with `-std=c23 -Wall -Wextra -pedantic` and no messages, and printed `got 5` and `3 1`.

```c Listing 03.08-6  fixed.c: deliberate choices, stated
// fixed.c
// Deliberate choices, written so that the compiler need not guess.
#include <stdio.h>

static int next_value(void) { return 5; }

static int rank(char grade) {            // passing grades, counting down
    int n = 0;
    switch (grade) {
    case 'A': ++n; [[fallthrough]];      // C23: the fall-through is intended
    case 'B': ++n; [[fallthrough]];
    case 'C': ++n; break;
    }
    return n;
}

static int first(int x, [[maybe_unused]] int y) {   // y: fixed interface
    return x;
}

int main(void) {
    int v;
    if ((v = next_value()))              // the assignment is intended
        printf("got %d\n", v);
    printf("%d %d\n", rank('A'), first(1, 2));
    return 0;
}
```

- **`[[fallthrough]]`**, an *attribute* of C23, states that falling into the next `case` is intended, and silences `-Wimplicit-fallthrough` at that place only.
- **`[[maybe_unused]]`**, also C23, states that a parameter may go unused, as when a function must have a fixed list of parameters to fit an interface.
- **Doubled parentheses**, `if ((v = next_value()))`, are a convention that GCC and Clang share for "I mean the assignment". They change nothing in the meaning, and `-Wparentheses` accepts them.

The last resort is `#pragma GCC diagnostic` (§03.03), which turns a warning off for a region of a file; it belongs around code you cannot change, such as a header from someone else, and nowhere else.

One caution about `-Werror` itself. Each new version of GCC adds and refines warnings, so a program that builds cleanly today may produce a new warning with next year's compiler. In the author's understanding, the common practice is therefore to use `-Werror` while developing and in your own automated builds, where a new warning should stop you, but not to impose it on others who build your published source with compilers you have not tried.

:::myth
"A program that compiles without errors is correct, and warnings are the compiler being fussy." `bugs.c` compiled without errors and was wrong in five of six places; the warnings named five of the six mistakes before the program ever ran. The opposite myth is just as wrong: a program with no warnings is not thereby correct. The compiler sees only what is visible in the text and in its analyses, and `bugs.c` at `-O0` with `-Wall -Wextra` still hid one mistake. Warnings are the earliest and cheapest detector of bugs, not the last.
:::

### On the AVR

avr-gcc speaks the same language, and on a microcontroller its warnings often concern the hardware directly. Listing 03.08-7 has two mistakes that the compiler can see.

```c Listing 03.08-7  avr_warn.c: a pin that does not exist, and a delay without F_CPU
// avr_warn.c  (ATmega328P)
// A pin that does not exist, and a delay without F_CPU.
#include <avr/io.h>
#include <util/delay.h>

int main(void) {
    DDRB = 1 << 8;                      // PB8 does not exist (bits 0-7)
    for (;;) {
        PORTB ^= 1 << 5;
        _delay_ms(500);
    }
}
```

```terminal
$ avr-gcc -mmcu=atmega328p -std=c11 -Os -Wall -Wextra -pedantic avr_warn.c -o avr_warn.elf
```

```output
In file included from avr_warn.c:4:
/usr/avr/include/util/delay.h:91:3: warning: #warning "F_CPU not defined for <util/delay.h>" [-Wcpp]
   91 | # warning "F_CPU not defined for <util/delay.h>"
      |   ^~~~~~~
avr_warn.c: In function 'main':
avr_warn.c:7:12: warning: unsigned conversion from 'int' to 'uint8_t' {aka 'unsigned char'} changes value from '256' to '0' [-Woverflow]
    7 |     DDRB = 1 << 8;                      // PB8 does not exist (bits 0-7)
      |            ^
```

Both are warnings, so `avr_warn.elf` was built, and both describe a program that would not work.

- **The first message comes from avr-libc, through the preprocessor.** `<util/delay.h>` contains a `#warning` directive (§03.03) that fires when the macro `F_CPU`, the processor's clock frequency, is not defined; the header then assumes a default, `# define F_CPU 1000000UL` (line 107 of the reader's copy), 1 MHz. On a board running at 16 MHz, every delay would then be sixteen times too short, and the LED would flicker instead of blinking. The line `In file included from avr_warn.c:4:` tells you how the compiler reached the header. With `-DF_CPU=16000000UL` this warning disappeared.
- **The second is `-Woverflow`**, which is on by default and needs no `-Wall`. `1 << 8` is 256, and `DDRB` is an 8-bit register: the conversion keeps the low 8 bits, which are all 0, so the program would configure no pin as an output at all: `PB5` stays an input, and each `PORTB ^= 1 << 5` merely switches its weak internal pull-up resistor on and off. The braces in `{aka 'unsigned char'}` translate the type name `uint8_t` into the type it stands for.

(avr-gcc prints plain apostrophes where Fedora's GCC prints curly quotes; the author has not established why, and it changes nothing in the messages.)

### One more thing the compiler can tell you: `-g`

§03.07 used `gdb` on `hello`, and `gdb` could show addresses and function names but no source lines: `Breakpoint 1 at 0x40113a`, and nothing about which line of `hello.c` that was. The option `-g` asks the compiler to write **debugging information**: a description of the program in terms of its source, for debuggers to read. Built from `where.c` (Listing 03.07-2), with and without `-g`:

```output
-rwxr-xr-x. 1 serajus21 serajus21 12704 Nov 27 02:39 where
-rwxr-xr-x. 1 serajus21 serajus21 14128 Nov 27 02:39 where_g
  [29] .debug_aranges    PROGBITS        0000000000000000 002308 000030 00      0   0  1
  [30] .debug_info       PROGBITS        0000000000000000 002338 0000f9 00      0   0  1
  [31] .debug_abbrev     PROGBITS        0000000000000000 002431 0000b3 00      0   0  1
  [32] .debug_line       PROGBITS        0000000000000000 0024e4 00006a 00      0   0  1
  [33] .debug_str        PROGBITS        0000000000000000 00254e 0000d5 01  MS  0   0  1
  [34] .debug_line_str   PROGBITS        0000000000000000 002623 0000a0 01  MS  0   0  1
```

The program with `-g` is 1,424 bytes larger, and the difference is six new sections whose names begin `.debug_`, in a format called **DWARF**. They have no `A` flag (§03.05): they are not loaded into memory, and the code does not change. On the reader's machine, the disassembly of `main` was identical in both programs, and `size` reported the same 1,276 bytes of `text` for both. With them, `gdb` speaks in source terms:

```output
Breakpoint 1 at 0x40114e: file where.c, line 10.

Breakpoint 1, main () at where.c:10
10	    int local = 2;
11	    printf("main   0x%" PRIxPTR "\n", (uintptr_t)main);
local = 2
$1 = (int *) 0x7fffffffe26c
Line 11 of "where.c" starts at address 0x401155 <main+15> and ends at 0x40116c <main+38>.
```

(This is the output of `break main`, `run`, `next`, `info locals`, `p &local` and `info line`; lines about debuginfod and the thread library are omitted.) Without `-g`, the same `info locals` answered `No symbol table info available.`

Two of the sections answer §03.05's and §03.07's promises.

- **`.debug_line` maps addresses to lines.** `readelf --debug-dump=decodedline where_g` prints the table: line 9 at 0x401146, line 10 at 0x40114e, line 11 at 0x401155, line 12 at 0x40116c, and so on to line 16. That is how `gdb` knew that `main`'s first line of code, after its prologue, is line 10 at 0x40114e, and that line 11 ends at 0x40116c.
- **`.debug_info` describes local variables.** The entry for `local`, from `readelf --debug-dump=info where_g`:

```output
 <2><e8>: Abbrev Number: 12 (DW_TAG_variable)
    <e9>   DW_AT_name        : (indirect string, offset: 0x57): local
    <ed>   DW_AT_decl_file   : 1
    <ee>   DW_AT_decl_line   : 10
    <ef>   DW_AT_decl_column : 9
    <f0>   DW_AT_type        : <0x5d>
    <f4>   DW_AT_location    : 2 byte block: 91 6c 	(DW_OP_fbreg: -20)
```

§03.05 found that a local variable has no symbol and no section: it exists only on the stack while its function runs. Here is how a debugger finds it anyway. The entry gives its name, the line and column of its declaration, its type (a reference to another entry, `int`), and its *location*: "`DW_OP_fbreg: -20`", 20 bytes below the function's *frame base*. `main`'s own entry gives the frame base as `DW_OP_call_frame_cfa`, the *canonical frame address*: the value `rsp` had just before the `call` that entered `main`. Check it against the code and `gdb`. `main` begins with `push %rbp` and `mov %rsp,%rbp`, so `rbp` is 16 bytes below that value (8 for the return address, 8 for the saved `rbp`); the code stores the 2 at `-0x4(%rbp)`; and 16 + 4 = 20. `gdb` printed `&local` as 0x7fffffffe26c, so the frame base was 0x7fffffffe26c + 20 = 0x7fffffffe280. The location is a small program for the debugger: the two bytes `91 6c` are the operation `DW_OP_fbreg` (0x91) and its operand, −20 written in a compact signed format.

`-g` and optimization can be combined. Built with `-g -O2`, the breakpoint on `main` showed `local = 0` at line 10, before the assignment had run, and `local = 2` two lines later: at both levels, `gdb` shows what is in the variable's memory at that moment. Optimization does make the description harder to follow (code moves, and variables can disappear from registers between uses), and §39.02 returns to debugging optimized code.

:::orbit
In the author's understanding, the rule of zero warnings is nowhere stricter than in software for spacecraft. Gerard J. Holzmann, of NASA's Jet Propulsion Laboratory, made it the last of his ten rules for safety-critical code (IEEE Computer, 2006): "All code must be compiled, from the first day of development, with all compiler warnings enabled at the most pedantic setting available. All code must compile without warnings." He applied it even to messages the developer believes mistaken: "If the compiler or analyzer gets confused, the code causing the confusion should be rewritten." The reasoning is the one this section has followed. Flight software cannot be patched by a visit, a warning costs seconds while a fault in orbit can cost the mission, and code that confuses the compiler is likely to confuse the next engineer who reads it. The same rule asks for the code to be checked daily with at least one static analyzer, the role that `-fanalyzer` plays in a small way in this section.
:::

## Terms introduced

- **Diagnostic**: any message from the compiler; the standard requires at least one for a violation of a syntax rule or a constraint, and none otherwise.
- **Syntax rule / constraint**: a rule of the grammar / a rule in a section headed "Constraints" of the standard; violations of either must be diagnosed.
- **Error / warning / note / fatal error (GCC)**: a problem that prevents output / a probable problem that does not / an explanation attached to the preceding message / an error that stops the compiler at once.
- **Position (`file:line:column`)**: where the compiler noticed a problem; columns count from 1.
- **Caret line / underline / label**: the `^` marking the position, the `~` marking the range, and the type names written beneath.
- **Fix-it hint**: a proposed edit printed with a message (`+++ |+#include <stdio.h>`).
- **Option name in brackets**: the `-W...` option that controls a message; `-Wno-...` disables it, `-Werror=...` makes it an error.
- **Error recovery**: the compiler's continuing after an error, to report further problems in one build.
- **Cascade**: messages that are consequences of an earlier mistake; fix the first and rebuild.
- **`-Wall` / `-Wextra`**: GCC's main and extra sets of warnings about probable mistakes; neither enables all warnings.
- **`-pedantic` (`-Wpedantic`) / `-pedantic-errors`**: diagnostics required by strict ISO C, including for GNU extensions, as warnings / as errors.
- **`-Werror` / `-Werror=name`**: treat all warnings / one warning as errors.
- **GNU extension**: a feature of GCC's dialect not in ISO C, such as zero-length arrays, statement expressions and nested functions.
- **Static analyzer (`-fanalyzer`)**: a deeper, slower analysis that follows the paths of a program to find mistakes such as uses of uninitialized values.
- **CWE**: the Common Weakness Enumeration, a public catalog of kinds of software weakness, cited by `-fanalyzer`.
- **`[[fallthrough]]` / `[[maybe_unused]]`**: C23 attributes stating that a fall-through is intended / that something may go unused.
- **SARIF**: a standard, JSON-based format for diagnostics, for tools; `-fdiagnostics-format=sarif-stderr`.
- **Debugging information / DWARF**: the description of a program in source terms, in the `.debug_*` sections, written by `-g`.
- **Line table**: the part of DWARF (`.debug_line`) that maps addresses to source lines.
- **Frame base / canonical frame address (CFA)**: the reference point for a function's local variables in DWARF; here, the value of `rsp` before the call.

## Answers

**Self-check 1.** At least one diagnostic message, in a form the implementation defines. It does not require the message to be called an error, nor the translation to stop; and it requires nothing at all for mistakes that violate neither a syntax rule nor a constraint, such as most undefined behavior.

**Self-check 2.** `bugs.c`: the file; `14`: the line; `18`: the column; `warning`: a probable problem, output still produced; the text: what was compared; `[-Wsign-compare]`: the option controlling it (enabled by `-Wextra`). Column 18 is the `<` operator, counting the eight spaces of indentation and `if (a[i] `: the comparison itself.

**Self-check 3.** Having assumed the C89 implicit declaration `int printf()` for an undeclared function, the compiler compared it with its built-in knowledge of `printf`, whose declaration differs. The message is a consequence of the missing `#include`, and the fix-it printed with the note, adding `#include <stdio.h>`, removes both.

**Self-check 4.** STAGE 1: the preprocessor (`fatal error` about a header, `compilation terminated.`). STAGE 2: the compiler proper (`error` with a column and a picture, about an expression). STAGE 3: the assembler (`Assembler messages:`, `Error:`, a `.s` file in `/tmp`, no column). STAGE 4: the linker (`/usr/bin/ld.bfd`, a section and offset, `collect2: error: ld returned 1 exit status`).

**Self-check 5.** The compiler can report only where it noticed that the program could not be valid: the first such token, `int` on line 10, which cannot be added to `struct point` as a second type. The text says what was expected "before ‘int’", and the place before `int`, skipping comments and blank lines, is the end of line 8.

**Self-check 6.** Without the `}` of the `if`, the `}` on line 10 closes the `if`, and `twice` remains open. `main` is then a nested function inside `twice` (a GNU extension, which `-pedantic` reports: "ISO C forbids nested functions"), so it is not an ordinary visible function ("normally a non-static function") and is never called there ("defined but not used"); the file ends with `twice` open ("expected declaration or statement at end of input", line 15); and `twice` has no `return` on that path ("control reaches end of non-void function", line 16). The context line names `twice` because, to the compiler, `main` is inside `twice`.

**Self-check 7.** At `-O0` GCC reports only reads of uninitialized variables that certainly happen, and the read of `total` is inside a loop that might run zero times. With optimization, `sum` was inlined into `main`, where `n` is 3, the loop certainly runs, and the read is certain; the manual states that these warnings depend on the optimization options. `-fanalyzer` is a separate analysis that follows the paths of the program symbolically, at any optimization level, and found the uninitialized `total` at `-O0`.

**Self-check 8.** It relies on a value that the program never provides; the 0 in the memory used for `total` was an accident of what ran before. Any change, another call before it, another compiler, another optimization level, can change that accident, and the bug then appears far from its cause, long after the code was tested.

**Self-check 9.** Facts of C: the order in which the arguments of a call are evaluated is unspecified, and using the value of a function that ended without `return` is undefined. Facts of the calling convention: an `int` is returned in `eax`. Facts of this build, in the author's reading: GCC evaluated the arguments from right to left, so `days(2)` ran just before `sign(0)` and left 30 in `eax`, which `sign(0)`, returning without setting it, passed on. With `-O2` the result was 0.

**Self-check 10.** "all the warnings about constructions that some users consider questionable, and that are easy to avoid (or modify to prevent the warning), even in conjunction with macros." With no options 41 warnings are on, with `-Wall` 94. `-Wshadow` and `-Wconversion` warn also about much code that is correct and intended, so avoiding them is not always easy, and the manual's criterion leaves them out (the reason is the author's reading of the criterion).

**Self-check 11.** Yes: a zero-length array violates a constraint, the standard requires a diagnostic, and a warning is a diagnostic. With `-pedantic-errors` the same message becomes an error and no program is produced.

**Self-check 12.** A new warning stands out only in a silent build; warnings are far cheaper to deal with than the bugs they reveal; and silence then means "passed a check". Against imposing `-Werror` on others: newer compilers add warnings, so a published program would stop building for others with no change in its code (the author's understanding of common practice).

**Self-check 13.** `[[fallthrough]]`: the fall-through into the next `case` is intended. `[[maybe_unused]]`: the parameter may be unused. The doubled parentheses: the assignment in the condition is intended. Each silences the warning at one place only and records the intention in the code for the next reader, while the warning stays active everywhere else, where it may find a real mistake.

**Self-check 14.** Without `F_CPU`, `<util/delay.h>` assumes 1 MHz, sixteen times slower than the Uno's clock, so every delay would be sixteen times too short. And `DDRB = 1 << 8` stores 0, so PB5 stays an input: each `PORTB ^= 1 << 5` only switches its weak internal pull-up on and off, and the pin is never driven as an output. Whether the LED shows anything then depends on the board's LED circuit (not tested); either way it is not the intended blink.

**Self-check 15.** From the location expression `DW_OP_fbreg: -20`: 20 bytes below the frame base, which `main`'s entry defines as the canonical frame address, the value of `rsp` before the `call`. Frame base = 0x7fffffffe26c + 20 = 0x7fffffffe280. `rbp` is 16 bytes below the frame base (return address and saved `rbp`), so `-0x4(%rbp)` is 16 + 4 = 20 bytes below it.
